## 一、现象（用户实测，2026-09-04 12:36）

一台电脑**同一 Windows 账号**开 3 个会话，各跑 BGI。开了联机助手的会话已显示「⚠ 跨会话」徽章（说明上一版发送端阻断已生效），但**污染仍发生**：正在跑任务的 BGI（日志标识 `Primary:S2:P22956`）被注入新任务，日志：

```
[12:36:56.173] [INF] TaskControl 将传送至 "须弥" "道成林" 七天神像
[12:36:56.189] [ERR] TaskRunner 任务启动失败：当前存在正在运行中的独立任务，请不要重复执行任务！
```

两个诉求：① 跨会话的任务注入必须彻底防住（发送端阻断不够）；② 这个报错不应导致正在执行的任务退出。

## 二、架构背景（已查实，不要重新调查）

- 助手↔BGI 通信：命名管道 `BetterGI.v2.user-{用户SID}.root`，隔离粒度是**用户 SID 不是 SessionId**。
- 同 SID 多会话时：第一个启动的 BGI 抢到 `FirstPipeInstance` 成为 Primary 持唯一管道（`BetterGenshinImpact/Service/Instance/InstanceBootstrap.cs:79-131`），其余会话的 BGI 降级为 ChildSession，**不注册任何 task.* 操作**（`InstanceRequestHandler.cs:111-113` 有预留 TODO）。任何会话的助手连管道都由 Primary 独答。
- 跨用户不会串（SID 管道名 + 服务端 ACL Deny 非 owner，`InstanceBootstrap.cs:288-298`）。
- 助手「跑任务」徽章数据链：本地管道轮询 `task.status` → 助手每 10s 上报服务器（`MainViewModel.cs:2841` → `SignalRClient.cs:279-289`）→ `RoomManager.UpdateControlStatus`（:1170-1187）→ 房间广播。裸 BGI 从不调 `ReportControlStatus`。

## 三、已完成的修复（commit 42b81a04，发送端止血）

`MultiplayerHoeingAssistant` 侧：`IpcClient.ConnectAsync` 成功后自动发 `ping` 比对对端 `windowsSessionId` 与本进程 SessionId（`VerifyRemoteSessionAsync`）；不可信（CrossSession/Unknown）时不采信 `task.status`、`TaskRunning` 按 false 上报、阻断 task.start/热键/关游戏/挂起恢复等控制指令、UI 亮「⚠ 跨会话」徽章。

**为什么不够**：阻断在**发送端**。其他会话若跑的是**没有此修复的旧版助手（或任何能连管道的脚本）**，仍可直接向 Primary 的 BGI 发 `task.start`——BGI 侧收到控制 op 时**零校验**（见下）。这正是徽章已亮、污染仍发生的最可能解释。

## 四、根因（两条，均已定位）

### 根因 1：BGI 侧对 IPC 控制指令没有发送方会话校验

- `InstanceRequestHandler.HandleTaskStart`（`BetterGenshinImpact/Service/Instance/MessageHandlers/InstanceRequestHandler.cs:501-684`）方法体**完全不引用 `connection` 参数**；`task.stop/suspend/resume/execute_hotkey/close_game` 同样无任何校验。
- **但基础设施已存在**：`InstanceConnection` 构造函数（`InstanceConnection.cs:44-58`）对每个服务端连接都通过 `GetNamedPipeClientProcessId` + `ProcessIdToSessionId`（:367-399，P/Invoke 已就绪）捕获了 `ClientProcessId` / `ClientSessionId`（:62-64）。目前只有 `HandleConnectionOpenAsync`（:173-176）消费这两个字段。

### 根因 2：HandleTaskStart「先杀再问」——预取消直接杀死在跑任务

用户观察到"在跑的任务退出了"**完全属实**，机制：

1. `HandleTaskStart` **:536-541**：主线程**无条件**执行 `CancellationContext.Cancel()` + `CancelTokenOnly()`——**在跑任务这一刻已被判死刑**，无论新任务能否启动。
2. :546-551：轮询等 `TaskControl.TaskSemaphore`（容量 1，TaskControl.cs:36）释放，上限 15 秒。
3. 超时仍继续 → `ScriptService.RunMulti`（ScriptService.cs:135）→ **:140 `CancellationContext.Instance.Set()` 重置全局取消上下文（WasCancelled 清 false）** → `TaskRunner.RunThreadAsync`。
4. `TaskRunner.RunCurrentAsync` **:52** `TaskSemaphore.WaitAsync(0)` 抢锁失败 → **:55 打 ERR 日志后直接 return（这步本身无损，不用改）**。

时间线重构：注入 task.start 于 ~12:36:41 到达 → 旧任务被 Cancel → 旧任务 12:36:56 打出最后一次回血传送 INF 后开始退出（清理 >15s 未放锁）→ 同秒新任务抢锁失败打 ERR。

**二次伤害**：RunMulti:140 的 `Set()` 把 WasCancelled 清成 false，导致 HandleTaskStart 末尾 :612-617 读不到取消标记，**给调用方返回 `status="started"`**（实际什么都没启动）——"新任务没起来、旧任务被杀、调用方还收到成功"。

### 已排除的假设

- 「将传送至七天神像」日志只有 `TpTaskOfficial.cs:293` / `TpTaskFastDrag.cs:240` 两处，都在 `TpToStatueOfTheSeven()`（回血/复苏传送）内，调用方全是任务内部逻辑（AutoFight 团灭复活、锄地回血等）。**注入的新任务在抢锁失败处就返回，执行不到任何传送**——该 INF 是旧任务自己打的，不是注入任务打的。
- 新版助手的所有 task.start 入口（房间远程指令、本机 UI、上线联动、自动恢复、热键注入）均已确认被 `CheckCrossSessionBlock()` 覆盖，无漏网。
- `config.pull_group`/`config.apply_group`/远程配置编辑等未守卫路径**不能注入任务**（只读写配置/弹 UI，属独立风险，本次可顺带一并拦截）。

## 五、修复任务（两个都做，a 治本 b 防御纵深）

### 任务 a：BGI 侧 IPC 控制指令统一会话守卫（治本）

落点：`InstanceRequestHandler.HandleAsync` 分发 switch（**:67-109**）**之前**加统一守卫（单点拦截，优于逐 handler 加）。

- 判定：`connection.ClientSessionId`（InstanceConnection.cs:64，构造时已捕获）vs `_context.WindowsSessionId`（InstanceContext.cs:37），不一致即拒绝。
- 建议拦截 op 集合：`TaskStart`、`TaskStop`、`TaskSuspend`、`TaskResume`、`ExecuteHotkey`、`CloseGame`、`SetTaskEnabled`、`ConfigApplyGroup`、`ConfigOpenRemoteEditor`（会在别人会话弹编辑器 UI）、`ConfigPullGroup`（跨会话读配置）。
- 返回 `InstanceIpcEnvelope.Failure(request, "cross_session_rejected", ...)`，附客户端/服务端 SessionId 便于排查，并打 LogWarning。
- `ClientSessionId == null`（P/Invoke 失败）时 **fail-closed**：拒绝控制类 op（参照 :173-176 connection.open 先例）。查询类（task.status/config.list/ping）可放行或同样拒绝——建议拒绝，与助手 42b81a04 的 Unknown 降级语义一致。
- 已验证合法性：BGI 内部（ChildSession→Primary 转发等）**没有任何路径发 task.\*/hotkey/close_game 类 op**，拦截不影响实例间正常通信；同会话助手 ClientSessionId == Primary 会话，正常放行。

### 任务 b：HandleTaskStart 无损拒绝（修"误杀在跑任务"）

- 主要落点：`HandleTaskStart` **:536 之前**——先查 `TaskControl.TaskSemaphore.CurrentCount == 0`（有任务在跑）则**直接返回失败响应，绝不做 Cancel**。把"先杀再问"改成"先问再杀"。原有 15s 等待和 generation 逻辑保留给正常路径。
- 次要落点：`ScriptService.RunMulti` **:140** 的 `CancellationContext.Instance.Set()` 在抢锁之前执行，会重置全局 WasCancelled。建议把 Set() 移到确认拿锁之后，或至少保证抢锁失败路径不影响 WasCancelled。注意这是单机/联机共用代码，改动需论证单机零感知（Set() 时机后移一位，语义等价）。
- `TaskRunner.cs:52-61` 本身已是无损拒绝（只打日志 return），**不要改**。
