## 1. 仲裁面定位与分层

| 层 | 职责 | 既有/新建 |
|---|---|---|
| BGI 执行锁 | 任一时刻至多一个在跑任务；PreemptionGate（A6 抢占/释放/takeover ticket）与 BgiTaskCoordinator 作业注册表为权威执行事实 | 既有，不动 |
| **槲寄生逻辑所有者租约（本阶段新建）** | 决定「哪个候选有权请求执行权」——排序、交接、压制；**不直接持执行锁**，执行权仍经既有 ext/v2 提交路径向 BGI 申请 | 新建（助手侧） |
| 原生模式 | 无计划引用时 BGI 原生模式不受影响（锚点 3） | 既有，不动 |

- 租约是**可逆运行态**：正常退出/失联（TTL 过期）即失效，不留永久只读或永久压制。
- F11 是**独立停止闸门**，先于一切排序与租约判断，不作候选；**F11 停止状态独立于租约生命周期**——
  租约释放/重新获取不解除已触发的 F11（其实现仍走 BGI 既有最终停止权路径）。
- 无双跑第一原则（R-1）：任何交接不确定 → 不启动，宁可错过触发不错跑。

## 2. 入口请求分类与候选模型

**入口请求三分类**（接线时按此分流，恢复请求**不进普通排序**）：
1. **可排序执行意图**（start/preempt）→ 归一为 ArbitrationCandidate 进排序；
2. **控制动作**（skip/stop/F11）→ system 层直接路径，不经排序（F11 走独立闸门）；
3. **既有运行恢复请求** → §5 四类合同分流，仅 A6 类要求票据；暂停续行/普通 Interrupted 恢复不要求 A6 票据。

**候选三件套**（不把所有上下文塞进候选）：

| 件 | 内容 |
|---|---|
| ArbitrationCandidate | 身份（§2.1）+ 排序键（tier/priority/scheduledAt）+ 执行意图引用（resourceRef+intent=start/preempt） |
| EligibilitySnapshot | 到点/窗口、链内前置就绪、人工暂停、固定排程占用、F11 态、票据与执行占用——**资格判定的全部输入** |
| HandoffContext | 被切作业身份、目标实例+epoch、动作关联号、确认截止时间——交接状态机的持久化段（§4/§6） |

### 2.1 规范化身份元组（ASTRA B2 冻结）

`stableIdentity = scope | namespace | workflowId | 触发出现身份 | runId | 节点出现身份 | 轮次 | attempt`
（Ordinal 字典序；`|` 为分隔符，各段不含分隔符）。**节点出现身份 = `nodeOccurrenceIdentity=(nodeId, occurrence)`**——
nodeId 与 occurrence 分别编码（既有 RunStore 模型中 occurrence 整数不在 run 内全局唯一，A/B 两节点可同 occurrence=0）；
各段固定规范化表示（可逆无歧义，澄清 2 冻结）：空=`~`、整数定长补零（8 位）、时间=UTC ISO8601、Guid="N" 小写串、字符串 Ordinal 原样（大小写不折叠）；**保留字符转义**：值内字面量 `~`→`~0`、`|`→`~1`（先转义再拼接，解码逆向单射）。

  **身份编码规则表（四轮阻断二冻结——实现者无任何自裁分支）**：

  | 字段类别 | 规则 |
  |---|---|
  | 整数（occurrence/轮次/attempt 等） | 非负整数，值域 0..99,999,999，定长 8 位补零；**越界或负值=编码响亮拒绝（不截断、不扩宽、不静默通过）** |
  | 时间（scheduledAt 等） | 唯一文本形式 `yyyy-MM-ddTHH:mm:ss.fffffffZ`（UTC、7 位小数、Z 后缀；不接受 `+00:00` 或省略小数的等价形式——比较前必须归一到此形式） |
  | Guid | "N" 格式 32 位小写十六进制 |
  | 字符串 | Ordinal 原样，大小写不折叠；保留字符先转义（`~`→`~0`、`|`→`~1`） |
  | 组合身份 | 字段顺序=§2.1 元组固定顺序，段间 `|` 分隔，先逐段编码再拼接 |

- `scope` = BGI 目标实例+epoch 命名空间；`namespace` = 入口类别（`trigger / manual / v2 / resume / system`），
  不同领域身份不跨命名空间比较唯一性。
- **手工/v2 无稳定请求 ID**：由入口适配器**首次接纳时分配一次身份**，后续重试复用同一身份（适配器职责，R5.2 接线实现）。
- `candidateId` = stableIdentity 的确定性派生（同元组同 ID）；**同 candidateId 不同执行载荷或排序键=身份冲突——
  冲突处理作用于整个同 ID 分组（整组拒绝、其余候选组继续处理，不保留先到项）**，拒绝留痕；
  **去重条件=同身份+同执行载荷+同排序键**（非仅同 ID）。
- 确定性承诺限定为「**相同已归一候选集合产生相同胜者**」；不声称无身份外部请求可跨重启自行重建。

### 2.2 排序键与层级（ASTRA B1 冻结——恢复上游裁决，不得漂移）

`tier`：**`system > fixed > plan`**（三值）。`flexible` 与 `chain` 是**来源类别**，比较器映射到**同一层级值 plan**——
灵活型「仅全局空闲时具备资格」的约束放在**资格判定**（EligibilitySnapshot），**不通过新增层级表达**。
反例锁定：灵活型 priority=-100 vs 普通链 priority=100 → **普通链胜**（同层按优先级）。

- `priority`：int32 大者优先，缺省 0（R5.4 落地 `schedule.priority` 策略）。
- `scheduledAt`：**计划时刻**；手工/v2 无计划时刻=null，排序时排最后，同到点组内以 stableIdentity 兜底。
- `tier=system` 仅由动作类型+既有调用方身份判定（A6/人齐/人工显式动作）；**来源本身不证明 system 授权**
  （v2 通道来的请求不因来源成为 system）；`v2` start 类操作默认 `plan/chain`（stop/resume 不是启动候选，按三分类分流）。

## 3. 排序纯函数合同（ArbitrationOrdering，无副作用可测）

**全序**：`tier desc → priority desc → scheduledAt asc（null 排后）→ stableIdentity asc（Ordinal）`。

- 先归一校验（§2.1：冲突拒绝、重复去重），再比较；`Compare` 只对已归一候选调用。
- `ArbitrationDecision Decide(candidates, eligibility, leaseState, f11State)`——**显式结果类型**（S1）：
  `NoEligibleCandidate / F11Blocked / TicketSuppressed / NeedReconcile / NeedPreemptConfirm / AllowRequestExecution`，
  拒绝原因与事实分层返回（原始回执词/业务结果/租约状态不混用）。
  - **Decision 载荷冻结**（S1 复核）：结果必须携带候选引用（胜者/被拒候选）、关联动作号（交接/提交）、结构化拒绝原因与压制来源（F11/票据/资格项/租约态）——日志与夹具按载荷断言，不只断言枚举值。 **各分支必填性冻结**：NoEligibleCandidate/F11Blocked——候选引用可空、压制来源/原因必填；TicketSuppressed——被压制候选引用+票据来源必填；NeedReconcile——关联事实引用必填；NeedPreemptConfirm/AllowRequestExecution——候选引用+关联动作号必填；**动作号=输入携带或确定性派生（同输入同号），纯函数内部不得生成随机身份**。
- 判定顺序：F11 闸门 → 票据压制（§5：压制**无关**候选，保留授权抢占方资格）→ 资格筛选（全用 EligibilitySnapshot）
  → 全序首元素。参选资格：已到点/窗口内且前置就绪；**顺序链内未就绪节点不参选**。
- 低优先级饥饿不设老化（R-6）；过期窗口候选按 missPolicy 处置（§2②6），不参与排序。

## 4. 安全交接状态机（ASTRA B3 冻结——转换表即合同）

```text
Idle → Evaluating → DirectStart（无在跑/无压制/有资格）
                  → PreemptRequested（向在跑方发取消或 A6 挂起请求）→ Confirming（等权威事实，有界超时）
Confirming → StartExecuting（§4.1 确认条件满足）
Confirming → Aborted（超时/关联不符/事实未知 → 不启动，本次触发按 missPolicy 留痕，原执行待对账）
StartExecuting → Submitting → Accepted（已受理待执行确认）→ Running（权威执行中，BGI 作业快照确认）→ Settling → Idle
DirectStart → StartExecuting（殊途同归统一提交准入；Accepted≠权威执行中——§4.2 受理≠执行，Running 是权威快照确认后的跟踪状态）
任意状态 + F11 → 独立停止路径（不进排序，状态保持）
```

### 4.1 转换判定表（每条必须可测）

| 事件 | 冻结判定 |
|---|---|
| 普通抢占确认 | **关联的被切执行已退出**（BGI 权威终态四词集合 cancelled/failed/succeeded/skipped 到达且身份+目标 epoch+动作关联匹配）才允许交接——**权威退出判定唯一定义点**（§8 引用本行，不另立集合）：skipped=权威退出语义（交接可放行），业务含义不推断，原始 skipped 不映射助手侧 skippedUser；该映射标注**待真实线路验证**。**终态只证明该执行退出，不自动证明租约/F11/票据/其他未决提交允许启动**；取消受理回执≠已退出（取消受理词为待验证合同，§8），受理只进 Confirming 等待 |
| A6 授权抢占 | 仍经过 `PreemptRequested→Confirming`；确认条件=**既有 A6 挂起/移交事实**（PreemptionGate/takeover ticket 语义），不套用取消重跑路径 |
| 抢占方终态 | 仅进入 `Settling`，**不直接解除票据压制** |
| settle 确认 | 明确进入**原票据恢复分支**，或经既有合同完成终结；**禁止「尚未处理恢复、无关候选已可启动」的空窗**——settle 未确认期间无关候选保持压制 |
| F11 / Stop / epoch 变化 | 停止状态与票据失效优先；**迟到的 succeeded 不撤销已生效停止**（B1 实施约束） |
| 超时 / 关联不符 / 事实未知 | 保持禁止新启动，原执行待对账；missPolicy 只处置本次触发，不得回 Idle 直接重提交 |

### 4.1a A6 settle/恢复/执行权移交转换（B3 复核冻结——与 §4.1 同等约束力）

| 权威事实或事件 | 冻结的后续状态与准入 |
|---|---|
| A6 挂起及移交已确认 | 仅授权抢占方进入提交准入 |
| 抢占方终态 | `SettlePending`——无关候选继续受压制 |
| 已选择原票据恢复，但恢复尚未确认 | `RestorePending`/`NeedReconcile`——继续压制；不得另建替代作业 |
| 原任务恢复执行已确认（权威快照出现） | 转入原任务的运行跟踪，**不能转为空闲** |
| 已确认不恢复且协议终结 | 同时确认无执行占用、无未决提交后，才允许空闲仲裁 |
| 恢复/终结结果未知，或遇 Stop/F11/epoch 变化 | 停止或待对账分支；票据失效本身不证明执行已退出 |

离开 `Settling` 的合法后继仅两种：「已确认不恢复且协议终结」→ `Idle`；「原任务恢复执行已确认」→ 原任务运行跟踪（**非 Idle，不经过 Idle**）。

### 4.2 提交结果三态（B3 复核冻结：受理/确定拒绝/结果未知）

- **受理**：`accepted/queued/adopted` 三词兼容（ed04355d，ext.task.start 已观测）=受理证据，**不等于正在执行**；
  执行状态另由 BGI 作业注册表权威快照确认（D6）。
- **确定拒绝**：既有拒绝词表白名单（capability_required/stale_epoch/request_expired 等七码，R4.10 IsPreSideEffectRejection）
  → Rejected，可证实未受理。
- **结果未知**（发送窗口崩溃/超时/result_unknown/无码等）→ **待对账状态**（Unknown 语义，禁止换键重跑、
  禁止回 Idle 重提交），按既有账本+job 查询对账（D11）。
- 继续后继节点≠恢复成功收尾权限（B1 实施约束）；叶子实际 succeeded 不撤销已生效 Stop/F11。

## 5. 恢复入口与票据（§2②7 落地 + ASTRA I2 冻结）

- **四类恢复分流**（R5 评审 §2②4）：暂停续行 / A6 票据恢复 / 确认取消后任务重跑 / Unknown 待对账——
  **仅 A6 类要求票据**；暂停续行与 Interrupted 恢复按 R4 既有合同，不被一概要求持 A6 票据。
- **票据权威在 BGI 侧**：三要素（被挂起运行+授权抢占方+epoch）由 **BGI 票据权威（PreemptionGate/SuspendedTaskContext）
  校验**；候选自带的 ticketBinding 只是关联提示，**不是授权证据**。
- **身份映射（类型核实后冻结）**：助手 `WorkflowRunRecord.WireRunId`（Guid 串）↔ BGI `SuspendedTaskContext.RootRunId`
  （Guid?）——类型相容；助手整数 `Attempt` ↔ BGI `SuspendedTaskContext.Attempt`（int?）——整数尝试号映射；
  BGI `AttemptId`（Guid?）为**独立 GUID 执行尝试身份**，其生成/持久化/重建规则属 BGI 侧既有合同，助手不与其直接映射
  （ASTRA 复核类型纠正）；映射经既有 ext 合同字段，不按名称猜测。
- **生命周期**：助手重启、BGI 未重启 → 原票据可能仍有效，**查询后按原协议处理**；BGI 重启 → 原现场丢失，
  **旧票据不得复活**（stale_ticket/stale_context 词表沿用 R2）；**票据有效期与租约 TTL 独立**（SuspendedTaskContext
  无到期字段，不认定共用到期规则）；`StopVersion` 与 `SuppressCompletionAction` 校验/传递保留（不只验三要素后恢复默认收尾）。
- settle/恢复/执行权移交的具体转换按 §4.1 表执行，联机打断/恢复语义验证归 R5.3。

## 6. 租约持久化（LogicalOwnerLease，ASTRA B4/B5/B6/I4 冻结）

### 6.1 存取形态与仲裁域

- 文件：`arbitration-lease.json`（RunStore 目录旁；RunStore 只枚举 `*.run.json`，不互读——B6 已核实）。
  文件自版本化 `"version": 1`；**单例=单 BGI scope**（v1 单目标）；多目标预留 scope 字段，启用时按 scope 分区。
- **仲裁域冻结**：同一配置根=一个仲裁域（助手实例既有单例约束）；**跨进程竞争经文件锁（FileStream 排他锁）
  作为共同权威串行入口**——`RunStore._gate` 只保同实例（B5 已核实），不用于跨进程排他。
- 获取/续期/释放均校验 `leaseId + ownerEpoch + expectedRevision`；**旧所有者不得续期/释放新所有者的租约**。
- **锁对象**：固定 `arbitration-lease.lock`（永不原子替换/删除——不把被替换的 JSON 数据文件当锁对象）；
  锁覆盖「读取当前状态→判定期限→校验身份及修订→更新→发布」全过程，竞争失败后必须重新读取。
- **四种代次分离**：`ownerEpoch`（助手进程纪元）/ BGI epoch（目标进程纪元）/ `generation`（所有权代次：首次获取=1，
  重新获取+1，续期/释放不变）/ `revision`（数据单调修订，每次写入+1）。
- **心跳字段与过期续期（澄清 1 冻结）**：所有者每次锁内写入（获取/续期/handoff 更新）递增 revision 并刷新 `heartbeatSeq`；**非所有者对账留痕只写 diag 段、不刷新 heartbeatSeq**；TTL 观察对象=`heartbeatSeq`+完整所有者身份（更替即重置计时）。**已过期租约不得续期复活**——只能重新获取（generation+1 进入新所有权代次）。

### 6.2 状态五态与语义分离（B4 核心）

`Absent / Valid / Expired / Corrupt / Unsupported`：

- **TTL 过期仅撤销逻辑所有者资格**——不代表执行锁释放、任务取消完成或票据失效。
  接管配置、租约有效性、执行占用、票据状态**分别判断**。
- `Corrupt`：保留文件并留痕，**不得降级按 Absent 处理**；`Unsupported`（更高 version）：响亮拒绝执行并留痕。
- **失联责任方冻结**：助手死亡时**没有本机组件负责取消 BGI 在跑任务**；安全保障=BGI 执行锁（物理无双跑）
  + **新所有者取得的是「对账资格」**——执行启动前必须先对账权威执行事实与票据状态（§4.1），
  事实不明→禁止启动。「失联取消不重叠」验收改述=「失联后新所有者先对账再启动，不重叠承认」；
  强杀助手场景由**存活于助手之外的测试驱动**完成（I3 复核）。
- **原子准入边界（B4 复核冻结）**：提交/交接**意图先在跨进程锁内持久化**（租约文件 handoff 段），再发送请求；
  **发送窗口三场景冻结（T1）**：

  | 暂停/崩溃位置 | 冻结保证 |
  |---|---|
  | 锁内最终准入/意图发布之前 | 恢复后重新校验：已过期或已换所有者 → 拒绝，不发布新意图 |
  | 意图已发布、发送结果未确定 | 新所有者继承未决事实；旧请求可能到达并被受理；冲突执行保持禁止 |
  | 请求已在途 | 按原提交身份对账，不假设接收端有代次拒绝能力 |

  **同一所有者的并发调用也不得覆盖未决意图**；意图消解必须基于关联的权威证据，查询未命中或超时不能单独作为消解依据。
  所有权更替**继承未决意图**（不因过期/释放/新 lease 清空）；已进入发送窗口的请求保守按待对账处理
  （一次查询未命中≠确定未发送）；新所有者在意图消解前不得发出冲突执行。
  承诺准确表述=「**阻止新的过期所有者提交，并对已进入发送窗口的请求保守对账**」——不做「到达 BGI 的旧代次请求
  一律被拒」的强承诺（那需要 BGI 准入端消费代次令牌，属协议范围变化，另立评审）。
- **过期即禁启**：即使 leaseId/generation 相等，已过期租约（TTL 失效）也不得启动——代次相等≠租约有效。
- F11 停止状态独立保持（§1）；租约释放不解除 F11。

### 6.3 时间与崩窗（I4）

- 心跳周期 5s、TTL 15s（设计值，可调；注入时钟保纯函数可测）。
- **本进程存活判断用单调时间**（Stopwatch）；**持久化 UTC** 仅用于记录与诊断（跨进程判断以 heartbeatSeq 观察+锁内复核为准）；系统时钟跳变不影响单调存活判定。
- 崩窗处置按件分开：正式文件（原子替换发布）/备份/临时残件各自验证——残件按无正式文件处理但留痕；
  **禁止通过旧备份或快照回滚复活旧所有者资格**（回滚后租约按 Expired/Absent 处理，须重新获取+对账）。
- **跨进程接管时间规则（B5/I4 复核冻结）**：以「**观察到 heartbeatSeq 持续不变达到 TTL**」的本地单调计时
  为接管依据，并在锁内复核；观察计时绑定完整所有者身份（leaseId+ownerEpoch+generation），更替后重置；观察者重启=重新等待一个 TTL（代价=恢复延迟一个 TTL，规则明确可测）；
  UTC 仅记录与诊断。单调钟跨进程不可比——旧进程自认存活与新进程判定过期的冲突，以本规则+锁内复核裁决。

### 6.4 交接上下文持久化（B6）

- HandoffContext **存于租约文件 handoff 段**（单文件承载租约+交接，避免两文件原子问题），至少含：
  被切方身份/授权抢占方/动作及提交身份/目标 epoch/恢复分支/未决阶段。
- **handoff 生命周期独立于租约有效期**：获取新租约只替换所有权部分、**保留未决 handoff**；释放不删除未决事实；
  正式文件缺失且存在残件 → 进入保守对账，**不得据此宣称没有未决动作**。
- **写入顺序合同**：动作发送前持久化意图 → 权威事实到达后更新状态；与 `*.run.json`/外部动作交叉不一致时
  取保守待对账，**禁止推导为空闲**。
- `WorkflowRunRecord` **本阶段不修改**：R5.1 新事实均可由既有 run 字段 + 租约文件 + BGI 权威状态**保守重建**
  （映射见 §7）；旧消费方不读租约文件=无执行含义；恢复限制=回滚仅到「已静止且恢复事实兼容」的状态（R5.6 I1 衔接）。

**旧版切换守卫冻结（T2）**：「旧版不满足静止前置不得执行」由**切换/启动控制面**落实，不依赖旧版自身判断（旧版不读 handoff 段）：
- 检查主体：R5.6 迁移/切换控制面（R5.1 交付其判定纯函数与夹具；端到端接线归 R5.6）；
- 检查内容：已静止（无在跑/无未决提交）、无未决 handoff、无存续恢复责任（票据/Unknown 待对账）；
- 检查期间持配置根级切换锁，阻止新写入、新提交及旧进程重新活动；
- 检查不通过 → 在切换/启动边界响亮拒绝并输出结构化原因（pending_handoff/pending_recovery/not_quiescent），不静默降级；
- 优先关系：上表「既有语义不变」三行仅适用于**旧版自身产生的运行事实的正常恢复**；接管 R5 新版产生且仍有恢复责任的运行 → 降级前置优先，守卫拒绝。
- **切换原子边界（四轮阻断一冻结）**：切换控制面**先封锁生产准入，再取得静止事实**；封锁持续至切换提交且目标版本接管完成、或安全回退完成——检查通过与切换生效之间不允许解封；
- **锁协同**：固定获取顺序=配置根级切换锁 → 租约锁（禁止反向）；运行时发布意图除持租约锁外，还须确认无生效中的切换封锁（切换闸门未激活）；
- 不认识切换锁的旧版：由控制面停止并确认退出、由控制面控制重新启动，不依靠旧版主动遵守新锁；
- 控制面在检查通过后崩溃：重启必须重新检查或恢复持久化闸门状态，**不得复用旧的通过结果**。

- **X1（记录语义）**：R5.1 §6 的逻辑所有者租约文件中，**`Handoff.Operations[]` 的结构定义引用 R5.2 §4.1**（不在此重复字段表）；适用记录语义含 R5.2 AMD-1-3（按操作类型的字段适用性与三态、恢复权威按事实类型）与 AMD-1-7（**准入事实与准入重试预算**独立于发送结果；`answeredSendSeq` 仍限「结果对应的发送轮次」）。**状态＝已登记**。
- **X2（版本语义）**：R5.1 §6.1 的**文件格式 `version`** 与 §6 的**修订 `revision`** 是**两个不同概念**——`version` 为格式版本（当前 1），`revision` 为文件级单调修订；**R5.2 AMD-1 不自动提升格式 `version`**（持久化内容增加须另行评估格式演进）。**状态＝已登记**。
- **X3（准入事实持久化）**：引用 R5.2 AMD-1-7 ⑨⑤——**准入裁决、准入重试计数与 `retryWindowDeadlineUtc`** 在租约权威串行边界内持久化；**准入重试计数与 `sendSeq` 分开**（本场景从未占位，`sendSeq` 保持 0）；**窗口截止时刻持久化后重启不得重置**。**状态＝已登记**。
- **X4（来源事实权威）**：引用 R5.2 AMD-1-5——**运行记录 `Handoffs` 是移交来源事实的权威载体**（追加式、旧绑定不替换、台账查询键＝`IntentKey`），与 **`Operations` 的授权/消费/发送绑定权威**相区分。**状态＝已登记**。

**完成证据**：本节即为 X1–X4 的逐项登记（章节锚点＝本 §11；责任方＝施工方；状态＝已登记；版本证据＝本节随 R5.2 AMD-1 同批提交）。**本节不宣称 R5.2 依赖组已生效**——生效状态以 R5.2 §13.8/§13.9 为准。
