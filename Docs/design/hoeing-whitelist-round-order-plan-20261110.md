# 联机锄地：按房间白名单顺序轮换世界（方案）

更新：2026-11-23 · v4（不加开关）· 已实施，验证范围见文末

## 1. 用户可见规则

- 多世界连续锄地直接使用房主的房间白名单，不加开关。白名单至少命中一名实际参与者时，按名单从左到右轮换，**首任房主也按名单排，不固定第一**。未到场条目跳过，不占轮次；到场但未命中的玩家排在命中者之后，按 UID 升序。
- 白名单留空、只有分隔符或无人命中时，由服务端沿用默认顺序：首任房主第一，其余按 UID 升序。非空名单无人命中时记警告。这是**服务端算出的默认顺序**，不等于客户端查询失败时自行排序。
- 先排序再取轮数上限。有开队预判时，仍只在原候选内过滤无可跑路线的世界，不递补计划外世界。例：房主 A，实际到场 A/B/C，名单 `B，D，A`，两轮候选为 B → A；D 未到场，C 排在候选之外。
- 现有白名单升级后会自动参与排序，不需重新保存；若仍希望房主先跑，可以把房主写在名单最前。入房、踢陌生人、单世界与单机逻辑不变。不兼容旧服务端或旧客户端，协调服务端与 BGI 同版发布，不扩大全局协议或版本校验的改造范围。

## 2. 实施范围

### 2.1 服务端统一生成顺序

- 继续由 `BgiCoordinatorServer/Services/RoundHostOrderDecisions.cs` 做排序。开队预判的 `WorldPlanState`（构造时复制 `HostConfig` 和参与者快照）与逐家执行路径的 `RoomOperations.Lifecycle.MarkRoomStartedAsync`（首次锁房生成 `Room.RoundHostOrder`）复用同一规则。用房主现有的 `HostConfig.RoomWhitelist`，不用轮换房间中补入参与者名字后的 `room.Whitelist`。本次顺序一旦确定，后续重传配置、名单编辑和换房均不重排。
- 只按半角/全角逗号 `,`、`，` 切条目，去首尾空白、忽略空项。**顿号 `、` 不是分隔符**，`Dream、渺茫` 作为一个完整玩家名。客户端现有入房与踢人拆名单的代码不动。
- 对房间玩家上报的 `PlayerName` 精确匹配（不区分大小写，不做 OCR 模糊匹配、不按 UID 匹配条目）。保留上一版审查讨论的括号备注匹配：条目与玩家名可拆主名、括号内备注参与匹配。一人多次命中取最早位置；多个人命中同一位置时按 UID 升序，每个 UID 只排一次。排序匹配不改变入房规则：仅命中备注不代表能通过服务端的精确入房校验。服务端独立构建，用相同的括号用例验证规则，不引用 BGI 项目。
- 保留现有已完成 UID 的裁剪和 `WorldPlanState` 的 `Take`／剩余世界顺序，不把“没拿到序列”当成已完成或无工作。保留房间历史依赖的 `[RoundOrder] ... 生成权威轮换序列` 日志格式；另记录采用的排序方式、未命中人数或默认回退原因。

### 2.2 客户端：有名单时必须确认服务端顺序

- `AutoHoeingTask.RunMultiWorldAsync`：有已确认的 `WorldPlan` 就使用其剩余 UID 序列；只有服务端确认 `NoWork` 才走无工作收尾。在当前分支，是否走开队预判不再由旧版的“续开重跑”开关决定，不新增也不恢复该开关。
- 逐家执行路径使用本场首任房主的同步配置判断有无有效白名单条目，不读成员自己的名单；配置未知不得视为名单为空。名单非空时，即使服务端最终算的是默认顺序，也必须拿到并校验服务端冻结的 UID 序列。名单已确认空时保留原空名单行为，不扩大本次改动。
- 用可取消的总时限重试获取顺序（计划上限 30 秒，包含请求时间，不是仅累计重试间隔）；房主锁房失败、参与者 UID 不足以确认身份、序列缺失或不可靠时，不回落到 `CurrentPlayerList`。记录原因，进入联机失败清理，并尽可能向当前房上报协同中止。单端超时不代表其他端也超时，不能仅靠延长重试或发送中止广播来保证全队一致。
- **首轮开始前确认到齐。** 在逐家路径且名单非空时，所有参与者确认同一房间、同一冻结序列后，才允许开锄或退出源房切世界。可复用同步设施，但预期人数必须取冻结参与者而不是掉线后的实时人数，且必须检查明确的成功结果。现有 `SyncRoundEndAsync(-1)` 会忽略不成功的等待结果，不能原样充当这个门禁。实施时针对“一端取序超时，另一端已取到”的场景验证不能有一端开跑、另一端退出。不得改变普通轮末同步的语义。
- 首个待执行世界不是首任房主时：已确认的开队计划复用 `AutoHoeingTask.WorldPlan.cs` 的目标房交接，直接进入目标玩家世界；逐家路径复用 `switchBeforeFirstRound`，先在首任房主游戏世界完成组队，确认后全员退组再转向目标。首项不是房主不等于原房主世界已完成，更新相应日志，不能因此写进度或报完工。

### 2.3 界面只改说明

`BetterGenshinImpact/View/Pages/View/MultiplayerHoeingSettingsView.xaml`：保留“房间白名单”标题、输入框和布局，不新增控件。在输入框下补充：

> 用逗号分隔名字。多世界锄地按名单从左到右轮换，房主也按所填位置排序。名单为空或未匹配到任何参与者时，房主先跑；留空不限制入房。

同时校正附近“按加入顺序轮换房主”的旧文案，并核对任务设置页及脚本设置说明。教程说明补充未匹配者排尾、轮数上限和旧名单自动生效。不新增 `AutoHoeingConfig`／`RoomConfig` 字段，不改 ViewModel 读写、配置组重置、单机清除及设置导入导出。

## 3. 审查结果与风险

| 已查链路 | 本版处理 |
|---|---|
| 房主配置与排序时机 | 房主上传已有 `RoomWhitelist` 早于首次开队计划或锁房。新流程用快照，逐家路径用首次锁房结果；确认开始前名单来源一致。晚加入、换房、掉线不能改变本场顺序或缩小确认人数。 |
| 轮换房主、参与者及进度 | `RequiredWorldParticipants` 是成员集合，不是轮换顺序；每轮房主按 UID 判定，发起房主仍负责本地进度。进度签名基于 UID 集合；改排序不改变签名，不重置旧进度。 |
| 停止、掉线、协调中止与守护 | 复用取消链、协调中止及有限重开，不吞掉取序或确认失败。继续用轮换窗口隔离旧房关房事件，但不能屏蔽真正的停止。首轮提前换房的正常与失败分支须验，静态检查不替代运行。 |
| 任务中心、助手、网页 | 排序同样适用于由任务中心发起的多世界房间，读取首任房主实际生效配置；不新增任务中心覆盖项。助手与网页不用新增排序逻辑，批次参与者判定保持按集合。 |
| 日志与版本 | 历史日志解析用 UID 集合，原格式保留。现有版本校验存在 alpha 通配，不当成防混用保障；本功能按 BGI 与服务端同版部署验证。不适配旧服务端的 v1 本地重算，不顺带删除旧逻辑。 |

## 4. 验证与验收

- **排序和入口**：纯排序测试覆盖空名单、无人命中、房主不在首位、未入房、未匹配成员、重复及歧义、括号备注和大小写、完成 UID 裁剪、`Dream、渺茫` 整名及两种逗号混用。服务端入口测试覆盖 `WorldPlan` 候选取前 N 后再过滤（不递补），以及逐家路径生成相同顺序。空名单和历史日志测试验证原行为未改。
- **客户端安全边界**：测试同一冻结顺序才放行；一端查询失败、名单配置未知、缺 UID、确认超时或手动取消时不允许只凭本地列表进入首轮，也不能标完成。覆盖首项是或不是发起房主；确认失败不能因人数实时下降被误放行。
- **实际入口**：分别验证有开队计划和逐家执行时，名单首项为非房主的两世界轮换；逐家路径额外核对首轮切换时的停止、退组和后续重启。以所有参与者实际进入同一个首轮目标、未额外跑原房主世界、失败不误报完成为验收依据；游戏内未验证如实标注，不作已通过结论。

## 5. 实施记录

- 服务端统一排序，逐家路径在首次锁房时冻结房间实例、名册、轮数与 UID 顺序。客户端查序最多 30 秒；确认阶段按服务端共享截止时间得到结果。成员离房、过期清退或房间中止不会缩小确认名册。首轮转世界时，如果无法确认已退出源世界，不尝试开跑。
