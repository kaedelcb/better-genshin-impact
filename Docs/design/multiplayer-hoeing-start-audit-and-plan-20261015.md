## 结论

当前两种入口没有共用完整的开始身份和生命周期。上线锄地走全队协调批次；一键锄地走各端独立的配置组循环。再加上准备阶段未完整占有执行权、suspend 只验证进程而不锁定被接管的执行根、服务端拒绝新轮前先中止旧轮，源码存在“新开始没成功，正在跑的锄地也被打断”的可达路径。

因此应把两入口的开始阶段作为一项完整能力整改：统一批次受理与所有权、先完成全员准备、准确接管旧执行根、保护已在执行的锄地、首线前严格验证队伍与路线，并统一失败与取消收口。继续单独修改报错分类、增加重试或延长等待，不足以解决这些相互竞争的路径。

## 当前完整流程

### 上线锄地

1. BGI 上线信号、助手定时或手动上线产生 generation。助手进入 Armed 并报告服务端。BGI 的 NotifyOnlineTask 立即返回，generation 是通知边沿，不等于完整锄地批次身份。
2. 服务端根据上线成员和预期人数选择参与 UID，校验绑定结构，建立 CoordinatedBatchState。单人直接 AllReady；多人先发 AllReadyConfirm，等待接收确认。
3. 成员收到确认请求后，先 ACK，立即开始本机准备；ACK 不代表此成员已经接受执行或准备完成。
4. 助手建立 `_activeBatch`，检查绑定、旧任务中心接管，采样当前执行根，然后 suspend 和等待旧根退出。直到这些动作完成才向服务端登记本端 token。
5. 全员登记才允许业务项运行。助手按请求键查询/提交 JobId，持有 BGI epoch；丢回执时原键补查，不盲目重新提交。
6. BGI 执行配置组或一条龙，进入 AutoHoeingTask：配置和资源准备、连协调服务器、建房/入房、加入游戏世界、全员就绪、路线同步和校验，最后起跑首条线路。
7. 全员当前项成功才推进下一项；明确失败由全队统一清理后至多恢复一次；Unknown/用户取消中止。完整成功后执行上线结束策略；失败清理票据及自己拥有的 JobId。

导航：OnlineIntentLifecycle.cs:151/263，RoomOperations.ControlRoom.cs:358，MainViewModel.OnlineBatch.cs:24/162/288/378，MainViewModel.CoordinatedBatch.cs:58/153/181，CoordinatedBatchState.cs:74。

### 一键锄地

1. 发送端向所选成员发送普通远程命令 `start_group + key=一键锄地`，带原始 CommandId 和两分钟接收期限。
2. 接收端直接遍历自己的 OnlineHoeingGroupNames，每项新造 `start_group`。不建立 OnlineHoeingBatch、不进入上线生命周期、不登记全队协调批次，也不读取条目类型。
3. 空闲时经普通 ext 队列执行；忙时经按键冲突策略 suspend、等退出、v2 task.start，执行完按固定停止策略处理。
4. 每台成员独立推进。只在 cancelled 时退出循环；failed 仍执行下一项，最后打印执行完毕。该专用分支提前 return，绕过正常远程命令回执。
5. 底层进入同一个 AutoHoeingTask，但缺少上线批次的 coordinatedHoeing 上下文和统一失败恢复合同。

导航：MainViewModel.cs:5234–5264、6889，CommandExecutor.cs:934/1361。两种入口共享部分配置和执行方法，并未共享一轮任务的所有权。

## 当前必须一起修的缺口

### 1 正常开始请求会中止正在执行的旧批次

RoomOperations.Batch.cs:26–37 先 `old.Abort("superseded")`，再以 previous_batch_active 拒绝新轮。新的 AllReadyAbort 因 generation 不同会被旧客户端忽略；真正的停止发生在旧客户端轮询到自身批次 aborted 后，finally 取消它拥有的 JobId（CoordinatedBatch.cs:78/183）。结果是新轮未启动，旧轮也被中止。

触发入口真实存在：RaiseLocalIntent 可产生新意图；ApplyEdge 在超过 60 秒防抖后能把 Executing 改成 Armed（OnlineIntentLifecycle.cs:209–223）。该分支必须改成无副作用拒绝新开始；明确的重开/停止应走独立、有身份的控制流程。

此行为还被测试写成预期：CoordinatedBatchGatewayTests.cs:118 直接断言旧轮为 aborted。本次该测试通过，证明当前测试保护了需要纠正的产品语义，不能以绿测表示不会打断。

### 2 两入口没有完整生命周期互斥

一键没有 `_activeBatch`。上线创建该对象后，RunTask 要到准备结束才赋值；OnlineHoeingBatch.IsAlive 只认 RunTask 未完成。普通任务没有任务中心 handoff 时，准备中的批次也可能被 busy 判断漏掉（OnlineBatch.cs:205/378，OnlineHoeingBatch.cs:27，MainViewModel.cs:5967）。两个异步入口可以在判定、挂起、提交之间穿插。

必须从接受开始意图起就持有明确的 Preparing 状态，覆盖准备、接管、运行、组间等待、停止和清理。不能仅把局部 suspend 调用串行化。

### 3 抢占只绑定进程，没有绑定准确的旧执行根

助手虽然捕获旧根，但 suspend 只发送 takeoverTicket 和 epoch（CommandExecutor.cs:1939），BGI 挂起到达时任意 `_active`（InstanceRequestHandler.cs:1636–1647，ExecutionScope.cs:305）。一键先在空闲状态启动后，迟到的首次 AllReady 接管能把这颗新锄地根取消；旧根在采样后被替换时也会误中继任根。

同票据重复 suspend 已经不会二次保存/取消，但可能等待正在正常运行的继任锄地根直到超时。票据幂等不等于业务开始幂等。

修复必须在 BGI 接管提交点原子核对 epoch、executionInstanceId、stateRevision，并把恢复现场、停止和释放绑定到同一 batch/attempt。目标变了就无副作用拒绝或对账；不能靠组名相同猜测同一次执行。

### 4 先中断原任务，再发现全队准备失败

当前外层先 suspend/settle，内层才登记。所谓“先登记再准备”只覆盖内层冷启动，没有覆盖外层接管。ACK 也早于本机接受执行，生命周期拒绝、配置错误、旧接管或 IPC 问题没有及时作为成员准备失败报告给全队。

08:24 是可见后果：本端原上线组已让位，等待三分钟才知道有人没登记。应先完成成员登记和非破坏性准备，再由服务端授予接管步骤；错误立即注明成员与阶段。发生接管后的失败必须按原票据清理，对无法证明的原计划状态保留责任。

### 5 一键丢失请求身份、类型及失败结果

MainViewModel.cs:5247 新造子命令丢弃原 CommandId、ExpiresAtUtc、来源身份等字段，generation 为 0；绑定为 onedragon 的条目仍被当 group。failed 继续推进且没有正常回执。上线分支也存在名称先复制、异步后再读类型的快照不一致（OnlineBatch.cs:209；CoordinatedBatch.cs:13）。

应删除一键独立循环，使用统一批次的冻结条目、类型分发、请求键、全队推进和回执。命令接收期限只限制受理；已正式接受的长批次不应因为原命令两分钟过期而在第二项被取消。

### 6 游戏内首线准入存在超时继续和失败正常返回

这些是当前源码可达问题，本次两次成功起步日志没有重现这些失败分支：

- 房主等 AllWorldJoined 得到 false 时只写超时继续，后续仍置 `_multiplayerPartyReady=true`（AutoHoeingTask.cs:1439–1446/1738）。后面的组队守卫无法再阻止假就绪。
- 路线同步丢弃 WaitForAllPlayers 的 bool 结果，随即写所有玩家同步完成；超时分支继续（3640–3646）。false 可以表示断线、超时、取消或关房，不能算成功。
- 房主路线等待超时、路线校验重试失败或 schema 校验失败有只记录后 return 的分支（3531、3681、3784）。计划路线计数在3856才累加；早退可能尚无失败标记和未执行计数。外层会把普通 return 当作世界完成（2332–2337）；CoordinatedHoeingOutcome 不能可靠区分初始化失败与合法无路线。
- 共同重跑登记遭拒后可先降级继续，批次严格检查却在核心函数返回后才发生（3874–3883、3263–3265）。对于需要固定全员合同的协调批次，应在首线之前决定能否执行。

修复采用明确的开始结果：Ready、明确无可跑路线、Failed、Cancelled。失败/未知不能写就绪、成功或世界完成；合法的全 CD 空路线由全队同一权威计划确认后正常跳过。DebugMode 可以保留诊断用途，但不能绕开正式多人任务必需的成员就绪、身份及资源合同。

### 7 取消收口与显示不能制造新的假故障

09:50 BGI 已按 F12 主动停止活动根、撤销票据并清理上下文；助手随后旧票据被拒，可以是正常撤销结果，不能直接说执行权残留（HotKeyPageViewModel.cs:410，CancellationContext.cs:138）。应按同 epoch、票据及原根的事实区分已撤销、仍占用和未知；保持票据校验，不放行陈旧请求。

同一链内修正 F11 硬编码、重复日志出口、取消后执行完毕文案和回执缺失。08:43 的周期上报 CTS 已释放异常有实际记录，但这次随后成功起步；应结束并等待上报任务再释放 CTS，不把它错误认作登记超时根因。

## 建议实施方案

作为一个完整的开始阶段修复交付，覆盖助手、BGI、服务端及对应UI状态。保留两入口的触发方式、成员选择、结束策略差异，共用下述执行流程。

1. **统一受理与批次身份。** 服务端分配稳定 BatchId，冻结参与成员、来源请求/意图、条目名称/类型/顺序、必要配置版本及结束策略。所有入口从受理起共用 Preparing/Running/Stopping/Cleaning 生命周期；按 batch/item/attempt 派生稳定请求键。
2. **保护已经在跑的锄地。** 同一次开始的重投返回已有状态；另一次普通开始遇已有锄地则明确返回正在执行，不改变旧批次。确需重开使用明确重开操作，先确认旧批停止，再启动后继批。旧版无批次身份的在跑锄地不能凭名称强行接管或冒认同批；先明确报告忙。合法后续轮次仍可在前轮结清后正常开始，不采用每天一次或固定秒数去重。
3. **先全员准备，后准确接管。** 收齐接收与准备结果：绑定可用、版本/能力一致、BGI启动和可信状态就绪。未齐时展示具体成员与原因，其他端不先停正常任务。上线信号和原计划要有明确等待/交接边界，避免信号组先继续开同一锄地又被批次重开。准备齐后，按准确旧根身份执行接管、保存原计划续接点并确认退出。
4. **统一提交与首线准入。** 每端只提交一次同身份业务项；丢回执补查原键。游戏内经历房间加入、进入世界、全员就绪、路线/变体合同确认后才报告已起跑。任何必需阶段失败立即返回可归因结果，不继续到首线，不假完成世界。
5. **统一失败、取消与恢复。** 全员同项成功才推进下一项。明确可恢复失败沿用一次全队恢复；未知先对账，不能盲重发。人工停止优先撤销整批及等待中的启动；清理只处理该批拥有的根/JobId/票据。旧回调不能释放后继批执行权。成功、失败、取消、已撤销、待确认分别显示并回执。
6. **成套升级。** 助手、BGI和服务端共同发布需要的能力；能力不足在准备阶段明确拒绝，保留已有任务。不能只更新助手后就宣称此方案已生效。合并重复日志出口，记录入口、batch、item/attempt、请求身份、目标epoch/原根/新JobId、阶段和停止原因；票据只留摘要。

建议先落实统一身份与无副作用拒绝，再把一键接入现有协调执行器、补目标化suspend和准备协议，最后收紧首线结果传播与UI。它们是同一交付内的实现顺序，不是分别宣布几个局部补丁已解决开锄问题。
