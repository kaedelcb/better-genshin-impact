# 槲寄生审查流程

2026-10-08 按用户要求精简。当前产品工作采用[交付流程](../../_workflow/usable-delivery-20261003/DELIVERY-FIRST-POLICY.md)；旧 v3 每代码批次双审、全历史归零、固定认证/突变矩阵不再是默认施工工序。

## 什么时候需要独立意见

- 用户明确要求或当前稳定版本需要综合实现复核时，组织一个完整范围；不因每个小功能、文件或子 Agent 任务另开审核。
- 关键业务行为尚未确定或复杂方案会影响真实数据/执行责任时，先定向澄清或集中方案评估；已明确的其他功能持续推进。常规有界修复不默认先方案审查。
- 原在途请求、授权模型/强度和有限次数保持原身份，失败/超时按原授权计数。不默认无限授权，不从旧文件获得新的次数，不自动追加复核。

## 怎么审

提供当前需求/完成判据、版本和相关未提交差异、入口/影响链、当前证据和真正关联的原问题。历史可以引用原件及 ID，不每次重写全部发现/unknown。

独立审查者按需追查相关调用方、被调用方、配置、恢复和依赖，不把导航当白名单，也不一次读完全部源码或认证所有 SDK。真实 User、凭据与无关私密文件不属于读取域。

报告区分本版功能/现实安全阻断、普通 BUG 后修、范围外历史和影响判断的未知；给出根因、可达后果、精确修复及最小有效验证。保留旧报告、原等级和未验证事实，不能用自写代码或新的分类伪关问题。

修复针对当前根因，验证与实际影响相称。反向突变或全矩阵只在关键判断确实缺证据时采用，不要求每个夹具/断言都做。修复后需要独立判断的部分集中复查，不重新启动整套前后审。

## 来源和接收

- 保存真正独立 Agent/CLI 的原始报告及可用版本/来源，不由主执行者自审冒充独立审查，不合成 receipt 或改原报告。
- 核相关源码和运行条件是否等价：无关变化记录理由，有关变化只补受影响部分。报告 pass、测试通过和产品实际验收分别判断。
- 现有 native_review/review_process 等工具仅在本次选择其协议时使用；严格格式、哈希、认证、checkpoint 是该工具的协议，不是所有产品工作必须先完成的任务。
- 工具无法表达当前授权或取舍时，保留原拒绝和旧请求，使用适用的可复核原始来源并说明局限，不改 owner_policy、重置账本或改旧 bundle 求绿。

## 模型和结束条件

槲寄生模型仍使用 gpt-6.1-sol，默认 medium；复杂或有现实高风险时 high，当前用户指定值优先。决定开始一次审查时才说明范围、问题和预期结束条件，不默认新增八维表单。

达到当前约定判据后回到版本交付；无现实关联的历史问题原级延期，不追求全历史零 open。未解决的本版功能不可用、误执行、数据损坏或停止失效风险仍阻断相应交付。
