## 初审结论

**当前版本不满足用户本次明确的易用性与产品关系要求，需要修正后再作本轮一次最终复核。** 主要问题不是少了说明文字，而是界面对象与用户要操作的对象不一致；部分添加操作还存在上下文默默重置的实际行为风险。

### R1 / P1：车道并非独立任务，用户被迫维护两个配对对象

- 原 `BasicTaskCenterView.Composition.cs:22` 起的 `AddLanesClick` 在没有出口时调用 `ShowFlowEditor(..., requireExit:true)`；应用后 `:77` 另外建立配对车道。车道“编辑”又只打开三项命名窗口（`:125`）。
- `WorkflowComposition.cs:33–49` 要求车道绑定一个独立的出口流程且必须紧邻；`WorkflowCompositionEditVm.cs:9–15` 的主表投影同时显示流程和车道两行。
- 后果：点击添加车道却进入“流程名称／出口判断”界面；完成后主表多出两个对象。修改进入条件必须找另一个流程行，车道自身编辑只能改名。用户看到的是实现中的图边关系，而不是“这一项选择走哪条路”。
- 必须修正：新车道自身拥有判断/选择步骤，创建和编辑车道都在同一个车道配置中完成。主表只出现一行车道，展示条件、两路任务和汇流。既有成对数据可以保留兼容，但不能要求用户继续管理同胞流程或丢失其配置。

### R2 / P1：全局“插入到”不仅抽象，添加后会悄悄回到流程顶层

- `TaskFlowEditorWindow.cs:111` 使用全局“插入到”，值为“主链／当前触发器·触发时执行／每次目标任务尝试前”等内部术语。
- `:207` 在每次选择节点时重建列表并把 `SelectedIndex` 设为 0；`:247` 附近添加节点后会刷新树并选择新节点，从而重新回到“主链”。
- 可达后果：用户先选择“日志触发时执行”并加入一个动作，紧接着再点第二个动作；第二个会被加到流程顶层，除非重新操作这个全局下拉。设置寄存器等动作因此可能在错误的时间执行，而不只是“看不懂”。
- 必须修正：在哪一组点击添加，就持续在该组添加。使用就地按钮，例如“日志出现后做什么 → ＋添加动作”“每次目标任务开始前 → ＋添加动作”“满足时执行／否则执行”。当前目标必须可见，不让一般用户管理“链／出口／插入位置”。

### R3 / P2：任务列表不足以解释将发生什么

- 原 `TaskFlowEditorWindow.Label` 只取自定义名或类型名；树节点通常只有“日志触发器／设置寄存器／星期判断”。
- `CompositionPlanRow.cs:76–87` 仅给日志额外显示关键字；车道显示“每轮只走一条车道”和“是／否＋名称”，没有显示根据哪个条件选择。折叠行的 `CompositionSummary` 主要在 tooltip 中（`:64`）。
- 后果：多个同类型节点无法区分，使用者不打开参数就不能核对 R1 写什么、监听哪项任务、为什么会进入 B/C。默认车道名“是／否”还会生成“是→是／否→否”的重复表达。
- 必须修正：步骤给出编号和关键参数；空配置明确标“尚未设置”。车道在折叠或展开标题上给出一句可读规则，例如“R1 等于 1 时走 B 线，否则走 C 线”，并明确每次只走一路、结束后继续下一项。

### R4 / P2：控件状态与整体主题不一致，禁用状态不可辨

- `CompositionPlanRow.cs:55` 创建普通 WPF Button，仅设颜色而没有完整 ControlTemplate；`:109–110` 的首项上移、末项下移置为禁用。用户截图已显示它们变为白底淡色箭头。
- `MistletoePage.xaml:1588–1593` 的来源筛选没有使用相邻控件使用的 `GoldComboBox/GoldComboItem`，用户截图显示了系统白底样式。
- 流程编辑器的自制 TreeView 展开 ToggleButton、参数滚动条，以及打开后的 ComboBox 项需要一同核对；只给关闭状态设紫金颜色不能证明打开/悬停/键盘焦点/禁用状态一致。
- 必须修正：复用共享紫金控件主题或补齐完整模板。禁用仅降低可用性提示，仍保留深色底与可读轮廓；所有选择器应包括 popup 和 item 状态。箭头有清楚的操作提示及可访问名称，不能仅靠一个字形判断。

### R5 / P2：重要任务配置被固定布局挤到滚动区底部

- `TaskFlowEditorWindow.cs:83` 固定参数区为 200 DIP；触发器参数和初始化/命中后操作入口的说明在同一区域较后位置（`:406–428`）。用户第一张截图已出现说明被下方边界遮住、系统滚动条突出。
- 后果：大片空白树区域与拥挤参数区同时存在，最需要解释的监听范围与后续操作不在阅读顺序中。
- 必须修正：按任务组织参数与就地动作入口，给参数区足够空间，窗口缩放时可滚动且底部保存/取消稳定可见。不得通过缩小字号解决；验证常用窗口、系统缩放和展开下拉后的可读性。

### R6 / P2：此前测试证明了实现路径，不等于证明用户能理解

- `WorkflowLaneEntryUiTests` 通过测试代码主动添加星期判断并点击“设为出口判断”，且断言独立流程与车道各一项。这准确验证了旧实现，却把本次被用户否定的产品关系固化成“通过”。
- `WorkflowCompositionUiTests` 通过代码选择“主链”下拉的索引再添加动作，只添加一项 callback，没有检查连续添加是否仍落在同一触发组。
- `UnifiedTriggerUiTests` 校验了计数、卡片高度与主题中的 GoldText/Dim 资源，却未实际展开来源 ComboBox，因而无法抓到系统白底来源框；车道测试也未验证禁用箭头实际渲染。
- 必须修正：保留旧执行/数据兼容证据，但新增按用户目标走完整操作的入口测试。检查新车道只有一行且进入条件能直接编辑、日志回调连续添加、折叠摘要含条件、打开的选择器、首末项禁用按钮。最终需要看真实渲染图，不能只找文本或检查资源存在。

## 本轮最终复核的结束判据

1. 新建与编辑车道都直接操作车道自身的条件；主表没有新增独立的配对流程。旧数据加载、编辑、复制/移序/删除与执行路线仍保持准确。
2. 普通流程可以通过步骤或局部组中的添加操作配置条件与触发动作；界面不出现“插入到／主链／设为出口判断”作为必学操作；连续添加不会丢失目标上下文。
3. 车道与流程摘要能让使用者核对关键条件和动作。两路都看得见，执行依然互斥并只汇流一次；未知或停止仍不能被当作否。
4. 用户三张图指出的系统白底/禁用按钮样式，以及同区域的打开、悬停、焦点和滚动状态，使用同一主题。常用窗口和缩放下参数及保存按钮可读。
5. 根代理提供修改后的真实 WPF 图、相关入口和执行测试结果后，本代理只对本次受影响范围再独立复核一次，原发现不改写为从未发生。未收到证据前，不写“最终通过”。

#### 当前判断及边界
