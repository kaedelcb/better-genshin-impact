# 自动本地提交节点

政策 ID：`auto-local-checkpoint-commit-20261004-v1`。
来源：owner 在 2026-10-04 本聊天纠正“完成修复和验证却长期不提交”，要求说明后续自动提交流程。适用于已获授权的开发、修复、集成及文档维护；只读讨论、审阅和材料外工作不据此获得写入授权。

## 默认动作与节点

在已有任务授权范围内，执行者主动完成本地 Git 提交，不等待 owner 再说“提交”。提交保存真实工程进度，与独立审查、生产开门、发布及最终 Goal 完成分别判断。

1. **聚焦修复批验证完成后**：完成影响相称的构建/定向回归，恢复所有临时突变，核对实际源码与验证版本，然后提交该批及必要配套依赖。共享不变量、协议或跨端依赖可以合为一笔，不按单文件碎片化提交，也不把“等整包验收”当作拖延阶段提交的理由。
2. **后审修复完成回归后**：成批处置原级发现，取得该修复的实际回归并恢复源码后，提交修复检查点。提交不自行关闭 MUST/重要项；正式闭合仍依原工序和独立证据。
3. **正式收口节点**：按原规定取得完整审查、认证及实际验收等证据，完成最终提交与交付/账本回填。早先阶段提交不替代这些条件，不将旧测试/收据改绑为当前认证。
4. **必要施工交接前**：完成安全操作后核对本聊天尚未提交的成果；归属与范围明确的成果应先提交可复核检查点，再记录最新 HEAD/工作区、保存交接、暂停自身 Goal 并核对接班。未达到最终验收的检查点如实写“候选／未审／未验收”；确需保全尚未验证或存在失败的进度时，可明确写 WIP、具体失败和剩余责任，不能伪记通过。

时间、工具数、回复轮次不构成提交触发器。编译/测试/源码写入、突变或恢复仍在进行时不提交中间变体，也不启动接班写者。

## 提交前后责任

- 动态核对分支、HEAD、已暂存/未暂存/未跟踪文件、写者、依赖、最新源码与证据；只提交已核实的任务范围。对继承前序会话的同文件增量，明确其来源与纳入理由，不称全是本聊天修改。
- 用明确文件列表执行 `git commit --only -m <message> -- <files>`；多行说明可使用 `--file`，仍必须 `--only` 和明确路径。新增文件先按明确路径登记，禁止整库或整目录批量暂存。其他人的已暂存内容和材料外成果须保留，不能顺带提交或清理。
- 若归属/依赖不明、同范围写者在途、文件身份漂移、工作区/提交钩子异常等使该组无法安全提交，记录具体原因、已保存位置及首次可提交动作，并继续其他可安全处理的任务。不能仅以“总 Goal 未完成”“尚未正式后审”“有已知旧失败”作为通用不提交理由。
- 提交说明分开记录已实现行为、验证范围、具体失败、未审/未验收状态及原级未决项。提交不是 pass/receipt，不释放原责任或开放生产门。
- 提交后原生读回 commit、实际文件范围、工作区及暂存区，核对与预定范围一致，并更新当前交接入口的最新 HEAD；原 opening、历史现场和旧收据保留原身份，不倒改历史。
- 默认只自动本地提交。push、合并、标签/正式发布、部署及生产运行仍依相应任务授权与质量门，不由本规则代替。

## 接入及边界

全局 AGENTS 第4.1节、项目 AGENTS 与交付优先政策导航本规则。槲寄生使用既有完整审查工序和同一原包，不拆包重置预算；源码稳定并准备最终认证/冻结时，先协调上述提交节点与快照身份。已有冻结请求正在读取或回收时，不造成它的 Git/源码身份漂移；待该安全操作终态后提交，并为后续阶段建立真实新快照，不重写旧身份。

本规则是执行者在任务中的默认动作，不是后台自动提交程序。没有新增 hooks、定时器、心跳、工具平台或会诊门。已运行执行者在自然边界显式读取后采用，不自动给其他聊天发消息，不因本次规则维护恢复产品 Goal 或创建施工接班。AGENTS/.agents 为本地持久入口且当前被 Git 忽略；新克隆或机器须核对入口，仓库中的本政策提供可追溯正文。
