# 槲寄生计划：接力手册（2026-09-24）

> 目的：把"这个计划怎么继续到验收完成"写清楚，并记录**自动跨任务接力当前损坏**的证据、判定标准与三种可行接力方式。

## 1. 当前故障（自动跨任务接力）

- 现象：用应用工具新建任务（`create_thread`）或同目录 fork（`fork_thread`）后，**该新任务的任何回合都跑不起来**，首轮即失败：
  `unexpected status 422 Unprocessable Entity: Failed to deserialize the JSON body into the target type: input: missing field 'call_id' ... url: https://api.deepseek.com/v1/responses`
- 实测次数：**4 次独立探针**（1 次完整交接提示词、1 次最小指令重试、1 次同目录 fork、1 次最小"只回复可以"探针），全部同错；失败回合里唯一的新增项是应用注入的 `create_thread` 工具回执（`functionCallOutput`，无匹配 `call_id`）。
- 根因判断（依据上述证据）：**新建任务的首轮请求体里被注入一条缺少 `call_id` 的工具回执**，而当前模型通道（配置里的自定义 provider → `api.deepseek.com/v1/responses`）对 Responses 结构做严格反序列化，直接拒绝整条请求。与提示词内容、长度、交接材料无关；本仓库代码无法修复（属应用／模型通道层面）。
- 影响范围：**只影响"跨任务自动接力"**；不影响当前任务内的推进（见方式 A）。

## 2. 三种接力方式（都能把计划推进到结束）

### 方式 A：同任务内接力（当前默认，用户零操作）

应用的目标（Goal）机制在**当前任务内**自动续跑：每当我完成一个批次并把目标标为完成，随后为新批次建立新目标，应用会继续把下一批推给我，**不需要用户输入"继续"**。

- 适用：现在（接力工具损坏期间）。批次 1–6 就是这样完成的。
- 代价：上下文持续增长，由应用自动压缩处理；不会丢提交（每批都有提交号与台账）。
- 你需要做的：无。

### 方式 B：手动新任务接力（每个批次一次粘贴）

1. 在应用里点"新建任务"，选择已保存项目 `better-genshin-impact-LCB`（**本地目录，不要 worktree**）。
2. 打开并**整段粘贴**提示词文件：
   `C:\Users\Administrator\.codex\task-relays\mistletoe\next-batch-prompt.md`
   （该文件在每批收尾时被覆盖更新，始终指向"下一批该做什么"。）
3. 判定标准：新任务首轮能正常回话（不是那条 422）即说明这条路可用；它会先读交接材料、做只读审计、再按批次施工。

### 方式 C：修根因后恢复自动接力（可选）

按顺序试，每步后用"新建一个只写『回复：ok』的任务"判定是否修好：

1. 重启 Codex 桌面应用（重新加载会话/工具状态）；
2. 若应用允许选择非 DeepSeek 通道的默认模型（模型目录里若存在），把默认模型切过去再试；
3. 更新/回退桌面应用版本（Windows Store 分发，更新由 Store 触发）。

修好后告诉我，我会再做一次探针；通过后即可恢复 `create_thread` 自动接力（交接规则仍按 [串行任务接续规则](mistletoe-session-relay-2026-09-24.md)：offer → created → ack → taken 单写者顺序）。

## 3. 每个批次的固定工序（三种方式一致）

审计（带代码位置）→ 反例先行（可复现的红）→ 实现 → 定向回归 + 完整回归（失败用例**身份**与基线比对）→ 既定 GPT 会诊（常规＝配置默认 `gpt-6-sol`／medium；最难或安全敏感＝`gpt-6-astra`／medium）→ 处置必改 → 文档与声明面同步 → 按文件提交（`git commit --only`）→ 写批次交接摘要与下一批提示词。
