# 四人精英锄地第三轮重跑后中止、漏第四轮的分析与修复方案

> 日期：2026-09-17。性质：事故审查、修复合同和实施验收记录。第 1–10 节保留事故分析与方案；第 11 节记录本轮已实施结果。
> 范围：全员使用同一新版 BGI、助手及服务端；不新增旧版本兼容分支。
> 用户授权复核后执行，本轮已修改 BGI、助手和服务端并完成针对性编译与自动化测试；未部署，未进行四机游戏实测；复核和测试通过后按用户要求提交。

## 1. 结论

本事故由两个层次的问题叠加造成：

1. **触发点：共同重跑收尾缺少全员完成屏障。** 线路已跑完、本机已回神像，并不代表全员收尾完成。旧客户端提交本机 Finish 后立即返回，上层发现会话仍未 Completed，抛出“共同重跑未完成确认，禁止记录本世界完成”，打断第三轮，第四轮没有执行机会。这处已在 `94da0cb8` 修复。
2. **扩大后果：联机任务异常结果和批次推进未形成全队一致的闭环。** 锄地入口捕获异常后正常返回；守护是否重开由各端本地状态决定。没有重开的端结束精英配置组，助手继续下发小怪。即使将失败正确上报，助手当前一般失败后仍继续下一组，因此不能仅靠补一个 throw 解决。

仅有 `94da0cb8` 时，修复覆盖本事故的收尾触发点，未覆盖异常结果与助手批次分叉。本轮新增三端一致推进及有界恢复，覆盖该缺口；实机端到端结论仍须按第 11 节验收。

建议最终行为：**同一联机批次只接受一份全队决策：继续当前组、共同恢复当前组，或共同终止批次。任何成员不能仅凭本地任务结束进入下一组。**

## 4. 代码因果链

### 4.1 重跑已经完成，为何仍报异常

- `CooperativeRerunSession.FinishAsync` 旧实现只发送 Finish。
- 服务端 `RerunExecutionState` 只有收齐固定全员 Finish 才转 Completed；先提交者的响应仍是 Finishing。
- `RunCooperativeRerunAsync` 随即打印重跑线路统计并返回。
- `ProcessRoutesByGroup` 校验会话必须 Completed，否则抛异常。
- `RunMultiWorldAsync` 的当轮调用因此中断，无法到达后续正常换世界流程。

该校验应保留。删除校验会把“未全员完成”伪装成成功，造成更隐蔽的提前关房或漏轮。正确修复是等待服务器权威 Completed，这已包含在 `94da0cb8`。

### 4.2 为什么没有继续第四轮，而是结束整个精英任务

`ProcessRoutesByGroup` 异常分支设置 `_sessionTerminated`、停止原因并中止会话，然后向上抛出。`AutoHoeingTask.Start` 捕获异常、记录日志、清理联机。异常不是“结束当前路线后继续下一轮”的控制信号，不能在未知完成状态下直接忽略。

当轮完成记录位于 `RunSingleWorldCoreAsync` 正常返回之后。因此本次异常路径不会在这里正常登记第三轮房主完成，更不会证明第四轮完成。后续恢复应按实际完成记录和 CD 重算，不能盲目跳到第四轮。

### 4.3 为什么有的端不重开，有的端可能重开

`HoeingGuardDecisions.ShouldRestart` 有 `isGuardRestartRun` 硬门控：一次守护重开之后，不再自动重开。它的优先级高于协同重开标志。

所以“所有端收到同一中止广播”不等于“所有端采取同一恢复动作”。只要各端已消耗的本地重开次数不同，就可能出现一个继续重开、其他结束的分叉。不能通过无限增加重开次数解决，否则可能恢复为无限重连循环。

原始片段只能确认该成员已用过重开机会。截图中其他端的状态尚未取得原始证据。

### 4.4 为什么上层进入小怪

存在两道相互独立的问题：

1. `AutoHoeingTask.Start` 消化异常后正常返回，外层不能可靠获知“精英只完成到第三轮”。`ScriptService` 有失败结果路径，但必须实际收到异常或显式失败结果；内部已吞掉的异常无法自动恢复为失败事实。
2. 助手 `BatchReconcileDecider` 对一般 succeeded/failed/rejected 都采用确认终态后推进的规则，用户取消和部分可重试错误另行处理。这是现有通用批次语义，不能靠正确标记 Failed 就自然阻止小怪启动。

因此要同时修复结果传播和联机批次策略。不能全局改变所有独立配置组的失败继续规则。

## 5. 已修与未修边界

| 项目 | 当前情况 |

## 6. 推荐解决方案

### 阶段 A：明确任务结果，停止假成功

复用现有 TaskRunResult、作业注册表与协调器，增加必要的联机业务结果信息，不另建并行的任务完成标志体系。

建议至少能区分：全部世界完成、策略允许的正常提前结束、用户取消、可恢复中断、恢复预算耗尽、执行失败、状态未知。业务分类可随既有结果携带原因，不要求全部变成新的全局 JobState。

实施要求：

- `AutoHoeingTask.Start` 保存异常/取消/业务终止原因；清理和授权内的恢复完成后，再向外层返回最终结果。
- 重开成功必须覆盖第一次失败的最终结果；重开失败或预算耗尽必须保留失败，不能因方法返回而变成功。
- 不能简单用 `_completedNormally == false` 把经验上限、用户停止、时间限制全部判异常。各类退出需明确映射，保留产品已有正常停止语义。
- 核对 `ISoloTask`/脚本宿主、TaskRunner、ScriptService、任务注册表、BgiTaskCoordinator、助手终态事件及轮询的完整传播路径。仅在 Start 内 throw 不构成完成。
- 路线 CD、当前世界完成和整个批次成功分别登记，禁止互相替代。未知状态保持未知。

### 阶段 B：对联机批次设置全队推进屏障

本次目标不是改变所有配置组的默认行为，而是给同一联机批次增加明确的失败和推进规则。

建议规则：只有全员对当前批次项达成成功或明确允许的正常终止结论，才允许进入下一项。一端失败、预算耗尽或状态未知时，不发后续配置组。手动取消按现有取消语义停止。

必须与阶段 C 一起验收：**仅改成本端失败停批次仍不足以保证全队一致**，因为别的端可能正在本地守护重开。

涉及入口：`BatchReconcilePlan.cs` 的决策模型、`MainViewModel.OnlineBatch.cs` 的动作消费、既有终态事件/轮询和批次收尾。失败停止不能冒充用户取消，不能误触发“全部完成”的绑定动作。抢占任务的恢复/租约释放应按既有清理合同处理，不能为了阻止下一组而永久占用任务槽。

### 阶段 C：统一恢复决策，禁止本地恢复与批次推进竞争

复用现有服务端协调层和协同中止通路，扩展为带身份的全队恢复决定；现有房间中止广播提供通知入口，但需要新增跨房间有效的批次决策记录。不能假定当前代码已有这项能力。

建议最小决策集：继续等待、共同恢复当前批次项、全队终止批次、全队放行下一项。

关键合同：

1. **稳定身份**：决策绑定 batchRunId、当前项身份、固定成员名单、世界轮次、attempt 和单调 revision。各端配置组显示名称可不同，不能只按名称匹配；同一房间号也不足以区分不同批次。
2. **单一决策权**：同一批次项恢复由服务端协调记录作权威；BGI 报告失败与本端清理状态，助手执行恢复/推进。不能保留未受该决策约束的本地自主重开同时运行。
3. **共享有界预算**：例如保留最多一次恢复的现有意图，但预算属于全队当前批次项而非各端私有布尔值。额度耗尽全队停止；不自动跳下一组。
4. **先停止旧任务再恢复**：新 attempt 放行前收齐必要成员的旧任务终止与槽位释放确认。失联、回执超时按显式失败/暂停处理，不把它当作已清理。
5. **跨房间保留**：旧房间关闭、退出世界和重建房间不能删除尚未完成的批次恢复决定。服务端重启或记录丢失时，各端进入未知/停止对账，禁止自行重开或推进。
6. **幂等与补查**：重复通知不重复启动，迟到的旧 attempt 通知不影响新任务。事件之外提供权威状态查询，避免丢一条广播就分叉。
7. **续跑依据**：根据已确认房主完成记录、路线 CD 与当前名单重建恢复起点。第三轮线路全 CD 时可正常完成空轮再进第四轮；不强行重跑已完成线路，也不预写第四轮完成。

所有参与端统一升级，不设计旧版本降级树。能力或协议不满足当前合同应明确拒绝启动该联机批次，不能半启用屏障。

### 阶段 D：日志和用户可见状态

将“重跑线路完成”“全员收尾完成”“当前世界完成”“精英批次项完成”拆开记录。最终日志至少包含：批次/项身份、世界进度、attempt、全员决策 revision、最终结果、停止原因、是否允许下一项。

示例：`精英未完整结束：已确认世界 2/4，当前第3轮收尾失败；恢复预算耗尽，全队终止，未启动小怪。`

其中进度必须来自真实确认记录，不能为文案方便写死为第三轮已完成。

## 7. 不采用的处理方式

- 删除 Completed 校验：会把提前收尾变成假成功。
- 固定延时几秒再检查：不能处理慢机、网络抖动和真实失败。
- 无限守护重开：恢复无限重连风险，也不解决各端预算分叉。
- 仅根据“未执行线路=0”放行：无法证明尚未进入的世界完成。
- 只增加异常上抛：助手一般失败仍继续，且脚本宿主可能再次吞掉异常。
- 仅靠 RoomClosed/重建房间保证一致：房间成员相同不等于各端运行同一个配置组。
- 全局改成任意配置组失败都停：超出联机批次范围，影响其他已存在的执行策略。

## 8. 验收矩阵

| 场景 | 必须满足 |
|---|---|
| 四人第三轮重跑，三人先回神像、一人延迟 | 先完成者继续等待；全员确认后进入第四轮；小怪不入队 |
| 第三轮全 CD | 正常结束空轮，进入第四轮，不触发重开 |
| 第三轮真实失败，全队有恢复额度 | 收齐清理确认，只生成一次共同恢复决定；全员仍执行同一精英批次项 |
| 历史各端本地重开标记不同 | 由同一批次预算决策，不再出现一端精英、三端小怪 |
| 恢复预算耗尽 | 全队停止当前批次；明确显示未完成世界；无小怪启动、无成功完成动作 |
| 一端掉线/终态回执丢失 | 通过查询对账；状态未证实前不放行；超时显式停止 |
| RoomClosed、重建房间、旧通知迟到 | 当前批次项和 attempt 不混淆；无重复恢复、无提前推进 |
| 服务端或助手重启 | 无权威恢复依据时保持未知/停止，不将旧任务当成功 |
| 第三轮已跑完线路但世界未确认 | 恢复利用 CD 与已确认记录，重新收口当前轮，再跑第四轮 |
| 手动取消、经验上限、时间限制 | 按各自明确语义终止，不能一律当故障重开；下一项规则有测试覆盖 |
| 普通非联机配置组失败 | 保持现有批次策略，不受联机门控误伤 |

验证分三层：纯状态机/决策测试；BGI—助手—服务端合同测试；实际四机精英→小怪完整批次验收。四机验收须同时记录版本、批次身份、attempt、第三/四轮进度和下一组启动时间。

## 9. 实施顺序与完成定义

1. 确认四端运行产物包含 `94da0cb8`，先验证已修的收尾触发点。此步骤不等于整体批次问题已修复。
2. 落实阶段 A 的真实结果传播，完成单端合同测试。
3. 将阶段 B 和 C 作为一个完整的联机批次闭环交付，配套日志。没有全队一致决策前，不宣称分叉已解决。
4. 完成上表四机实测后才宣布端到端修复；独立提交、分段审查，不顺带启动一条龙/槲寄生大迁移。

推荐默认策略是：**允许有界的全队恢复；恢复失败或预算耗尽则全队终止当前批次，不进入小怪。** 人工后续可选择恢复精英或明确跳过，但系统不能自行将未完成解释成成功。

## 11. 复核后实施结果

### 11.1 修正方案中的隐患

| 复核发现 | 本轮处理 |
|---|---|
| 只上抛异常，宿主或助手仍可能当作一般失败继续 | BGI 批次作用域保留未完成标记，队列输出 `hoeing_incomplete`；助手交给服务端决定恢复或停止 |
| 各端独立重开次数导致一端精英、三端小怪 | AllReady 固定成员名单建立独立批次；当前项必须全员成功才推进；恢复额度属于全队当前项 |
| 收到停止应答就恢复，旧任务仍在清理 | 按句柄请求取消；继续查询执行器终态；BGI 等 Dispatcher 委托和执行作用域退出后才公布结果 |
| 用全局停止误伤随后启动的其他任务 | 批次取消仅作用于拥有的任务句柄；旧句柄不能停止新任务 |
| 10 秒收尾定时器在全队等待时启动完成后任务 | 批次策略收尾必须通过 `CoordinatedSucceeded` 门控；异常分支清除恢复上下文，不执行成功动作 |
| 新 AllReady 覆盖尚在清理的旧批次 | 等待旧批次退出；超过 30 秒拒绝新批次。服务端也拒绝直接覆盖仍活动的批次 |
| 把正常关房的会话终止标记误判为失败 | 全轮正常完成凭证优先于正常关房标记；已知路线清零不能替代多世界完成凭证 |
| 资源缺失、组队失败、共同重跑提前返回却按成功推进 | 受管批次明确失败；共同重跑能力缺失拒绝执行，不添加旧版降级分支 |
| 启动应答丢失导致重复提交 | 固定请求身份，通过作业注册表找回句柄；最多补查 30 秒，不新建身份重复启动 |

服务端批次记录不依赖游戏房间生命周期，因此正常退出世界、房间关闭和重建不清除全队恢复决定。旧批次身份、旧 attempt、旧项回报不能推进当前项；同一成员更换运行 token 视为助手重启并终止旧批次。

### 11.2 当前明确的行为

正常路径：**四端完成精英当前项 → 服务端推进 → 四端开始小怪项**。

异常路径：**确认精英未完成 → 全队停止旧任务 → 收齐执行器终态 → 全队恢复精英一次**。再次失败、未知终态、人工取消、参与者失联或清理超时，停止该批次，不进入小怪，也不执行“成功后启动指定任务”。

恢复重新启动当前配置组，沿用既有已完成房主记录和线路 CD 逻辑；不是新增逐坐标快照恢复。恢复可能再次执行组内准备步骤、进入已完成世界走空轮。没有确认过的第四轮不会因当前线路数为零直接算完成。

范围为助手 AllReady 绑定的整个联机批次，包括其中的配置组和一条龙项目。未带受管批次标记的手动/独立启动保留既有策略。批次内一般配置错误按未知/中止处理，只有明确的锄地未完成错误进入共享恢复。

### 11.3 超时及容错边界

| 环节 | 当前界限和行为 |
|---|---|
| 全员登记 | 最多 3 分钟，未齐不开始 |
| 服务端成员心跳租约 | 90 秒；超期由后续查询触发全队中止，不缩减名单假装全员完成 |
| 全队清理 | 最多 90 秒，未确认全员终态不恢复 |
| 助手失去权威响应 | 30 秒内重连/查询，期间不启动新项；超期中止 |
| BGI 不可用 | 最多等待 60 秒；检测进程纪元变化即中止旧批次 |
| 单次 RPC | 10 秒上限；只读 IPC 短暂失败最多读取 3 次 |
| 启动结果未知 | 按原请求身份补查至 30 秒，找不到则停止推进 |
| 共享恢复 | 每批次项最多 1 次；完成后进入下一项重新计数 |

取消应答与任务终止严格区分。无法连接或游戏退出持续卡住时，程序能够保证不自动推进，但不能保证远端已成功退出游戏世界；会记录停止未确认，需人工检查。服务端重启不恢复内存批次，选择停止而非猜测成功。

各端绑定名称允许不同，只验证数量、顺序位置和类型；无法自动判断两个不同名称是否语义上都是“精英”。仍需用户正确配置相同的业务顺序。该实现没有引入完整业务流程配置同步。

### 11.4 自动化验证与待验收项

已执行源码构建和针对性自动化测试，使用独立 `_buildcheck_tmp/team-batch-client/`、`team-batch-server/` 输出目录；客户端构建传入 `DeployToBgiTools=false`，未覆盖用户运行产物。

- 服务端、控制房间及网关相关测试：66 项通过、0 失败。覆盖真实 AllReady 创建批次、网关响应和连接身份约束，以及固定成员、重复/迟到消息、失联、登记/清理超时、恢复预算。
- 客户端相关测试：146 项通过、0 失败，覆盖共享执行入口、任务队列、共同重跑、守护逻辑，以及本轮新增的结果分类、异步作用域隔离、只读重试、任务句柄取消和四成员合同测试。
- 四成员合同测试将真实服务端状态机与助手结果分类连接，验证：一端成功、一端第三轮失败、两端清理；清理未齐不能恢复；旧 attempt 成功不能算进新 attempt；恢复后四端成功才能推进小怪。
- 测试中保留现有编译警告；未以排除测试、替换失败断言等方式规避失败。此前已确认的其他基线失败不作为本轮通过项。

**尚未执行四台真实游戏端验收。** 需要全员 BGI、助手及服务端一起升级后，实测第三轮复苏重跑、慢机收尾、全 CD 空轮、F11、断线与恢复耗尽。自动化测试证明代码层合同，不证明游戏 UI、网络及发布产物已生效。

本轮按用户要求提交三端源文件、新增测试和本报告，未部署；不能只发布 BGI 侧异常传播，三端需要统一升级。
