## 0. 统一链路（冻结——所有执行请求的必经路径）

```text
可信入口上下文 → 无副作用动作解析（含既有冲突策略解释）→ 启动/控制/恢复三分类分流
→ 启动候选：仲裁轮次（原子入队快照→归一→冲突整组拒绝→去重→全序唯一胜者→授权记录）

→ 受理→接管台账落盘→确认可重建→关闭提交子状态；交接责任段独立存续至 settle/restore 闭环
```

## 2. 入口适配器与可信上下文（I1/B7/I-1）

### 2.1 可信入口上下文（AdmissionContext）

| 字段 | 来源 | 说明 |
|---|---|---|
| namespace | **调用方代码位置**（可信），不用 opcode/配置名/远程自报字段推断 | manual/v2/resume/system/trigger（trigger 归 R5.5，本阶段预留） |
| requestIdentity | 入口适配器首次接纳分配一次（Guid N 小写），同次用户操作的内部重试复用同一身份 | 分配发生在候选比较与提交之前；跨轮行为按 §3.3 请求状态分类表 |

**操作创建/续用分离**（六轮阻断 1 冻结——墓碑删除后旧身份识别依据）：
- **创建新操作**：只能由可信适配器在「无既有身份」时发起；身份分配+Operations 登记=**同一次原子发布**；**不得凭调用方提供的已有身份补建操作**。
- **续用已有操作**（重试/恢复/携带既有身份的调用）：适配器显式声明续用意图；Operations 记录缺失=**响亮拒绝 stale_operation_identity**，绝不回退为创建新操作/换身份/重新绑定。
- 无稳定客户端请求号的外部命令（旧 v2 客户端）：**每次命令=新操作**（不承诺两次外部命令识别为同一用户操作；R-2 不要求旧客户端升级的原话边界在此）。

来源本身不赋予 system 层级（R5.1 §2.2）。

## 3. 仲裁轮次与请求状态（B3/B-3/B-4 冻结）

### 3.1 轮次（并发合同）

- 门面串行段（单信号量）；**入队与「快照并移除」为原子操作**：进入串行段时快照当前待裁决队列并清空，该集合即当轮候选。
- 当轮处理：归一 → 同 candidateId 不同载荷/排序键=整组冲突拒绝（留痕，其余组继续）→ 去重（同身份+同载荷+同排序键）→ 资格筛选 → 全序唯一胜者。
- **非胜者生命周期**（三轮重要 3）：当轮裁决完成即完成——非胜者请求返回结构化「未获选」终局结果（含胜者引用与压制来源），请求状态=终局 NotSelected；**不留排队/裁决中悬置**，不自动进入下一轮（调用方按 §3.3 状态表决定后续）。
- **当轮裁决持续到胜者占位（提交子状态落盘）成功或明确失败才结束**；网络发送在锁外（B-4）。
- **确定性承诺精确表述**（建议①）：**相同归一候选集合及相同资格输入产生相同排序决策**；资格变化或最终校验失败不构成确定性失效。
- 门面排序仅对**本进程内队列**成立；跨进程排序不作承诺，跨进程一致性由租约文件锁+占位不覆盖保证（B-4）。

### 3.2 授权记录与唯一消费点（B-4/三轮 B-4——不可由外部请求自报）

**SubmissionAuthorization**={candidateId、规范化载荷指纹、目标 bgiEpoch、actionId、submissionIdentity、签发 revision、sendSeq}。
- **唯一消费点冻结**：授权签发、身份绑定、消费关系、Submission 占位=**租约锁内一次原子发布**（同一 revision 内四者同生）；
  RunStore/external-start-ledger 的镜像记录允许事后补写，**但不能反过来产生第二次消费**——消费权威=租约文件记录。
- E1 流程候选（runId/node 为空）=流程启动授权；**发送前固定 `candidateId→runId→首个实际执行节点提交键`** 并校验其属于获准流程定义；
  授权已消费而映射未持久化的崩溃窗：重启后以租约文件消费记录为准重建映射，**不得把同一授权绑定到另一 run/节点**。
- Runner 后继提交：授权绑定运行台账**合法游标及其修订**——「游标合法」与「授权尚未消费」同时成立才签发；**同一游标只产生一次对应提交授权**；租约有效本身不是后继授权。
- **Submitting 是责任状态，不是发送许可**：重启读取/对账回退/重复调用不得凭 Submission.state=Submitting 重新取得发送权；发送许可仅存于「当轮锁内占位成功后的当次锁外发送」。
- 抢占确认仅是提案确认；实际取消/挂起前须重新串行准入并持久化交接意图，不凭旧确认结果直接产生副作用。

### 3.2a 两层模型：逻辑绑定唯一 × 发送许可分轮（四轮阻断 2 冻结）

- **逻辑执行绑定唯一**：candidate→run→节点/游标的绑定不可改写（同游标=同一逻辑执行，只绑定一次）。
- **发送许可按 sendSeq 分轮**：同一逻辑绑定仅在「上一轮经关联验证确定未受理」时才产生下一轮发送许可；**Unknown/已受理/待对账一律不产生下一轮**。
- 无损拒绝重试**不增加业务 attempt**；确认取消后重跑才进入新 attempt。
- 线上提交键与拒绝缓存语义**按操作逐条冻结**（§6.1 映射表）；无法证明旧键可重试时，不得仅凭本地 sendSeq 递增认定重试成立。

### 3.3 请求状态分类表（B-3——操作身份与处理状态分离；状态读取/迁移在权威串行边界内完成；持久化载体=Operations[] requestState/lastResult，§4.1）

| 已有状态 | 同身份调用行为 |
|---|---|
| 排队/裁决中/已占位/发送中 | 合并到已有处理，不新增发送者 |
| 未知/待对账 | 返回对账状态，不重发 |
| 已受理/终局完成 | 返回既有结果 |
| 可重试拒绝（操作级白名单内，已关闭 Submission） | 预算内由唯一重试者重新 Admit：**重新签发授权、重新占位、sendSeq 递增**；并发重试者合并 |
| 身份冲突（同身份不同规范化载荷/排序键）/不可重试拒绝 | 返回终局拒绝——**不得静默返回成功**；冲突拒绝不抹掉原请求已受理事实 |

**可重试拒绝的退出与再入场**（三轮 B-3 冻结）：
1. **一切经关联验证的确定未受理结果都先关闭对应 Submission**（无论是否可重试）——重试资格不决定是否保留未决提交责任；
2. 请求再记为「可重试拒绝」或「终局拒绝」；
3. 重试时请求身份（requestIdentity）不变；**线上提交键是否复用按具体协议对拒绝结果的幂等缓存语义确定**，不自行假定旧键可重试；
4. **sendSeq（发送序号）区分同请求的各次发送**：上一轮迟到结果不得完成下一轮占位（关联校验含 sendSeq）；
5. 身份与载荷/排序键一致性检查**先于**缓存结果返回。
6. **重试窗口持久化与到期转终局**（七轮重要 1 冻结）：首次进入可重试拒绝时持久化**有界重试窗口截止时刻**（retryWindowDeadlineUtc，由首次确定拒绝时刻+窗口上限派生）；后续重试与进程重启**一律沿用持久化截止时刻，不得重置**；窗口到期后由当前所有者**锁内复核**「最近发送经关联验证确定未受理且无更新发送责任」成立才转终局拒绝（复核不成立=保守停驻，不臆断）；该到期处理**仅适用于有确定拒绝证据的操作，绝不用于 Unknown/Reconciling**（后者按 §4.1a 终局判据表第四行持续待对账）。

**操作级重试白名单初表**（协议审查子集，随实现逐操作登记）：IPC task.start 的「任务运行中」无损拒绝=可重试（既有 1s×6 语义）；**stale_epoch/request_expired 等身份/时限类一律不在透明重试**（epoch 固定合同 I-1：变化即拒绝或对账，不重写身份）。

## 4. 提交责任模型与统一提交边界（B-1/B-2 冻结——R5.1 冻结稿修订登记，加法不动序列化框架）

### 4.1 数据结构：交接责任与提交子状态分离

租约文件 handoff 段拆为两个独立字段（**取代 v2 的 Submitting 枚举方案**——HandoffPhase 既有六值不动）：

```
LeaseHandoffSegment {
  Pending?      // 交接责任（被切方/授权抢占方/恢复责任；阶段机 R5.1 §4.1/§4.1a 不变）
  Submission?   // 当前未决发送（至多一笔）：{ submissionIdentity, sendSeq, actionId, targetEpoch,
                //   candidateId, state=Submitting|Reconciling, recordedAtUtc }
  Operations[]  // 逻辑操作权威记录（本段新增，恢复权威——不依赖可缺失的镜像）：{
                //   requestIdentity, candidateId, payloadFingerprint, sortKeyFingerprint,
                //   runBinding?（candidateId→runId→首节点提交键，不可改写）, cursorRef?+cursorRevision,
                //   requestState（§3.3 状态机）, lastSendSeq, retryWindowDeadlineUtc?（§3.3-6，持久化不得重置）, lastResult?{ outcome=Accepted|Rejected,
                //   reasonCode, retryable, retryBudgetUsed, evidenceSource, answeredSendSeq }, takeoverRef?,
                //   zone=Active|TerminalPendingTransfer|Tombstone, updatedRevision, updatedAtUtc }
  // 关闭后保留的完整发送关联（六轮重要 1 冻结）：submissionIdentity 全量保留；targetEpoch 原目标实例/epoch
  //   不可改写；wireSubmitKey（线上提交键，无法确定性推导时显式存储，逐操作 §6.1）；runBinding/cursorRef
  //   不可改写；lastResult.answeredSendSeq 标注结果对应的发送轮次——下一轮占位后不得把上一轮拒绝误当本轮结果。
}
```

- **Submission 只承载当前未决发送；Operations[] 承载逻辑操作全史**——关闭事务=同一次锁内原子发布内「更新 Operations 记录（结果/状态/水位）+ 移除 Submission」，无「已关闭、状态未记录」崩窗。
- 拒绝关闭后镜像未补齐即重启：runId/首节点键/游标绑定/重试预算**从 Operations 原样恢复**（不重置、不改写）。
- **outcome 仅 Accepted/Rejected**（五轮重要 1）：对账确认的受理结论写入 `evidenceSource`（原始回执词/对账结论+产生端），不设第三关闭依据；owner 显式对账只是取证入口。

- **关闭 Submission 只移除未决责任**；操作事实由 Operations[] 继续保留（消费权威=租约文件）。

### 4.1a Operations 状态分区、终局判据与清理安全（五轮阻断 2/六轮阻断 2+重要 2 冻结）

**状态三区**（同一 Operations[] 内的记录状态，非物理分区）：
- `Active`（非终局）：**永不清理**；占用主槽位（主槽位口径见容量联动）。
- `TerminalPendingTransfer`（已终局待迁墓碑）：**占用主槽位**——终局只改状态不申请新槽位，**迁移成功才释放原槽位**；结果落盘与 Submission 关闭**无条件允许**（责任结清不被容量阻断）；暂留原槽位，墓碑有空间时迁移。
- `Tombstone`（终局墓碑）：环形上限 256 且最短保留 24h；迁入即释放主槽位。

**终局判据表**（按事实分类，无远端作业的操作不虚构台账）：

| 操作情况 | 可终局依据 |
|---|---|
| 从未发布发送许可、确定不再处理（未获选/本地校验拒绝） | 本地权威裁决+无未决发送责任 |
| 经关联验证确定未受理 | 拒绝证据+不再允许重试（预算耗尽/终局拒绝——预算规则 §3.3） |
| 已受理 | 关联执行权威终态（BGI 快照/job 注册表）+接管台账一致 |
| Unknown/待对账 | **不得仅凭超时或查询未命中终局**（持续停驻，§8 待对账夹具） |

**身份冲突调用的拒绝不改变原操作已受理/未决事实**（终局判定的附属冻结）。

**容量联动**（六轮重要 2 初版，七轮阻断修订）：主槽位计数 `primarySlotsUsed = Active 数 + TerminalPendingTransfer 数`，上限 32。
- **新操作创建**（§2.1 创建路径）准入双条件：①`primarySlotsUsed < 32`；②Tombstone 有空槽或可立即清理出 1 槽（到期墓碑）。**容量检查/清理迁移/新登记在同一权威串行边界内完成**——先迁移可迁项再重判主槽位，仍不满足才响亮拒绝 operations_capacity_full（不凭边界外读数判定）。
- **终局与关闭不申请新槽位**（Active→TerminalPendingTransfer 原地保留；迁移成功才释放）；续用/取证/关闭调用不走新槽位门槛。
- **拒绝诊断**（七轮建议②）：operations_capacity_full 诊断分别显示 Active 数/待迁移数/墓碑数/最早到期可清理时间，可观测可处置。
- **吞吐代价明示**（八轮实施关注 2，接受为非缺陷）：256 墓碑均未到期时即使主槽位空闲新操作仍拒绝；长循环/多节点流程同样可达——实现期如实报告该压力场景，不得误诊为槽位泄漏，也不得临时放宽未知责任清理/旧身份补建规则。
**重放安全**：兼容重试预算窗口为秒级有界，24h 墓碑 ≫ 合法重放窗口；墓碑已清理的旧身份再到达=由 §2.1 创建/续用分离兜底（续用方记录缺失=stale_operation_identity 响亮拒绝，不创建不绑定）。

### 4.0 租约文件格式演进（三轮 B-1 冻结）

- 租约文件 `version` 升为 **2**（新增 Submission 字段的格式代）；既有 R5.1 消费方按 Unsupported 合同**响亮拒绝** version 2 文件——不依赖「加法字段被旧读者忽略」的弱假设（R5.1 §6.2 Unsupported 语义原样复用，不动序列化框架、不升流程定义 schemaVersion）。
- version 1 文件（R5.1 格式）由新消费方读取时：Pending 段原样保留（未决阶段/关联身份/ReconcileFromPhase 不动），Submission/Operations 视为空（向后读兼容）；**缺字段沿用保守拒绝，不默认为无责任**；写入一律 version 2。
- **降级边界**：静止是允许评估降级的必要条件，**不自动完成格式降级**——version 2→1 的转换/重建/禁止降级策略挂账 R5.6（迁移切换统一裁决），静止后直接用旧版读取仍会 Unsupported（按设计）。
- **静止判定扩展**（切换/迁移前置，§7 闸门与 R5.6 复用）：未决 Submission、已受理未终结台账记录、Pending 交接责任，三者任一存在=非静止。

- **提交子状态回答「本次提交是否仍可能被受理」；Pending 回答「原交接是否还有恢复责任」——两者独立存续**。
- **双字段组合约束**（三轮重要 1）：Pending.ReconcileFromPhase 不受 Submission 状态切换影响；关闭 Submission 不调用 Pending 消解接口（TryResolveIntent 仅服务 Pending）；Pending 与 Submission 并存时二者**授权抢占方与目标 epoch 必须匹配**（锁内写入校验，不匹配=invalid_request 响亮拒绝）；拒绝操作不改变任何责任字段。
- 受理/确定拒绝只关闭 Submission；**绝不顺带消解 Pending**（票据压制与恢复责任保持至 settle/restore 闭环）。
- 直接启动：Pending=null + Submission 落盘；抢占路径：Pending 存续 + 授权方提交时 Submission 落盘。
- Submission.Reconciling=发送结果未知（等价保守语义，不换键重跑）；对账证据转换：原受理回执丢失但关联 job 已运行/终结→可确认「曾受理」，**保留原始证据来源、不伪造远端回执词**；Reconciling→Submitting 仅恢复责任阶段，**不得重新触发发送**。

### 4.2 统一提交边界（一切执行提交必经）

1. **锁内最终校验**（切换锁→租约锁；**锁内只消费本地事实**——不含远端网络查询，I-3）：F11 闸门 → 票据压制 → 资格关键事实复核 → 租约四连（leaseId+ownerEpoch+expectedRevision+TTL 未过期且属当前所有者）→ 目标 bgiEpoch 匹配（只比较不重写）→ 切换闸门未激活 → Submission/Pending 冲突检查。
2. **Submission 落盘**（锁内，原子发布）；**发布失败=不得发送**。
3. **锁外发送**：既有提交路径原样。
4. **三态对账**（协议面×操作映射，§6.1）：受理→**先持久化接管台账**（E1/E2=RunStore 运行记录；E3/E4/E5=外部启动台账 external-start-ledger.json，修订守卫，含 submissionIdentity/resourceRef/受理时刻/bgiEpoch）→**确认记录足以跨重启重建**→关闭 Submission；两份记录短暂并存按去重处理，**不得出现两份同时缺失**（B-2）；确定拒绝→关闭 Submission 留痕（§4.2c 统一关闭接口）；未知→Submission.Reconciling。

### 4.2c 统一关闭接口（四轮重要 1 冻结——两个合法分支，无第三路）

关闭 Submission 仅两类依据：①**受理且接管台账已持久化并可重建**；②**经关联验证的确定未受理**（含白名单内可重试拒绝——先关闭再按 §3.3 记可重试/终局）。
两分支共同校验：当前所有者四连+当前 revision+目标发送身份（submissionIdentity+sendSeq）匹配；**都不消解 Pending**；关闭即同次原子发布更新 Operations[]（结果/状态/sendSeq 水位）并移除 Submission。
「拒绝操作不改变责任字段」限定为**本地准入/存取校验失败**（invalid_request/lease_stale_generation 等响亮拒绝）——不涵盖远端确定未受理后的责任结清（那是关闭分支②，字段变化=Submission 移除+Operations[] 结果/状态同次原子更新）。
5. **租约所有权更替继承 Submission 与 Pending**（不随换主清空）。

**接管顺序反例钉死**（B-2）：受理回执到达 → 接管台账未落盘时崩溃 → Submission 仍在 → 重启对账按 submissionIdentity 查 job 注册表确认「曾受理」→ 补落台账 → 关闭 Submission。验收注入「受理后/台账落盘前/意图消解后」崩溃窗与「queued 尚未出现在运行快照」并发请求。

### 4.2a 接管台账合同（三轮 B-2 冻结）

- **必要字段**：submissionIdentity+sendSeq（完整发送关联身份，与 Submission/Operations[]/回执处理/对账同一规则）、candidateId、resourceRef、actionId、目标 bgiEpoch、受理时刻、受理证据来源（原始回执词或对账结论+产生端）、状态（AcceptedPendingExecution/Running/Terminal）、关联 runId（E1/E2）。
- **准入读取规则**：资格快照的「执行占用」= BGI 快照 ∪ 运行台账 ∪ **external-start-ledger 中已受理未终结记录**——queued 不因运行快照为空而失去占用意义；台账损坏/读取失败/记录交叉不一致=保守待对账，不推导空闲。
- **终结与清理**：台账记录仅在关联 job 权威终态（BGI 快照/注册表）确认后转 Terminal；Terminal 记录按既有历史保留策略清理（不即时删除）。
- **关闭 Submission 接口合同**：验证台账接管事实后，按「目标 Submission 身份+当前 revision」锁内关闭；**非所有者收到回执只能提供证据，不凭旧修订消解新所有者持有的责任**；旧回执不关闭另一笔 Submission（sendSeq+身份关联）。

### 4.2b 崩溃/交错行为表（三轮 B-2 冻结——每行有夹具）

| 崩溃或交错位置 | 必须维持的行为 |
|---|---|
| Submission 发布后、发送前 | 恢复者不得仅因 state=Submitting 就发送；继承原身份保守对账 |
| 已受理、台账未发布 | 保留 Submission；查询未命中不能消解 |
| 台账已发布、Submission 未关闭 | 按完整身份合并；重复接管幂等 |
| Submission 已关闭、仅有台账 | 台账继续阻断冲突启动（§4.2a 准入读取） |
| 关闭前后所有权更替/迟到回执 | 重新读取并校验当前关联记录；旧回执不关闭另一笔 Submission |
| 台账损坏/读取失败/交叉不一致 | 保守待对账，不推导空闲 |

### 4.3 物理边界声明（I-3）

助手侧锁只承诺**授权与意图发布的原子性**；物理执行竞争仍由 BGI 权威执行锁处理。锁无法冻结外部原生任务启动——原生面排除项（E5b/E6 外部/E7）由此兜底，不属逻辑准入承诺范围。

### 5.1 恢复五路径（逐路径标明实际副作用与准入）

|---|---|---|

**恢复/打断的锁约束按实际动作拆开承诺**（三轮 B-5 冻结）：
- Stop/F11 的**立即停止部分**保持独立直接路径——不等仲裁、不等租约锁、不被租约故障阻断；
- 查询/通知/恢复事实登记可走独立路径；
- **发出 resume、恢复票据或产生抢占执行副作用**=必须完成各自持久化准入（恢复专用边界：继承租约所有权四连+TTL+**原票据 BGI 权威校验**+保留 StopVersion/SuppressCompletionAction 校验传递）；允许有界等待或快速失败留待处理，**不因控制路径低延迟要求绕过责任发布**；
- 人齐打断若含后续启动/恢复：「立即停止」与「产生新执行副作用」分别按上两条约束。

**「未完成交接禁止后续执行」限定**（B-5）：禁止的是**无关或未经授权的后继提交**；用于完成该交接的合法恢复动作（A6 恢复经恢复专用边界）不受此禁。

## 7. F11 与事实快照合同（B2/I-3 冻结）

1. **F11 判定先于租约获取与一切排序**——F11 激活时 Admit 直接 F11Blocked，不发生租约副作用；Stop/F11 停止路径不走 Admit，不被租约故障阻断。
2. EligibilitySnapshot 全输入枚举：到点/窗口、链内前置就绪、人工暂停、固定排程占用、F11 态、票据与执行占用、未决意图/提交子状态。
3. 快照语义：快照来源/有效期/epoch/停止版本/失效规则逐项登记（实现入档）；null/过期/失败/epoch 不符=**未知**——未知占用不解释为空闲。
4. **锁内只消费本地事实**（无远端网络查询）；本地事实更新与准入检查正确串行（事实供给方先刷新、锁内读最新本地快照）；含远端查询的取证一律锁外有界等待——**停止/打断的立即停止部分不取门面信号量、不等租约锁、不等 IPC 队列**（夹具断言，R-4 行为零回归）；含执行副作用的恢复/启动部分按 §5.1 锁约束（三轮 B-5），两部分承诺不互相套用。
