## 1. 用户需求与交付目标

以一个执行端 A 为中心，管理 A 在多个助手房间中的独立联机任务配置，并将完成后的去向可视化。

例如，A 在甲房间与 B、C、D 执行联机锄地，整轮正常结束后，按 A 在甲房间预先设置的完成后动作登录乙房间。切换成功后加载 A 在乙房间的独立配置。乙房间的 E、F、G 可能还没有准备好，此时 A 可以：

- **待命**：不启动任何额外任务，等待乙房间通过原有机制准备、上线并开锄；
- **执行指定任务**：执行选定的 BGI 配置组、一条龙或槲寄生计划表，在等待队友期间做其他任务；其中可利用现有「联机锄地上线」任务或受支持的命令，在合适时机触发乙房间的上线。

乙房间以后开始联机锄地时，仍按乙房间自身的绑定、成员、人数、定时及现有联机接管规则执行。整轮正常完成后，根据乙房间自己的完成动作，继续切换到丙房间、恢复任务、停止或执行指定任务等。

三个动作必须区分：**实际登录房间、执行普通本机任务、提交联机锄地上线意图**。切换成功本身不等于上线，也不等于已经开始下一轮联机任务。

首版建议覆盖当前本机执行端所有已保存的房间档案（目前上限 5 个，支持不同服务器），不要求为每个房间开一个助手实例。本机与目标房间的配置关系由 A 自己设置，不替其他成员安排去向。

**版本前提（用户已明确）：全体用户及必要的 BGI、助手、协调服务端统一升级，不考虑新旧版本混用、旧客户端协议兼容或降级运行。** 升级须接续现有用户已保存的配置和数据，原有动作、房间隔离、远控及其他功能仍须正常。只按照同版实际需要调整协议和校验，不为旧程序增加兼容层。

## 3. 正式界面设计

### 3.1 入口及返回

在现有「助手房间」下拉窗口标题右边增加「任务编排」按钮，其他控件与样式保持原样。

```text
助手房间    [任务编排]                 ×
最后确认：甲房间 · B54387

  所有房间        3 个房间
✓ 甲房间                          B54387
  乙房间                          24D888
  丙房间                          C12345

[复制房间号] [管理房间]        [切换房间]
```

- 点击「任务编排」关闭下拉窗口，在耕地机主体区域进入独立编排视图；右上角原来的「查看：…」显示「任务编排」。保持既有顶栏固定宽度（96 DIP）及其他布局。
- 进入、退出、编辑编排仅改变界面，不改变当前实际登录房间或旁观房间的授权。
- 重新选择具体房间或「所有房间」，返回原耕地机成员卡片视图；区分用户主动选择与 `SelectionChanged` 自动同步。编排页打开时，即使下拉窗口正打开、实际切房或档案刷新，也不得误退出编排、改写原查看房间或释放其旁观连接。
- 新增独立 `IsShowingRoomOrchestration` 或相当的 Home 内容状态；完整隐藏原成员卡片及其批量/快捷指令区域，不改变 `ViewedRoomProfileId` 原有持久化语义及其他页面导航。鼠标、键盘主动选择均可正常返回。遥控器模式不开放本机执行端编排写入，保存时再复核运行角色。
- **页面选择必须记忆（用户新增要求）**：在 `AssistConfig` 增加独立的 Home 内容模式（例如 `showRoomOrchestration`，默认 false）。主动进入任务编排时立即原子保存；主动选择具体房间/所有房间返回时，同一次保存更新模式与原查看房间 ID。下次启动直接恢复该模式及查看房间，不先闪现另一页面。自动切房、房间刷新、程序同步选择及切到其他主导航页面均不得重置该记忆。配置保存失败显示未记住，不能假报成功；普通设置保存及配置导入保留本机显示偏好，运行角色不支持编排时按原房间视图安全显示而不擅自写回旧记忆。该字段与实际登录、任务运行、房间档案切换分离。复用[已存在的查看记忆](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.RoomView.cs#L130)、[启动配置](../../MultiplayerHoeingAssistant/App.xaml.cs#L89)和[导入保留本机偏好入口](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.ConfigTransfer.cs#L311)，不新建页面设置文件。

定位：[MainWindow.xaml](../../MultiplayerHoeingAssistant/Views/MainWindow.xaml#L809) 顶栏、[房间弹窗](../../MultiplayerHoeingAssistant/Views/MainWindow.xaml#L990)、[Home 内容](../../MultiplayerHoeingAssistant/Views/MainWindow.xaml#L1270)、[弹窗事件](../../MultiplayerHoeingAssistant/Views/MainWindow.xaml.cs#L195)。

- 图示自动生成，所有房间都展示，即使没有连线；支持多个房间指向一个房间或形成多房间回环。回环不会因登录直接触发下一次切房，每次都仍需实际联机执行、正常完成及原批次结清。目标不能是当前源房间本身。
- 样式沿用紫金主题；原生 WPF `ScrollViewer`、`Grid`/`Canvas`、`Border`、`Polyline`、箭头，采用纵向自然布局、鼠标滚轮及左键拖动浏览，不引入图形库、不提供缩放适应工具。可参考[已有流程图](../../MultiplayerHoeingAssistant/Views/FlowChartWindow.xaml)和[任务中心图示](../../MultiplayerHoeingAssistant/Views/TaskCenterFlowChartWindow.cs)，不修改其模型或窗口。
- 连接线表示已保存的配置；实际登录标记只依据已确认的连接。区分「正在联机锄地」「等待甲批次结清」「正在切换」「乙已就绪」「切房后任务已受理/运行中/完成/失败/待核对」「上线待确认」「乙已上线等队友」等状态。本地 `IsOnlineReady` 不能单独作为服务器已受理上线的依据；未确认或旁观断线不可假报成功。展示最近一次已确认的跳转及其后续动作状态即可，不增加历史管理系统。
- 房间改名后以稳定 ID 保持关系；删除目标、修改服务器或房间号时，显示关系失效或要求重新确认，禁止静默改成其他目标。当前状态高亮不得仅来自配置中的去向。

#### 3.2.1 逐项执行状态与可读性（用户新增要求）

房间卡显示的是**本机在该房间的任务**，而不是其他人的执行结果；同时清楚展示当前已确认登录位置。每个绑定任务必须按执行顺序逐项显示名称、类型、状态及可确认的进度/结果。房间头部说明最近一次执行的时间，连接线上分别展示切房确认、后继任务及命令上线受理状态。不能用一个绿色房间卡掩盖其中仍有未执行、失败、取消或待核对的任务。

| 状态 | 视觉表达（既有主题色 + 图标 + 文字） |
| --- | --- |
| 当前实际登录 | 金色外框与定位图标、明确「当前登录」，不是任务成功标志 |
| 已完成 | 青绿勾选及「已完成」，必须有匹配任务的成功终态证据 |
| 正在执行 | 淡蓝播放图标及「进行中」，必要时显示当前已确认的任务序号与进度；不是仅已入队 |
| 等待 | 金色时钟与明确原因，如待命、上线待确认、等队友（确认人数）、等旧批次收尾或等待切房 |
| 未开始 / 无记录 | 紫灰空心标记；只有当前批次确认未开始才写「未开始」，无历史证据显示「无执行记录」 |
| 已停止 / 已取消 | 中性色停止标记，区分停止、取消和真正失败 |
| 失败 / 带错误完成 | 火元素色警示标记和文字，显示可确认原因，不把带错误完成标成正常成功 |
| 断线 / 结果未知 | 问号及「待核对」，不把最后一次状态当成实时运行 |

已有[批次快照](../../MultiplayerHoeingAssistant/Services/CoordinatedBatchSnapshot.cs#L3)、[旁观房间批次](../../MultiplayerHoeingAssistant/Services/RoomSpectatorSession.cs#L288)、[本机作业终态证据](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.CoordinatedBatch.cs#L752)可复用，但批次 Index 推进不一定代表该项成功。显示归属按档案 ID、服务器/房间号、本机身份、批次 ID/代次及实际 jobId/runId，任务使用冻结的绑定顺序。编辑后的新顺序标为下轮生效，不把旧任务完成标志按新列表下标套用。所有房间汇总列表会按 UID 去重，编排读取对应房间快照，不从汇总卡片反推自己的状态。

现有切房会清空旧房间的最后批次显示（[提交入口](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.RoomSwitch.cs#L383)）。仅保留每个房间最近一次本机已确认的执行结果/冻结任务顺序/时间，以及现有方案所需的最近确认跳转和在途状态，支持重启后的正确显示；不建立新日志或历史查询系统，不调用管理端专用历史接口。回环进入新批次后当前轮状态重新归属，过去的成功只显示为带时间的最近记录，不以全局百分比宣称所有路线跑完。重启时未确认的运行状态重新核对，未经确认不得显示正在执行或已完成。

#### 3.2.2 界面形态与审核门

保持原 [MainWindow.xaml](../../MultiplayerHoeingAssistant/Views/MainWindow.xaml#L8) 的紫金主题、HarmonyOS Sans SC 字体、240 DIP 左栏、顶部两行导航及 96 DIP 查看按钮；只替换 Home 内容区。默认窗口 1180×860，最小 980×720。经过[三方向比较](assistant-room-orchestration-ui/directions.md)与独立 UI 审核，用户最新明确[改选 A 纵向接力图](assistant-room-orchestration-ui/direction-approved.md)，删除重复标题行和适应/缩放工具栏，直接使用拖动与滚轮。正式视觉参考为[纵向简洁版交互原型](assistant-room-orchestration-ui/design-demos/dir-1-v2.html)、[默认窗口](assistant-room-orchestration-ui/design-demos/dir-1-v2.png)、[向上拖动后](assistant-room-orchestration-ui/design-demos/dir-1-v2-dragged.png)及[最小窗口](assistant-room-orchestration-ui/design-demos/dir-1-v2-min.png)。原型仅示例数据，不连接真实助手、不报告真实运行；正式只实现 A，不保留 B 的横向布局或多模式切换功能。

**纵向画布最终约定：**

- 删除内容区整行独立「任务编排」标题及原本机执行端/最近执行状态、缩放工具栏；顶部现有查看标签已足以标明页面。保留紧凑当前登录/执行状态条。2026-11-26 用户进一步明确删除状态条下方整行（房间数量、各状态数量及「按住拖动 / 滚轮」提示），不保留占位；房间卡片内的状态和进度、画布拖动及滚轮功能不变。
- 房间节点沿纵向接力线排布，卡片按可用宽度自适应，任务名称、类型、状态及配置操作分列，完整连接动作在两个房间之间显示。已完成/计划连接采用可识别的线型和图标。多路线、汇合和回环保留明确有向关系或已有节点引用；独立房间另列。相比原 B 不需要强行横排、横向导航、定位当前、缩放或适应功能。
- 仅图示内容区域自然纵向滚动，当前登录/执行状态保持可见；鼠标滚轮是默认操作，内容超过可用高度时沿用现有原生滚动条。鼠标/键盘及未来触屏均可浏览完整节点。四、五房间或长任务超出视口时不得强制压缩字号；保证滚到末尾后最后一个房间及全部编辑入口可用。状态更新不强制跳到新节点，尽量保持当前视口位置。
- **左键直接拖动画布**：按住空白、连接区域或卡片非交互部分向上/下拖，移动超过系统拖动阈值（原型 6 DIP）才捕获鼠标并平移视口；有抓手反馈。不拖动节点、不建立连线、不修改配置；编辑按钮、下拉、可选文字、原生滚动条保持原交互。松开、取消、失去捕获及窗口失焦及时释放，不产生误点击；没有可滚动内容时不拦截正常操作。不新增缩放/适应、左右浏览或底部工具条。
- **未来网页版**：在助手侧展示数据边界，将房间稳定 ID、冻结任务顺序/状态、当前登录、连接与后继动作、已确认时间和结果同 WPF 布局/滚动状态分离。未来网页可沿用相同状态语义、纵向自然滚动及触屏滑动；本会话不开发网页版、Web 专用接口、远程编排协议或第二套执行逻辑，不改变当前网页产品。

- 房间名、任务名、状态标签、配置按钮各占可用布局，长文本换行并提供完整内容访问；不将状态挤出可视区、用极小字强行适配、让箭头穿过节点或遮住操作控件。五房间、汇合/回环、独立房间、空数据都须可读；窄窗优先重排，必要时只使用内容区滚动。连接线独立区域，提供文字的源→目标关系。

### 3.4 在编排页直接编辑任意本机保存的房间

不要求登录某个房间才能编辑在该房间的任务。节点「编辑配置」打开明确标记房间名称/房间号的编辑器，复用现有联机绑定（配置组、一条龙及顺序）、完成后动作、定时、预期开锄人数等对应设置；可查看快捷指令摘要并复用现有对应编辑入口。任务目录来自本执行端的 BGI/助手，而非目标房间的其他成员。

既有[绑定编辑入口](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.cs#L3727)会将旁观房间卡片识别为远程目标，**不能**通过模拟点击另一房间的成员卡片来写本机档案。新增按本机档案 ID 的窄读写入口：

- **以 `ActiveRoomProfileId`（而不是连接是否在线）判断配置归属**。活动档案即使处于断线或单机状态，仍从运行中的 `_config` 读取；保存同时同步运行字段及档案，按原规则上报、处理定时。实际登录标记另按确认连接判断。
- 非活动档案：读取及写入指定 `AssistantRoomProfile`，不改当前运行字段，不切房、不发送其他房间命令、不重启当前房间定时器。
- [AssistConfigManager.TryStore](../../MultiplayerHoeingAssistant/Services/AssistConfigManager.cs#L154)会重新捕获活动档案；[现有完成动作保存](../../MultiplayerHoeingAssistant/Services/CompletionPolicyFields.cs#L69)又可能仅更新内存运行字段，随后的[普通设置保存](../../MultiplayerHoeingAssistant/Views/SettingsWindow.xaml.cs#L118)可能再次应用旧档案。新编排及原绑定/完成动作入口在相关保存边界上，以最新配置为基础定向更新本次实际改动的字段，同一提交内核对档案身份/原编辑版本并同步档案及运行字段。复用配置导入守卫、切房保护、原子落盘及读回确认；不能用打开窗口时的整份旧副本覆盖其他房间或远程更新，不重写全局配置管理器。
- 绑定任务目录仍来自本机 BGI；队友绑定结构只检查所编辑房间的有效成员快照，无该房间快照时提示尚未核对，最终沿用已有开批校验。BGI 不可用或旧绑定为空时，未修改的绑定不得阻挡其他字段保存；实际修改的任务引用仍须按现有规则校验。目录刷新后的选择列表与保存校验使用同一目录。依据：[现有绑定校验](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.cs#L4481)及[OnlineHoeingBindingValidator.cs](../../MultiplayerHoeingAssistant/Services/OnlineHoeingBindingValidator.cs#L43)。
- 非活动房间定时编辑仅在用户明确设定或确认其定时时，同步该档案的 `_roomScheduleSuppressed`、待确认及当日触发状态（[切房恢复抑制](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.RoomSwitch.cs#L348)）；保留现有过时不补触发规则。只修改完成动作、绑定等字段不解除定时抑制或导入待确认。定向编辑不提供同步全员选项，活动房间的预期开锄人数及其他设置仍受原执行/等待期间限制。

## 4. 数据与运行设计（尽量小的改动）

### 4.1 保存合同

不新建另一个流程配置系统。扩展现有房间级完成动作，逻辑上应能表达：

```text
源房间：甲的档案 ID + 配置确认时的规范化服务器/房间号
完成动作：切换助手房间（明确的业务动作类型）
目标房间：乙的档案 ID + 配置确认时的规范化服务器/房间号
切换成功后动作：待命 | 执行指定任务
若执行指定任务：任务类型、目标任务、起始方式、起始任务、优先级等
```

内部字段命名和布局由实施时对现有类型核实后定稿。建议保持通用 `TaskConflictPolicy.Resume/Stop/RunSpecified` 的现有收尾语义：界面显式呈现「切换助手房间」，旧批次内部沿用 Stop 释放责任，另外冻结切房目标及后续动作快照。避免将房间名称编码进任务名，或直接扩展通用枚举导致遗漏分支并误恢复任务。目标和后续动作都明确校验；普通 Stop 与切房动作有独立语义。

- 已有用户配置缺少新字段时完全按原来的完成动作；普通动作无切房目标，不触发切房。若明确选择切房但目标或后继任务无效，提示设置错误，不当成普通停止或随机选择目标。修改为恢复、停止或普通执行指定任务时清空切房及其后续动作数据，避免残留隐式动作。
- 更新 `AssistConfig`、`AssistantRoomProfile.Capture/ApplyTo`、`CompletionPolicyFields` 读取/保存/校验、`CompletionActionPanel` 快照、批次冻结/恢复快照、设置导入确认比较等真正消费位置；不改无关全局配置合同。
- 建立关系时同时保存源、目标档案 ID 与当时规范化服务器地址/房间号（配置确认，不要求连接目标）。现有房间管理允许保留 ID 改址，[档案编辑入口](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.RoomSwitch.cs#L689)表明单纯冻结 ID 无法防止关系在下次开批时被静默解释为新地址。改名不影响，改址或删除则关系失效，要求用户重新确认。批次受理及实际切房前复核保存的身份。后继任务引用进入现有[导入资源重命名](../../MultiplayerHoeingAssistant/Services/ConfigTransferResourceReferences.cs#L47)和[计划 ID 映射](../../MultiplayerHoeingAssistant/Services/ConfigTransferMistletoe.cs#L110)；无法确定引用时提示并禁止执行，不按同名任务盲目替代。
- 联机批次受理时冻结完整有效完成动作：源、目标身份、跳转后的动作和任务修订；批次期间编辑只影响新批次。恢复原批次也必须使用原冻结值，而非新配置。
- [SnapshotBatchCompletionPolicy](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.OnlineBatch.cs#L385)的 `Source == "manual" && !UseCompletionActions` 分支必须整体关闭切房目标及后继动作。**自动上线批次的 `UseCompletionActions` 也可能为 false**，仍应使用房间绑定动作；不得对所有批次统一按该布尔开关禁用。纯普通一键自定义/快捷任务即使取得协调批次成功，也不等于实际联机锄地完成，不触发新切房；原三种完成动作保持原语义。
- 同版成员卡片、房间管理摘要、远程完成动作及一键锄地确认明确展示新动作和目标/后继摘要。手动开批勾选完成动作时，如果确认内容或受理时任一侧包含切房，比较确认的动作身份/修订与执行端实际冻结的完整动作；不一致时提示重新确认，不允许确认甲→乙后静默执行甲→丙，亦不允许确认普通停止后隐藏切房。对原三种未涉及切房的动作不附加无关版本校验。服务端现有[开批校验](../../BgiCoordinatorServer/Services/RoomOperations.Batch.cs#L183)是该同版合同的窄接入点，不改变批次调度和离房准入。
- 统一升级直接采用明确的业务动作类型和同版必要字段；内部继续复用 `stop` 收尾语义，不为了旧版本增加转换层或能力协商。原远程绑定、定时、其他字段更新不覆盖完整切房动作；已有活动房间远程编辑保留原三种动作的显式设置能力，同版展示切房关系。新增任务编排配置由执行端持有；监控端使用后文约定的同 UID 定向查询和编辑协议，原有活动房间编辑不变。

### 4.2 自动切房的实际执行时机

当前服务端要求旧批次满足现有 `IsTerminal`/安全离房条件，才允许参与成员离房。同服务器其他房间也禁止旧未清理批次中的同 UID 加入新批次。A 本机做完后，如果 B/C/D 仍在收尾，A 可能需要等待。保留现有共同完成后离线队友按现有规则解除等待（`CompletionWaitReleased`）的规则，不额外要求每个离线端报告物理清理成功。

首版建议保留现有准入规则（不要求服务端为 A 提前放行）：

```text
甲房间整轮联机正常完成
    ↓ 核验本机绑定成功、权威批次成功、原停止授权有效
按现有 Stop 路径结清旧执行责任、接管票据及清理回执
    ↓ 释放本机旧批次；等待甲全队达到现有离房条件
复用现有真正切房事务（可取消、有界等待）
    ↓ 乙房间入房及就绪确认，应用乙独立配置
到达乙，旧房上线意图清除
    ├─ 待命：不额外启动任务
    └─ 执行指定任务：在乙当前上下文发起独立任务
           ↓ 可通过现有上线命令在乙上线
乙后续批次仍走乙自己的准备、联机接管和完成流程
```

如果将切房等待直接放进 `FinalizeLocalCoordinatedBatchAsync` 的收尾动作，切房又在等待 `_activeBatch`、接管票据和计划表接管责任解除，会形成循环等待。以 `RetryCoordinatedCleanupAsync` 确认清理及 `CompleteCoordinatedCleanup` 移除 `_activeBatch` 为分界，在旧批次移除前登记一次独立后续动作，释放后才派发并复用 `SwitchAssistantRoomCoreAsync`。等待甲队友收尾复用现有可取消长等待（目前长等待上限 6 小时），而非普通切房 45 秒预算；入房等网络操作仍沿原有有界时限，不修改手动切房默认等待。

**成功判据：**

- 本机有实际联机任务的完成证据、全部冻结绑定正常成功且无累计本机任务错误，同批权威终态为正常 `completed` 且无累计队友任务错误（`completed_with_task_errors` 不推进）。[CoordinatedHoeingEvidence.MatchesTerminal](../../MultiplayerHoeingAssistant/Services/CoordinatedHoeingEvidence.cs#L32)允许实际联机次数为零的普通任务成功，这一事实不能授权切房。
- 正常循环和清理补报两条路径共同保存同批权威完成事实。[清理补报](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.OnlineBatch.cs#L932)可能先于执行循环设置 `CoordinatedSucceeded`；不能只依赖该布尔值或 `CleanupConfirmed`。收到本机清理确认（或权威查询明确已清理）且成功条件齐全后，在同一登记边界确保后继只产生一次。查无旧批次本身只能结清旧责任，不能证明成功。
- 允许共享恢复后取得真实正常成功；不能把所有非空 Reason 当作失败（`shared_recovery` 可保留）。错误、取消、停止或未知不推进新动作。保留现有本机提前释放、共享恢复和原三种完成动作的终态语义。

依据：[MainViewModel.OnlineBatch.cs](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.OnlineBatch.cs#L891) · [MainViewModel.RoomSwitch.cs](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.RoomSwitch.cs#L193) · [服务端离房检查](../../BgiCoordinatorServer/Services/RoomOperations.ControlRoomMembership.cs#L225) · [批次终态](../../BgiCoordinatorServer/Services/CoordinatedBatchState.cs#L110) · [跨房准入](../../BgiCoordinatorServer/Services/RoomOperations.Batch.cs#L126)。

### 4.3 切换确认后的任务执行与乙房上线

后续任务是本机的新任务，不属于甲房间旧批次，也不是乙的联机绑定。只在切房业务结果明确成功、乙实际已就绪、目标身份与冻结快照一致、原停止授权仍有效时，使用现有相应类型的任务启动能力。

- 不复用甲已经释放的接管票据、批次 ID 或旧房远控上下文；不能将原完成动作内部的旧批次收尾方法直接再调用一次。复用任务目录解析、目标/起始方式校验、普通任务提交与计划表调度入口，为甲→乙登记独立后继意图。
- **后继实际发包也须受原授权约束。** [普通指定任务发包](../../MultiplayerHoeingAssistant/Services/CommandExecutor.cs#L1394)的幂等键来自远控上下文，未传原 `expectedStopVersion`；BGI 缺少该值会采用执行时的停止版本（[InstanceRequestHandler.cs](../../BetterGenshinImpact/Service/Instance/MessageHandlers/InstanceRequestHandler.cs#L924)）。仅针对新增动作，将冻结意图键、原 BGI 纪元及停止版本、任务修订、乙房间身份贯通准入和真实发包。即使甲内部按 Stop 收尾也必须捕获停止围栏。复用[保留回执启动能力](../../MultiplayerHoeingAssistant/Services/BgiExternalClient.StateContinuation.cs#L73)及结果查询，明确禁止在冻结/发送阶段自动补入共享接管票据。计划表复用继承停止授权的登记能力，不直接把新动作塞入仅支持旧 `RunSpecified` 批次的完成流程。
- 切房过程中不提前执行后续任务，不因通用 ack、BGI 收件确认或已入队而报告任务成功；区分待提交、已受理、运行、完成、失败、取消及未知。使用原意图标识及实际 jobId/runId 跟踪结果和已受理任务的停止，同一意图最多受理一个任务/计划，不因查询超时而重新取得授权或跨通道重发，不用提交成功代替运行成功。任务受理后由正常任务执行链持有责任，编排仅观察结果，不持有阻塞乙下一轮联机或乙→丙的锁。
- **执行指定任务不等于上线。** 例如「乙房上线前准备」配置组先跑日常，执行既有 `联机锄地上线` 动作并选择「当前登录房间（不切换）」；此时实际登录已是乙，无须再做一次切房。现有允许指定房间的上线动作也可显式选择乙，但它受实际配置组及房间动作链的上下文限制。编排页不替任务另行自动发送或重复发送上线。
- 如果任务没有安排上线命令，A 可以在乙做普通任务，乙自身未来的定时上线、手动上线、合法命令仍照常生效。等待人数及上线意图期限遵循原行为。不得在乙等待期间隐式沿用甲的上线意图。
- 乙满足条件开始联机时，普通任务是否让位、暂停、恢复或被停止，继续由现有 BGI 联机接管及乙的完成动作决定；切换后的任务不得持有会阻止乙联机开批的旧批次/切房锁。尤其不能等待整个后续任务运行结束才释放甲的批次责任，否则任务自己触发乙上线后可能互相等待。
- **乙开批与后继启动竞争：**[切房事务](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.RoomSwitch.cs#L405)提交后会派发缓存命令及异步核对乙的批次，单看 BGI 空闲不足以判定可以启动新任务。仅为编排后继在现有受理/接管选择边界做短暂协调：以乙已经成立或正在受理的批次及用户新安排为优先；尚未获准且发生竞争时撤销后继，并显示原因。已受理并明确纳入接管对象的任务才交由乙正常让位/恢复。防止[计划表等待停驻](../../MultiplayerHoeingAssistant/Services/TaskCenter/WorkflowRunner.cs#L832)遗留未受理的编排计划，在乙选择停止或切丙后又被唤醒。保留所有其他正常任务的现有仲裁和定时行为。
- 乙的联机批次随后正常完成，应用乙的完成动作（例如乙→丙）；不重复执行甲→乙附带的任务。若乙明确配置恢复原任务，仍按已有恢复语义执行。

这些补充仅保护新切房和后继启动确实触发的边界，不建立一套新的上线调度器，也不改变普通手动、定时、其他配置组的正常上线逻辑。

### 4.4 停止、失败、重启及配置变动

- 把待切房及后续任务的授权绑定原批次 ID/代次、原控制上下文、源和目标真实身份、原 BGI 停止版本。不得在切房后重新采集较新的停止版本来绕过用户在甲按下的 F11。`MarkSettled()` 会释放旧批次恢复信号，需在旧批次释放前明确登记自己的可撤销后续动作；派发只一次。
- 原批次未结清时按既有长等待规则；目标删除/改址、来源身份变化、新的手动切房或执行意图产生、当前有普通停止/重置、已有远控或批次争用时，按原互斥与身份复核机制撤销尚未提交的旧后续动作，不抢占用户新安排。甲等待队友时也要识别新本机任务，不能让旧编排在用户后来开始的任务中途切房。该限制只针对自动编排，不改变现有手动/BGI 独立切房允许普通本机任务继续运行的语义。F11、停止、重置及用户取消可以撤销未提交部分。
- 现有 `room-switch-pending.json` 仅在首次离房前保存记录，旧批次恢复记录在结清后不再提供执行授权。只需新增本功能的一次在途意图/状态（原批次及身份、冻结目标和任务、原停止授权、确认进度及实际 jobId/runId）和最近切房信号截止依据，复用已有切房事务、任务台账及结果查询。不得在甲清理期间提前设置现有未确认切房标志，以免反向阻断清理；不引入通用持久化队列、自动重放或第二套恢复引擎。
- 明确拒绝/失败：不启动后续任务，按已有切房恢复原房间或显示断线。离房、入房或就绪结果未知：先使用已有待核对入口，后继不盲目执行。
- **乙已确认就绪但后续任务启动失败或运行失败**：保留乙为当前房间，分开显示「切房成功、后续任务失败」，不得自动切回甲、重跑甲锄地或偷偷改为其他任务。后续任务已提交但结果未知时先核对，避免重发。
- 重启：房间配置、连线和最后确认的房间保留；尚未确认的切房/任务提交按已有恢复规则标记中断或待核对，无法证明授权及执行结果时不自动重放。若切房和后续任务已完成，不能由于重复回执再次执行。
- **跨服务器停止代次归属问题已由源码核实。** 服务端[批次代次](../../BgiCoordinatorServer/Services/RoomOperations.Batch.cs#L12)在各进程独立生成，助手按全局 `_resetFenceGeneration` [过滤开批](../../MultiplayerHoeingAssistant/ViewModels/MainViewModel.OnlineBatch.cs#L437)，甲的高位停止可能错误拒绝乙合法低位批次。因为本功能承诺覆盖已保存的跨服务器房间，实施时只需在助手已有控制上下文中按已确认服务器/房间隔离该围栏，过滤迟到旧回调；回到甲仍保留甲的原无效批次屏障，不重置全局停止授权，也不改服务端代次算法。
