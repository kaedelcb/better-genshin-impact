# 槲寄生后续施工：辅助设施接入计划

用户于 2026-09-27 授权直接接入：设施现在一次性进入计划，后续由施工执行者调用，
owner 不用记住导入时机、填清单或运行命令。工具入口：[workflow.py](../../tools/mistletoe/workflow.py)，
格式与操作：[README](../../tools/mistletoe/README.md)。本文件不改变任何产品完成状态。

## 执行规则（后续批次默认携带）

1. 先建立本批 Goal（结果、约束、完成判据），再核对权威计划、现场代码、工作区和其他
   在途任务。本批范围及回归以权威合同为准，不能根据工具支持哪些格式反过来裁剪范围。
2. 开工时执行者建立 `_workflow/<本批>/manifest.json`，登记实际源码/测试/合同/关键依赖、
   必要证据及其等级、运行条件和失效条件。已有材料先审计，避免重复施工；不得将事后
   当前哈希伪记为旧测试的运行版本。文件由执行者维护，不向 owner 索要填写。
3. 回归后使用 `audit --stage evidence` 整理全部执行结果、差集及已有突变记录，生成证据索引。
   索引保留 component/runtime 等边界、失败和未验证项；不能自动替代新的回归或宣布验收。
4. 每次会诊前执行者生成 `audit --stage review` 材料，随后 `verify`，并运行会诊渠道自身预检。
   预检错误由执行者修复，材料不能自动删减。语义完整性、同子批累计预算、重要/必改闭环、
   会诊模型/强度及规定点位继续按原规则。没有发出请求的本地预检不计会诊，已发失败/超时仍计。
5. 收口前使用 `audit --stage closeout` 和 `verify`，逐项对照权威完成判据，包括原有针对性、
   完整回归、同条件基线、突变、声明面和实机要求。报告成功只证明机械核验，不能开启生产门。
6. 工具或材料有问题，执行者自行修复或登记并完成同等人工核验；不能让 owner 到该步骤再导入，
   不能为了工具变绿排除失败，也不因此额外重复全部产品构建。真正需要 owner 的业务/门禁裁决
   按既有流程批量汇总。此设施不新增会诊点、不取消既有点、不降低模型强度。

### 超大会诊材料的通道选择

- **常规会诊仍使用既有 GPT 会诊工具。**先固定审查快照并通过 `audit --stage review`、`verify`，
  再按原合同提供精确文件和问题。只有本次必需的源码、原始执行证据和差异在去重、定向分包及
  发送前预检后仍受会诊工具的文件数、单文件或总量限制，执行者记录超限项与预检结果，
  **自行触发该次会诊的本地回退**，不等 owner 逐次指示：用独立 GPT/Codex CLI 进程在
  `-s read-only` 模式按精确路径读取固定快照。只在原合同允许且不割裂重要问题证据时分包；
  不把网络、服务或报告回收失败推定为材料超限，先按实际错误排查。材料恢复常规规模时
  仍用原工具；不能把一次回退写成永久停用 GPT 会诊工具，也不能为了适配上限删去重要/
  必改项要求的原始证据。
- 本地回退保持同一子批、固定模型与强度、审查问题和已验证快照；只读进程不得改代码、读取
  真实 `User` 或无关私密文件，也不得由施工主执行者自审冒充独立会诊。记录回退原因、精确路径、
  源码/证据哈希与审查前后状态，并保存 CLI 事件记录、退出码和独立报告；无报告不算通过。
  发送前确认本地进程能使用本批规定的模型与强度、且子批仍有会诊额度；不能满足时登记阻断，
  不降配、不绕过预算。报告须核对实际读取范围与快照一致，发现漂移则不能用作该版本结论。
  跨工具累计会诊请求不重置，已发送失败/超时仍按原预算计数；预算用尽而重要/必改未闭合时
  保持阻断并走 owner 检查点。只读直接读取能避开附件体积上限，但不能保证模型上下文或服务
  不再失败，不能因此减少规定会诊、回归或生产门。

## 每个后续批次的默认提速工序

- 每个新批次使用 `schema_version: 2` manifest，改动前运行 `workflow.py begin` 固定开工版本、
  工作区、范围及已有材料。执行者逐项核对已有结果与适用版本，登记可复用证据或不复用理由；
  不重复做已由同条件证据证明的工作，也不拿旧结果冒充当前回归。纯文档批次只做适用的文档
  核查；产品行为验证、会诊和实机要求仍按权威计划。当前在途 SB21-4 的精确 v1 批次保留兼容。
- 新代码批次**改代码前**，在本批 `_workflow/` 写出状态、并发、
  故障三类风险矩阵，逐行列入口/场景、预期、是否关键；运行 `workflow.py begin` 固定开工 HEAD、
  工作区状态、源码清单及原始矩阵。发现新路径可追加行，原始行的场景与预期不得静默改窄。
- 主执行者先评估是否有独立只读问题适合 1–2 个子 Agent 并行核查。使用时固定开工版本、
  开工源码哈希、问题和报告，主执行者在送审前复核版本漂移；不用时写一句具体理由。子 Agent 不共享写权，
  不同时操作测试产物或真实运行环境；核心状态链保持唯一代码写者。
  有实际收益才派出，例如固定源码上的调用链/影响面核查、测试失败与 testId 差集归因、既有
  交付证据完整性核对；不为凑并行数量拆任务。Runner、受理账、物理槽、跨端授权与迁移激活
  等共享状态链不得由多个子 Agent 同时改代码；worktree 文件隔离不代替身份/事务语义审查。
  版本持续漂移或协调成本超过收益时串行推进，不承诺按 Agent 数量同比缩短工期。
- 已知问题与关键反例尽量同批实现、做有判别力的反向突变及适用回归。送审时矩阵各行须有
  可索引的测试/运行反例与具名 testId；关键行须绑定有效突变。上轮必改/重要发现逐项保留原级、
  同一修复批归集候选修复证据；仍未形成候选修复的项目走 owner 检查点，不伪称本轮可验证闭环。
- 纯文档批次也须登记复审轮次并集中处置上轮重要/必改发现；不需要为文档伪造状态/并发/故障
  矩阵、TRX 或产品突变。主执行者继续按文档范围校对权威引用和语义。
- `workflow.py audit --stage review` 对新批次拒绝缺开工快照、结果复用评估或子 Agent 决策；
  对新代码批次再拒绝缺矩阵维度/反例/证据引用、
  子 Agent 评估、上轮重要发现批量处置的材料；`verify` 再查源码与材料漂移。只有两步通过，
  且会诊渠道自身预检通过，才发送该稳定快照。失败先本地修正，**不**拿失败材料消耗会诊请求。
  现有在途 SB21-4 的 v1 manifest 被精确列为兼容项，不热改其 Goal；其他新代码批不能选 v1 绕过。
- 工具核查的是已声明范围的机械完整性，不能独立证明 `begin` 确实先于代码修改、矩阵已穷尽
  所有语义、行的关键性判定正确或执行者没有隐瞒上轮发现。全部不适用会被拒绝；全部非关键须
  书面说明，但两者的业务合理性仍由主执行者与审查者判断。子 Agent 结论同样须人工复核；
  也无法阻止执行者绕开工具直接联系会诊渠道；这些仍须主执行者和审查者核实。
  不改原定会诊点、模型强度、反例/回归、实机、owner 裁决或生产门。

## 交接与无感使用

- 生效点：后续新批次及现有任务完成后的自然接力。**不向正在施工的会话注入指令**，不要求
  当前活动 Goal 重启，不修改活动台账、R5 设计合同、声明面清单或生产代码。
- 后续开工提示词/交接稿必须在唯一完整的 `/goal` 代码块内带上本文件入口，要求执行者自行
  建立本批 v2 manifest、核对已有结果、评估子 Agent；代码批次另建开工矩阵，均调用
  begin/audit/verify、修复错误及保留全部
  原质量门；不得要求用户另发正文/安装指令。
- 新工作区由执行者核对工具和本文版本。若独立 worktree 未包含尚未提交的设施，按交接列明的
  权威工作区与哈希精确读取或同步**本设施文件**；不覆盖当地改动、不复制整份用户 AGENTS，
  不要求 owner 手动导入。跨机器材料不可用时如实处理外部阻塞，不能虚称已自动生效。
- 当前项目 AGENTS 与 `.agents/` 是被 Git 忽略的本地入口；总计划和本文件作为可版本管理的
  入口补充。执行者必须实际读取，不能假定模型已自动热加载。
- 不增设插件、Stop 钩子、心跳、定时器、自动发消息或创建会话；这是执行流程内的工具调用，
  不是后台服务。新代码批调用本工具时有机械拒绝门，**不是**会诊渠道的不可绕过拦截器；
  未读取本入口的会话不会自动受其约束，交接必须带上入口与上述执行要求。

[并行成果索引](mistletoe-parallel-deliveries.md) 是本计划后续入口的必读材料。每个新批次/自然接力选择剩余施工前，执行者定向核对索引中的独立任务、报告和提交；在安全窗口由主线唯一写者回收并刷新计划，集成后按实际版本验证。后续完整 Goal/交接携带未消费成果来源，执行者自行获取缺失文件，不让 owner 搬运。独立完成不等于主线集成或正式验收；索引是发现/核验流程，不是即时自动回写或后台同步服务。


## 并行成果的自动接收责任（2026-09-27 owner补充）

后续执行者在开工、自然边界和收口时读取 [成果索引](mistletoe-parallel-deliveries.md)、
[机器台账](mistletoe-parallel-deliveries.json)，运行 `tools/mistletoe/deliveries.py` 发现漏登记和版本漂移。
到对应目标集成批，把接收、适配、回归和回填提交/证据纳入完整Goal，在安全写入窗口自行完成既有授权范围内的集成。
owner无需记住成果、另发提醒、手动cherry-pick或搬文件。业务裁决、资源缺失、实机及生产授权仍按原门禁处理。
独立收口方交出登记信息，主线自然边界补账；未知报告必须核验，不把发现当完成。
若工具/材料缺失由执行者自行获取核验或等效检查，不降低质量门、不即时改活动Goal、不自动向其他会话发消息。
