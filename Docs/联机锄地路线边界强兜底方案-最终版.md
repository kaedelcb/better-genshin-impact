## 1. 目标与保证边界

为正常推进、复苏、战斗、传送、卡点、断线等不同情况提供统一恢复出口，避免逐个案例增加放行条件。

硬规则：服务端没有确认当前路线边界已完成之前，客户端不能执行下一条路线。恢复成功后一起继续；无法确认全员安全恢复时停止整队，不静默缩减为三人继续。

“逻辑路线边界一致”不等于“游戏内空间位置相同”。第一版保证相同执行计划、相同下一路线和旧执行器已经退出；若要求实际传送到同一位置，必须另定义经过路线校验的公共传送点及物理到达确认，不能把游标赋值描述成实际汇合。

## 2. 当前实现依据及已知限制

- AutoHoeingTask 中的 route_sync_done 位于路线列表同步后、路线验证前，不是每条路线结束屏障，也不能直接当作新协议的启动授权。
- 多世界 round_end 同步属于轮末流程。
- CheckSyncAtRouteStart 返回的 Wait/CatchUp 没有在调用方形成强制等待。
- 外层路线是 foreach 枚举；修改 count 并 continue 不会改变枚举的实际目标。不能复用这段代码声称已经具有可靠的指定路线跳转能力。
- 服务端 FightingStatusChangedAsync 当前仅记录日志。心跳证明连接存活，不证明任务在推进。
- 旧集体跳段仅按进度和 ArrivalSet 选人；服务端筛选名单与实际组广播接收者不是一回事。组广播会送到整个组，必须显式验证客户端对象筛选，不能将服务端 Required 名单当作定向发送证据。
- 当前集体跳段确认实现存在待复核项：下一段意图在实际到达前回报成功；失败回报也可能进入 AppliedAll；目标进度未强制匹配；段首抛出点与 catch 的覆盖范围；吞异常导致回报无法重试；取消 Gate 生命周期。不能将它直接作为可靠的锚点执行基础。

## 3. 术语及身份

锚点表示“旧路线执行已结束，准备进入下一路线”，不是允许提前执行目标路线。

身份字段：

```text
sessionId：服务端生成，区分房间实例，不能仅用可复用房间码
worldEpoch：当前世界代际
planId / planHash：冻结的逻辑路线计划
phaseId：正常执行与协作重跑隔离
anchorSequence：服务端单调编号
commandId：本次恢复动作编号，重发保持不变
revision：服务端状态版本
playerUid：参与者身份，重连不能按旧 connectionId 计数
```

AnchorId 由服务端生成。参与 UID 集合在启动时冻结，重连仅更新传输连接绑定，不能让旧连接与新连接算两人。

## 4. 状态机

每个会话阶段最多一个活动边界；终态必须保留可查询记录，不能广播后立即删除。

```text
Enrolling → Running(N) → CollectingBoundary(N)
                              ↓ 超过等待预算
                           Pulling
                              ↓ 旧执行器退出
                           WaitingReady
                              ↓ 全部成员准备完成
                           Released(N+1)

任意不可恢复故障 → Stopped
最后路线完成 → Finished（仍需全员收口）
```

首路线必须在计划校验、能力协商、全员加入新会话后获得启动许可。最后路线不能因没有下一路线而绕过全员完成确认，避免提前关房或进入重跑。

## 5. 三个确认的精确定义

| 状态 | 允许确认的条件 | 不代表什么 |
|---|---|---|
| PullApplied | 对应 commandId 的旧路线子任务已退出并完成清理，目标游标已准备 | 不代表完成被跳过的路线，也不代表角色已经移动到目标位置 |
| AnchorArrived / Ready | 成员在共同计划的同一逻辑边界停止，目标合法，没有旧输入任务残留 | 不允许开始下一路线 |
| AnchorReleased | 服务端确认固定参与者全部 Ready，发布下一路线授权 | 不能被普通 AllArrived 替代 |

正常完成成员也必须提交 Ready，不是只有被拉成员上报。失败不计入 Ready；Stop 策略下不使用 Arrived ∪ Removed 作为放行集合。

## 6. 客户端执行方式

### 6.1 外层游标

锚点模式使用显式路线索引或独立路线调度器，不再用 count 修改 foreach 的假跳转。普通模式路径保持原行为。

```text
取得 Running(N) 授权
→ 执行路线 N（独立子任务取消令牌）
→ 收集真实执行结果
→ 等待子任务完全退出及输入清理
→ Report + Ready(N)
→ 轮询/事件取得 Released(N+1)
→ 更新游标并执行下一路线
```

被协调跳过的内容必须记录为协调中止/未完成，不能计入正常完成或擅自清掉待重跑记录。completedCount、skippedCount、count、remainingEstimatedTime、守护进度、CD/黑名单和路线持久化均须逐出口保持一致。

### 6.2 拉取动作

Pull 指向服务端已经创建的当前边界，不允许客户端自行选择更远路线。收到后只中断当前路线子任务，不取消整个会话。

```text
校验身份、计划、命令和当前阶段
→ 保存请求（不覆盖在途不同命令）
→ 取消当前路线子任务
→ await 原任务退出及 finally 清理
→ 若需要复苏，由执行线程串行完成恢复
→ 准备下一路线游标，尚不运行目标路线
→ PullApplied
→ Ready
→ 等 Released 后执行
```

不能在 SignalR 回调里直接传送、注入键鼠或启动第二个 PathExecutor。不能仅靠战斗结束后的单一消费点：长战斗、普通同步等待、传送、拾取等都须具有有界退出路径。到期仍无法退出时停止整队，禁止并行启动替代执行器。

## 7. 独立协议

新增独立协议域，不复用普通 AllArrived、StartRoute、Abort 或 CollectiveSkipAppliedAll：

```text
command: sync.routeAnchorEnroll
command: sync.routeAnchorReport
command: sync.routeAnchorPullApplied
command: sync.routeAnchorPullFailed
command: sync.routeAnchorArrived
command: sync.routeAnchorCancel
query:   sync.routeAnchorState
event:   sync.routeAnchorChanged
```

状态查询与所有变更响应返回同一权威快照，包含身份字段、revision、阶段、当前路线、下一路线、各 UID 状态、恢复命令及截止时间。事件只负责通知尽快查询，不能成为唯一正确性来源。

报告必须绑定当前已授权路线，不能依赖客户端自报 completedRouteIndex 推进服务端。相同 commandId 重发只补回报或返回当前状态，不能重复执行。旧代际消息拒绝并记录，不应仅因为收到旧消息就停止当前正常会话。

## 8. 时间和容错

以下数值是待配置适配及实机验证的初始建议，不是现有可靠常量：普通边界等待 90 秒、战斗宽限 120 秒、复苏宽限 180 秒、传送宽限 60 秒、恢复命令最多重发 2 次。

- 状态有单独进入时间与单调进度序号；重复心跳和重复状态报告不能无限刷新宽限。
- 存活与进展分离。允许活跃任务在对应预算内自然完成，但必须有会话级绝对截止时间。
- 战斗等待预算必须兼容房主实际 FightTimeoutSeconds，不能固定 120 秒误判更长的正常战斗。
- 重发不是重新执行：命令身份不变，回报可重复。
- 回报方法必须返回可核验响应或抛出失败，不能吞网络错误后登记为已确认。
- 客户端定期查询当前状态，建议 2 秒，网络调用使用独立短超时和会话取消令牌。
- 服务器失联时客户端停止新路线推进；超过会话安全期限本地停止，不等待一帧永远收不到的 Stopped。
- 停止通知丢失、服务端重启、房间码复用、新旧连接乱序都必须通过会话身份与查询恢复处理。

## 9. 与现有功能的隔离

### 9.1 普通同步与旧集体跳段

普通路线内同步规则不修改。锚点模式激活时，旧集体跳段的主动命令、已武装定时器和客户端迟到信号必须统一隔离，不能两套控制器同时推进。锚点关闭时走原行为，但不得在活动恢复事务中直接切换。

### 9.2 战斗与复苏

新增活动观察记录优先放在新会话状态里；不要为了锚点全局重定义既有 PlayerStatus 或 IsAbnormal。战斗/复苏观察只能提供等待依据，不能自动证明 Ready。锚点不改写普通恢复 TargetProgress。

### 9.3 掉线与取消

保留已有重连宽限和离线终止语义。固定参与者失效时走 Stop，不因心跳人数减少缩小分母。用户取消优先立即停止本机，再尽力通知服务端；不能等待网络回执才响应取消。

### 9.4 多世界与协作重跑

正常路线完成必须先完成 Finished 收口，再移交现有重跑/换世界流程。不得同时运行两套路线释放权威。重跑是否共享新调度器必须在实现前读取现有 CooperativeRerunSession/RerunExecutionState 全部阶段后确定适配，不可简单加 generation 后声称兼容。新世界必须创建独立会话，旧回调无权改变新会话。

### 9.5 路线变体

路线索引必须来自冻结的共同逻辑计划，不能假定同一个本地文件名或相同序号代表同一条路线。计划需携带逻辑 ID、执行顺序及各成员已验证的本地映射；不能把合法变体差异直接判为哈希错误。

## 10. 能力协商和发布

增加明确 capability，例如 hoeing.routeAnchor.v1。只有服务器和全部参与 BGI 客户端都支持、计划一致且完成入会确认时才能激活。部分客户端支持时禁止半启用，任务开始前明确失败或整房间选择旧模式。

首版 EnableRouteAnchor 默认 false；开启必须由房主在会话开始时固定，全员使用同一个 effective mode。配置开关只在下一会话生效。活动会话不能通过关开关强行清掉屏障后放行。

“回滚”是停止本轮后下轮选择旧模式，不是运行中无条件切换，也不是保证所有旧代码自动正确。此前新增确认代码需要单独复核，不能盲目作为可信基础。

## 12. 必须验证的性质

1. 未释放不运行下一路线；正常成员和被拉成员均适用。
2. 只有固定参与者全部 Ready 才能 Released；失败和离线不算成功。
3. 旧执行器退出前不能报告 Applied，也不能启动新执行器。
4. 同命令重复执行至多一次，但重复回报可安全补发。
5. 旧消息、乱序、丢事件、重复连接、重启不会越过屏障。
6. 无人到达路线结尾时，会话仍通过独立看门狗获得有界恢复或停止，不能等第一条 Report 才启动监测。
7. 首路线、最后路线、单路线、空计划、调试起始索引均有明确终态。
8. 被协调略过的工作不伪造完成，待重跑记录保留。
9. 用户取消立即生效，失败通知丢失也会本地停止。
10. 关闭模式下普通同步、FastReport、单机及原执行结果保持一致。

四端测试必须运行真实协调客户端和可注入的路线执行桩，而不是只向 Room 手工填 ArrivalSet。覆盖 A 复苏、B 结束、C 战斗、D 等待，断言执行游标、实际任务退出、共同 Ready 和 Released，而不仅仅断言广播出现。

## 13. 实施顺序与交接门槛

## 附录 A：阶段 0 只读基线核查结果（已执行，2026-09-16）

核查对象：`BetterGenshinImpact/GameTask/AutoHoeing/AutoHoeingTask.cs` 路线循环约 3560–4050 行，以及 `RouteExecutionEngine`、`PathExecutor` 对外层索引的影响面。

### A.1 路线索引与计数语义

```text
count = 0                                   （3566）
startIndex = max(0, StartRouteIndex - 1)    （3575）
currentRouteIndex = startIndex + count      （3663，每轮迭代开头计算）
count++                                     （3742，进入路线执行前自增）
```

结论：

- 路线"序号"由 `count` 决定，不由 `foreach` 枚举器决定；
- 因此"刚执行完的那条路线"的索引是 `startIndex + count - 1`（代码 3861 行已有同款用法）；
- 锚点提交边界时必须使用该值，不能用 `currentRouteIndex`（它指向下一条）。

### A.2 路线循环内全部出口（已逐一登记）

| 行号 | 出口 | 语义 | 对索引/计数的影响 |
|---|---|---|---|
| 3649 | `continue` | 中断重对齐 `count = startRoute - startIndex` | 只改标签，**不改变枚举项** |
| 3683 | `continue` | RouteEnforceSync 同款跳转 | 同上 |
| 3717 | `return` | `RouteSyncDecision.Abort` 结束整轮 | **直接离开方法，绕过轮末汇总** |
| 3739 | `break` | 协调停止 `IsExitTriggered` | count 已自增 |
| 3748 | `break` | 限时区间 | count 已自增 |
| 3759 | `continue` | CD 跳过（仅单机） | skippedCount++ |
| 3775 | `continue` | 关键词过滤跳过（仅单机） | skippedCount++ |
| 3885 | `continue` | 路线被跳过后的"不跳过重试" | count 已自增，实际已前进（与注释不符，属既有隐患） |
| 3972 | `break` | 连续跳过达上限 → 会话级异常退出 | 关房/Offline + Degrade |
| 3976 | `continue` | 联机路线被跳过 | skippedCount++ |

### A.3 对锚点设计有约束的既有事实

1. **不存在真正的"跳到指定路线"能力**：`count = target - startIndex; continue;` 仅重命名标签，枚举仍按原顺序前进 → 方案第 2 节的告警成立；Pull 必须引入真正的索引驱动循环，不能复用该段代码。
2. **路线完成上报只覆盖一个出口**：`RouteSyncCoordinator.ReportRouteCompletion` 仅出现在 `FullyCompleted` 分支（3994），跳过/异常/限时/协调停止出口均不经过 → 锚点 Ready 收集必须覆盖**全部出口**，否则必然漏报。
3. **存在绕过统一收口的出口**：3717 的 `return` 直接离开方法 → 锚点收口不能依赖循环末尾，必须用 `try/finally`。
4. **协作重跑使用冻结计划索引**：路线身份取自 `cooperativePlan.Manifest.OriginalIndex`（3828），完成判定走 `execResult.CooperativeOutcome`（3979）→ 锚点路线身份必须来自该冻结计划，不能用本地枚举序号（与正文 9.5 一致）。
5. **多世界与轮末**：轮末 `SyncRoundEndAsync` + `LeaveCurrentWorldAsync`，新房间天然 `IsStarted=false` 需重新 `MarkRoomStarted` → 新世界必须新建会话，旧回调不得影响新会话。
6. **取消路径**：3741 `_ct.ThrowIfCancellationRequested()`；3736 先判 `IsExitTriggered` 再取消 → 用户取消与协调停止是两条不同路径，锚点取消通知必须与二者都区分。

### A.4 阶段 0 结论

锚点实现不能建立在"路线循环末尾统一收口"的假设上，必须：

```text
进入路线前取得授权
执行路线（独立子令牌）
所有出口归一到一个 finally 收口
提交边界 → 等 Released
```

正文第 6 章的 `while(routeIndex)` 改造确认为**必要**，不是可选优化。

### F.2 门控调用点的选择（与附录 A.3 的关系）

附录 A.3 曾要求"用 try/finally 把全部出口归一"。实际接线改为**在路线循环的公共入口（时间限制检查之后、路线执行之前）做一次门控**，
理由是：门控的目的是"**进入下一条路线之前**必须拿到放行"，因此只有**会走到下一次迭代**的路径需要它；
`break`（协调停止/限时/连续跳过达上限）与 `return`（RouteSyncDecision.Abort）都是**结束本轮**的出口，
不存在"进入下一条路线"，无需边界收口。这样避免了在 10 个出口逐一插桩带来的回归面。

跳过的路线（CD/关键词/联机路线跳过）不需要单独插桩：其 `continue` 会让下一次迭代的门控自然以 `ResolveOutcome(上次快照, 当前计数)` 提交为 `skipped`。

### F.3 门控语义（不可绕过）

```text
未启用（配置关 / 单机 / 未入房 / 服务端无能力） → 直接 true（完全不发锚点协议）
首条路线（currentRouteIndex <= startIndex）      → 直接 true（轮次起点由 route_sync_done 覆盖）
同一边界已提交过                                 → 直接 true（幂等，不重复提交）
调用 CompleteBoundaryAsync：
    Released  → 记 _routeAnchorLastBoundary，继续
    Stopped / Failed / Cancelled → 记错误日志 + _stopReason + _sessionTerminated + 取消联动令牌 + break
```

`effective mode` 在**进入路线循环之前**一次性固定（`EnsureRouteAnchorInitialized`），运行中改配置不影响本会话（方案第 10 章）。

## 附录 K：跨轮状态复位与订阅释放 + 一次文件损坏事故的恢复（2026-09-16，第十一轮）

### K.1 修掉两个我此前引入的真实缺陷

**缺陷 1：门控从第二轮起会静默失效（严重）**
`_routeAnchorLastBoundary` 与锚点客户端都是**轮内**状态，但字段挂在任务实例上跨轮复用。
第二轮进入路线循环时，边界索引 0..N 全部 `<=` 上一轮的最大值 →

→ **整轮都不再提交边界、门控形同不存在**（且没有任何日志提示）。

## 附录 N：Pull 跳转判定固化（2026-09-16，第十四轮）

### N.1 本轮定位

阶段 4 只剩两步：**Pull 真跳转**与**正在执行子任务的取消**——两者都要改生产路线循环的运行时行为，
是全计划风险最高的一步（第十三轮已把循环改成索引驱动，为它铺好路）。
本轮**不接线**，而是把"接线时最容易写错的部分"固化成可测纯函数，使下一轮的接线变成机械动作。

### N.2 新增（`RouteAnchorJumpDecisions`，客户端纯函数）

| 函数 | 契约 |
|---|---|
| `CanJump(current, startIndex, target, routeCount)` | 目标必须在 `[startIndex, routeCount)` 内，且**严格向前**（向后跳=重复执行已完成路线，非法）；越界/相等/负值一律不跳 |
| `ResolveLoopIndexForJump(target)` | 必须写 `target - 1`：外层循环 `for(...; routeIndex++)` 在 `continue` 后会自增一次，写 `target` 会**跳过目标路线（漏执行且不补跑）** |
| `ShouldReportPullFailure(canJump)` | 不能跳必须**如实回报失败**，交服务端强兜底整队停止；禁止静默继续跑旧路线 |
| `ShouldAbortCurrentRoute(current, target)` | 一旦可跳就必须先中断当前路线（目标严格向前） |

关键设计取舍：这里**不判断**"是否在战斗中/能否中断"——那属于执行阶段职责
（不可中断时必须回报 `PullFailed`），避免把一个安全默认塞进判定函数而掩盖真实失败。

### R.2 新增 `RouteAnchorPullExecutor`（客户端）

```csharp

```

固定顺序（方案 §6.2，不可调换）：

```text
1. 无待执行命令            → NoCommand（不发任何消息）
```

## 附录 T：阶段 4 最后一步——Pull 接线（路线边界版，2026-09-16）

### T.1 接线内容

在索引驱动的路线循环顶部、**边界门控之前**新增 Pull 消费块（`AutoHoeingTask`）：

```csharp
if (_routeAnchorEnabledThisSession && _routeAnchor != null)
{
    var pullExec = await new RouteAnchorPullExecutor(_routeAnchor).ExecuteIfPendingAsync(
        routeIndex, startIndex, groupRoutes.Count,
        abortCurrentRouteAsync: _ => Task.FromResult(true),   // 边界处无路线子任务在跑
        ct: _ct);

    if (pullExec.Result == RouteAnchorPullExecutionResult.Applied)
    {
        routeIndex = pullExec.RequiredLoopIndex;
        count = pullExec.TargetRouteIndex - startIndex;   // 维持 currentRouteIndex = startIndex + count 不变量
        continue;
    }
    if (pullExec.ShouldStopRound) { 记 _stopReason + _sessionTerminated + break; }
}
```

### T.2 本轮采纳的安全取舍（必须明确记录）

**本版在"路线边界"消费 Pull，不中断进行中的路线。**
理由与代价：

- 好处：**完全避开**"取消正在执行的路线子任务"这一类高风险语义（重复/漏执行路线、输入未清理仍在按键），
  无需引入子令牌、也无需等待 `RouteExecutionEngine.ExecuteRoute` 真正退出。接线因此只有十几行且零新增回归。
- 代价：恢复延迟 = 最多"当前这条路线剩余时间"。若成员正卡在同步点等待，会先由既有 120s 同步超时放行，
  再到路线边界消费 Pull；若该延迟超过锚点的等待预算，服务端会走强兜底 `Stopped`（**整队停止，而不是走散**）。
- 结论：这一版保证"不新增风险 + 不会走散"，但不保证"最快恢复"。**立即中断版**列为后续增强。

**顺序设计（已核对）**：先消费 Pull 再走边界门控。跳转后 `for` 自增恰好落到 `target`，
届时边界门控会对 `(target-1 → target)` 这个边界执行 `Enroll`（同边界幂等复用）+ `Report` + `Ready`，
与服务端锚点语义完全对应（被拉成员此前未提交过该边界，因此不会重复提交）。

**不变量修正**：跳转时同时修正 `count = target - startIndex`。
若只改 `routeIndex`，会破坏附录 A.1 记录的 `currentRouteIndex = startIndex + count` 不变量，
导致日志、进度上报（`AutoHoeingProgress.CurrentRouteIndex`）、守护计数与实际执行的路线错位。

## 附录 U：重连/重复上报健壮性 + 轮次收尾主动取消（2026-09-16，第二十一轮）

### U.1 修掉一个会在真实重连中误停整轮的缺陷

**问题**：`CompleteBoundaryAsync` 把"报告返回 null"一律当失败。
但服务端对同一锚点的**重复报告**会以 `Duplicate` 拒绝（这是正确行为），

**修复**（客户端，权威快照优先）：

```text
Report 返回 null
→ RefreshAsync 查权威快照
→ Released           → 返回 Released
→ Stopped            → 返回 Stopped
→ MyState ∈ {Reported, PullApplied, Ready} → 视为"已提交过"，继续走 Ready 与等待放行
→ 其它（含查不到快照）→ 仍返回 Failed（保持安全默认，不放宽真实失败）
```

## 附录 X：成员离开房间的快速停止（第二十四轮复查发现并修复）

### X.1 发现的问题

`RoomManager.LeaveRoom`（成员主动离开 / 心跳判死后被清理）会把玩家从 `room.Players` 中移除，
但锚点的参与者集合是按 UID **冻结**的，`EvaluateRouteAnchorAsync` 之前只做：
"取连接 → 取不到就 `continue`（不下发 Pull）"。
后果：该成员的状态永远停在 `Pathing`，`DecideRelease` 既不放行也不停止，
**整个队伍被拖到绝对截止（10 分钟）才会 Stopped** —— 与"有界收敛"直接冲突。

### X.2 修复

在分类循环最前面加一条判定：参与者已不在 `room.Players`（即已离开房间）→
**立即** `Stopped`（`LatestFailureReason = "member-left-room"`）+ 释放兜底定时器 + 广播 `RouteAnchorStopped`。
语义与强兜底一致：成员不可恢复 → 整队停止，而不是静默缺员继续。

### X.3 验证

```text
服务端 BgiCoordinatorServer.Tests：246/246 全绿（+2 例）
  · 参与者离开房间 → 立即 Stopped（不等绝对截止）+ 广播一次 + 兜底定时器释放
  · 已离开且同时"停滞"的成员不会被下发无意义 Pull（它已无连接）
客户端（Release，vstest）：744 总 / 730 过 / 14 失败（本轮未改客户端 → 集合一致）
编译 error CS = 0
```

### X.4 三轮复查的共同结论（值得沉淀）

第 11、23、24 轮连续发现的三个缺陷属于**同一类**：

```text
"我为锚点新增的状态"在某个生命周期边界上没有正确复位或识别
  · 客户端：跨轮未复位 → 第二轮门控静默失效
  · 服务端：跨世界未复位 → 第二个世界每轮被误停
  · 服务端：参与者离开房间未被识别 → 整队被拖到绝对截止
```

三者都不是逻辑判断写错，而是**生命周期管理缺失**。因此后续任何新增锚点状态，
都必须同时回答三个问题：**何时创建、何时复位、成员/轮次消失时如何识别**。

### Z.2 一轮正常锄地应看到的序列（2 人，20 条路线为例）

```text
客户端（每台成员都会打印一次）：
  [联机][锚点] 本会话 effective mode: Enabled=True（配置=True, 服务端能力=True），planId=plan-20-xxxxxxxxxxxxxxxx

每条路线边界（第 2 条路线开始前、以及之后每条）：
  客户端： [联机][锚点] 提交路线边界：{N} → {N+1}（completed）
```

## 附录 AA：审查发现的整合缺口——锚点未感知"协作重跑"（第二十七轮，**未改代码**）

### AA.1 事实（均来自代码检索，非推测）

| 事实 | 证据 |
|---|---|
| 服务端用 `RerunExecution.BlocksLegacyAdvancement` 屏蔽旧推进机制 | `RoomOperations.SyncPoint.cs` 4 处（496/577/784/799/823）、`HeartbeatMonitor.cs` 3 处 |
| **锚点代码完全不感知重跑状态** | `grep -c "RerunExecution" RoomOperations.RouteAnchor.cs` → **0** |
| 重跑阶段会阻塞旧推进 | `RerunExecutionState.cs:48`：`Preparing / Running / Finishing` 三者皆阻塞 |
| 客户端的锚点门控在**正常路线循环内**；Finished 收口在循环之后 | 门控：`TryPassRouteBoundaryAsync`（循环内）；收口：`TryFinishRoundBoundaryAsync`（第 4284 行，循环后） |
| 协同重跑会话在轮末流程建立 | `CooperativeRerunSession.StartAsync`（3170 / 3772 行） |

### AA.2 缺口描述

方案 §9.4 要求："正常路线完成必须先完成 Finished 收口，再移交现有重跑/换世界流程。
**不得同时运行两套路线释放权威**。"

现在的实际情况：

```text
领先成员 → 跑完循环 → Finished 收口 → 进入协同重跑（服务端 BlocksLegacyAdvancement=true）
落后成员 → 仍在正常循环里 → 到达边界 → 向服务端 Enroll/Report/Ready
                                        ↑ 服务端锚点对此毫无感知，会照常创建/推进锚点
```

即：**重跑窗口内，锚点与重跑两套推进机制可能同时活跃**——正是 §9.4 明令禁止的形态。
旧集体跳段有 `BlocksLegacyAdvancement` 保护，而新增的锚点没有。

### AA.3 两个候选修法（需完整上下文决策，本轮刻意不选）

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 重跑窗口内锚点让位（推荐）** | `Enroll` 在 `BlocksLegacyAdvancement == true` 时返回 `rerun_in_progress`（不创建/不推进锚点）；客户端把该拒绝识别为"本轮推进权归重跑"→ 门控**直接放行**（新增一个结果值，如 `YieldedToRerun`），而不是判 Failed | 与 §9.4 一致：重跑负责收口；落后成员不被误停 | 需新增一个等待结果值并调整 `AllowsNextRoute` 的放行集合（放行集合变大，须写清"仅此一例"）；需补测试证明不会放宽其它失败 |
| **B. 重跑窗口内锚点照旧** | 什么都不做 | 零改动 | 违反 §9.4；两套推进并存，可能出现"重跑要求 A 成员做某事、锚点要求它跳路线"的交叉指令 |

**我倾向 A**，但 A 涉及"放行集合"这一最敏感判定（`AllowsNextRoute`），
在上下文不足时改动它等于在最危险的地方动手——因此本轮只固化分析，不实施。

### AA.4 附带确认（本轮已核对，无需改动）

- 锚点门控**只在正常路线循环内**执行，因此重跑阶段本身不会被锚点门控阻塞；
- 轮末 `Finished` 收口发生在进入重跑之前，顺序正确；
- 因此缺口的唯一形态是"**落后成员在重跑窗口内提交边界**"，而非"重跑被锚点卡住"。

### AA.5 建议的下一步

1. 先按附录 Z 实机跑一轮**不含重跑关键词**的常规锄地，验证主流程；
2. 再开重跑关键词跑一轮，观察是否出现"领先成员已进入重跑、落后成员仍在 Enroll"的日志交叉；
3. 若出现交叉，按方案 A 修（届时需完整上下文 + 放行集合的专门测试）。

| 客户端 `CoordinatorClient` | 新增 `LastRouteAnchorErrorCode` + 纯函数 `ExtractAnchorErrorReason`（解析服务端统一格式 `route_anchor:<reason>`，非该格式返回空串、**绝不猜测**） |

### AB.2 关键正确性细节（本轮踩到并修正）

`BgiGatewayClient.InvokeCommandAsync` 在响应带 `error` 时**会抛 `GatewayErrorException`**，
而不是返回带 error 的信封。因此原因必须从异常的 message 里提取（最初写成读响应载荷，测试直接抓出来了）。
提取函数是纯函数并有 7 例参数化测试锁定格式（含"无关消息 → 空串"与 null/空串），
因为"是否让位"取决于这个值——**猜错会导致该停止时继续跑**。

### AB.3 放行集合的窄化锁定

新增测试用**枚举全量遍历**断言放行集合**恰好**为 `{Released, YieldedToRerun}`：
将来若新增结果值，不会被默认放行。同时另有 3 例证明其它拒绝（`config_disabled`、`capability_required`）
仍然判 `Failed` 并**不放行**。
