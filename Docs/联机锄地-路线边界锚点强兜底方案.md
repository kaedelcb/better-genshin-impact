# 联机锄地 · 路线边界锚点（强兜底）方案

> 状态：方案已确认（用户选择 A. 强兜底），待实施
> 目标读者：实施者（不需要再重新审查/推导，按本文执行即可）
> 前置：本轮已落地的「集体跳段 Applied 确认闭环」（SkipId + Applied + 专用异常）是本方案的"拉"通道前置件，**继续留用，不废弃**

---

## 1. 要解决的问题

### 1.1 现状（已核实，含位置）

联机锄地目前**没有任何"路线边界汇合点"**：

| 现存的"对齐"机制 | 位置 | 实际效果 |
|---|---|---|
| `route_sync_done` | `AutoHoeingTask.cs:3372` | **一轮只调用一次**（开跑前），轮次级锚点 |
| `round_end_{round}` | `AutoHoeingTask.cs:2732` | 仅**多世界**轮末，120s |
| 每条路线的"线路同步检查点" | `AutoHoeingTask.cs:3693` | **空转**：`CheckSyncAtRouteStart` 返回的 `Wait`/`CatchUp` 在 switch 里没有分支，只有 `SkipToTarget`/`Abort` 被处理 |
| 路线内局部同步点 | `PathExecutor` + 服务端 `ShouldBroadcastAllArrived` | 进度豁免 / 异常标记 / 集体跳段 —— 全靠"见招拆招" |

**后果**：中途一旦出现异常（复苏、战斗中、卡死、掉线、误判、跳过头、迷路…），没有任何地方会强制把大家重新捏回一起。
局部机制各自为政、互相干扰（已实测：健康的慢走玩家、正在战斗的玩家、刚复苏跳段的玩家都会被判成"落后者"），
于是"情况举不完、补丁打不完、越补越走散"。

### 1.2 需求目标

**一条规则覆盖所有情况：不管中途发生了什么，每条路线边界强制重新对齐一次，误差不跨路线累积。**

### 1.3 可验收的"完成"标准

1. **不变量**：任何成员在**没有到达路线边界锚点之前**，不得开始下一条路线。即"没人能独自跑到前面去"。
2. **有界**：每次锚点最多等待 `RouteAnchorWaitSeconds`（默认 60s）；超时后落后者只能被"拉"或"剔除"，**绝不允许无限等待**。
3. **可确认**：所有"拉"的下发都有 Applied 回报，服务端能知道谁没跳成，不靠假定。
4. **缺员有明确结论**：剔除后按房主配置"缺员继续"或"协调停止"，不允许"少人却继续跑"。
5. **零回归**：单机模式、路线内普通同步点规则、FastReport、掉线逻辑行为不变。
6. **可回滚**：一个开关即可退回今天的行为。

## 2. 核心机制

### 2.1 一句话

**在每条路线的边界上做一次权威对账，对账只看三件事，每个缺席者只有三种结局。**

对账只看：**到了没有 / 活着没有 / 还有没有响应**
（不看异常标记、不看进度数值、不看路线变体 —— 这些正是会误判的东西）

| 结局 | 判定条件 | 动作 |
|---|---|---|
| **等** | 心跳新鲜（≤30s）且最近有上报 | 大家等它，上限 `RouteAnchorWaitSeconds` |
| **拉** | 心跳新鲜，但停滞（超过 `RouteAnchorStallSeconds` 无任何上报） | 下发"**跳到锚点（下一条路线起点）**"指令；客户端确定性执行并回报 Applied；最多 `RouteAnchorPullRetries` 次 |
| **放弃** | 心跳过期 / 已判 Offline | 从"必须集合"剔除（复用既有心跳+宽限期判死）；按 `RouteAnchorOnMissing` 决定继续或停 |

### 2.2 为什么这样就不必再枚举情况

- **误差不累积**：中途所有机制都可以出错，但影响被限制在"一条路线之内"；边界强制归零。
- **不依赖脆弱推断**：锚点按**路线索引**对齐，不依赖进度数值/变体/异常标记。
- **有界**：等有上限、拉有次数、放弃走既有判死，三条路都收口。
- **可确认**：拉的结果有 Applied 回报（复用本轮已建通道）。

## 3. 实现方式

### 3.1 锚点位置（复用现有空转的检查点）

- **落点**：客户端 `AutoHoeingTask.cs:3693` 那个"线路同步检查点" —— 把空转的 `CheckSyncAtRouteStart` 换成真正的锚点等待。
  （该位置语义完全一致：每条路线开始时执行一次，天然就是路线边界。）
- **锚点 ID**：`anchor_route_{routeIndex}`，携带路线索引与世代（房间/轮次），跨轮不污染。
- **参与者**：全员在线成员，**不区分正常/异常**。

### 3.2 客户端改动（3 处）

1. **到达锚点**：路线开始前调用 `WaitAtRouteAnchorAsync(routeIndex, ct)`：
   - 沿用既有 `subscribe-before-action` + 超时模式；
   - 上报用既有 `sync.waitForAllPlayers`，`syncProgress = -1`（服务端按"等所有"处理，天然**无豁免**，正是锚点需要的语义）；
   - 超时/房间关闭等异常按既有约定映射（不吞异常）。
2. **执行"拉"**：收到"拉到锚点"指令时做确定性跳转：
   - 复用既有 `SkipRouteRequested`（跳到下一条路线）+ 既有"跳到指定路线"能力
     （`AutoHoeingTask.cs:3630-3655` 的 `WaitForStartRouteAsync` + `count = target - startIndex; continue;`）；
   - **唯一需要新增的客户端能力**：把"跳到指定路线"从"仅 `IsAbortRequested` 路径可用"扩展为"锚点路径也可用"（同一套跳转代码，加一个触发源）。
3. **回报结果**：跳转成功/失败后回报 Applied（复用本轮已建的 `sync.reportCollectiveSkipApplied` 通道语义），并**再次上报到达锚点**。

### 3.3 服务端改动

新增房间状态 `RouteAnchorState`（`BgiCoordinatorServer/Models/`）：

```
AnchorId        // anchor_route_{n}，含世代
RouteIndex      // 锚点对应的路线索引
Generation      // 房间 / 轮次（跨轮隔离）
Arrived         // 已到达的连接集合
Pulled          // 已下发"拉"的连接 → 次数
Dropped         // 被剔除的连接
Phase           // Collecting → Pulling → Released
DeadlineUtc     // 等/拉 的截止时间
```

对账流程（每次锚点评估时执行，全部在 `lock(room)` 内决策、锁外广播）：

1. 记录到达（复用 `RecordArrival`）。
2. 逐个缺席者分类：**等 / 拉 / 放弃**（判据见 2.1）。
3. "拉"：广播锚点跳转指令（复用 `room.startRoute` 事件，payload 增加 `anchorId` + `routeIndex`），
   按 `RouteAnchorPullRetries` 有界重发；收到 Applied 后转入"等到达"。
4. 全员都有结论（到达 or 剔除）→ 广播锚点放行（复用 `AllArrived`，`syncPointId = anchorId`）。
5. 按 `RouteAnchorOnMissing` 决定缺员后继续或协调停止。

### 3.4 配置（房主设置 → 同步给成员）

| 字段 | 默认 | 含义 |
|---|---|---|
| `EnableRouteAnchor` | true | 总开关（多人模式内生效） |
| `RouteAnchorWaitSeconds` | 60 | "等"的上限 |
| `RouteAnchorStallSeconds` | 30 | 判定"停滞"的阈值（超过则转"拉"） |
| `RouteAnchorPullRetries` | 2 | "拉"的最大次数 |
| `RouteAnchorOnMissing` | 继续 | 剔除后：继续 / 停止 |

落点：服务端 `RoomConfig` + 客户端 `AutoHoeingConfig` + 既有 host→member 配置同步链路。

### 3.5 与现有机制的关系（谁留、谁降级）

| 机制 | 处置 |
|---|---|
| 路线内普通同步点（`AllArrived` / 进度豁免） | **保留不动**，继续做"路线内局部优化" |
| 集体跳段（`RequestSkipToProgress`） | **降级为可选**：默认不再中途任意触发（避免把人拆散），其"跳到指定位置+确认"能力转为锚点的"拉"通道 |
| 本轮已做的 SkipId / Applied / 专用异常 | **继续留用**，是"拉"的确认与执行前置件 |
| `route_sync_done`（轮首）、`round_end_N`（多世界轮末） | 保留，作为轮次级锚点；路线锚点是其细分 |
| 单机模式 | 全部在多人与开关内，**零路径** |

## 4. 验收与测试

### 4.1 服务端单元测试（新增）
- 锚点对账三分类：等 / 拉 / 放弃各自命中条件；
- 等待上限到点转"拉"；"拉"重试到上限转"放弃"；
- Applied 幂等、旧锚点/旧世代消息忽略；
- 剔除后按配置"继续"或"停止"；
- 有活动锚点时重复评估不创建第二个锚点。

### 4.2 客户端单元测试（新增）
- 路线开始必上报到达锚点；
- 收到"拉"能跳到指定路线并回报 Applied；
- 跳不动时回报失败（不静默）；
- 单机/开关关闭时不触发任何锚点行为。

### 4.3 场景回归（把本次实测的场景搬成断言）
- 3 人 + 落后 A（A 在早同步点 / A 已脱离集合）；
- A 复苏跳段 + B 打完 + C 刚开打 + D 在战斗前同步点等；
- 断言：**最终所有人在同一条路线边界对齐**（而不是"各自在不同点等"或"裂成两拨"）。

### 4.4 不回归验证
- 现有服务端 149 例、客户端全量（已知 14 例预存失败为基线）保持不新增失败。

## 5. 代价与回滚

- **代价**：每条路线多一次集合等待；慢的人会被等（有上限可控）；单轮总时长增加。
  用 `RouteAnchorWaitSeconds` / `RouteAnchorPullRetries` / `RouteAnchorOnMissing` 三个旋钮控制。
- **回滚**：`EnableRouteAnchor = false` → 立即退回今天的行为。
  代码不删、协议不改线形（新增事件/字段旧端不识别即忽略），因此回滚不需要重新发版协议。

## 6. 实施顺序（分阶段，可分段验收）

1. **阶段 1（服务端）**：`RouteAnchorState` + 对账状态机 + 配置字段 + 单元测试（不接客户端，用测试驱动）。
2. **阶段 2（客户端到达）**：路线开始调用锚点等待 + 配置读取 + 单元测试。
3. **阶段 3（客户端"拉"）**：开放"跳到指定路线"给锚点路径 + Applied 回报 + 单元测试。
4. **阶段 4（场景回归）**：把 4.3 的场景写成端到端断言。
5. **阶段 5（收尾）**：全量测试 + 记忆沉淀。

## 7. 禁止触碰（防"修好这坏了那"）

- 单机路径、`FastReport`、普通同步点放行判定（`ShouldBroadcastAllArrived` / 进度豁免）、
  掉线宽限期与判死、多世界轮换主流程、复苏/卡死保护分支、路线内消费点顺序。
- 任何改动都必须由 `EnableRouteAnchor` 或既有开关门控；关闭时逐字节回到今天的行为。
