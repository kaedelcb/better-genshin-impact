**具体反例：**

当前版本 B 的修复前红夹具正常执行，退出码为 1，生成正确失败 TRX，并以 `expect_success=false` 纳入材料。新增 capture 按第 54 行不给合格标记，第 56 行又要求该报告来自有效执行证据；合法红夹具因此不能进入已接入批次的审查。

突变验证还有第二个冲突：正确的 mutant 执行既应非零退出，其输入 M 又应不同于最终恢复版本 B。若统一要求退出成功、输入等于当前 B，真实突变证据无法认证；若让 `mutations[]` 继续绕过 ExecutionEvidence，旧 mutant TRX 与手填退出码仍可能被误用于新版本，原来源缺口没有闭合。

**建议集中补齐以下合同，再实施：**

1. **分离来源认证与结果判定。**  
   `capture(recipe)` 保存实际退出码、完整结果和输入/产物身份。完整、可核验的预期失败执行可以获得来源收据，但绝不能因此成为绿色回归。启动失败、超时、输入漂移、缺结果仍阻断认证。

2. **明确按用途验证的接口。**  
   使用 `validate_execution_evidence(receipt, expected_identity, purpose)`，至少区分：
   - `current_regression`：绑定当前输入，退出 0，TRX 绿色。
   - `negative_test`：绑定指定输入，核验预先声明的失败测试及断言。
   - `historical_baseline`：绑定原执行身份，只用于比较。
   - `mutation`：验证三次执行之间的关系。

3. **让 `mutation_check()` 消费三份认证收据。**  
   固定顺序为：B 基线执行 → 精确突变为 M → M 执行并命中目标断言 → 字节恢复 B → B 恢复执行。绑定突变补丁、输入清单、三次产物与结果；不得只验证最终源码已恢复。最终收口仍要求当前版本 B 的绿色回归。

4. **补充集成及反向突变测试。**  
   验证合法红夹具和 B→M→B 可以通过各自证据门；错误断言、构建失败冒充突变命中、旧 mutant 报告重放、恢复不完整均拒绝；负向或历史证据不能满足当前绿色回归门。保留现有“非零退出＋绿色 TRX 不得证明成功”的测试。

上述修订不需要放宽任何绿色回归要求。它需要明确的是：**失败结果可以是真实、有效的负向证据，但不能被消费为成功证据。** 本轮不构成实现验收。
