**结论：changes_required。发现 7 项 MUST／IMPORTANT，建议补齐以下合同后再实施。**

本次仅通过 `review_snapshot.inspect_snapshot` 阅读冻结文件；未执行命令、测试或修改文件。以下反例是静态推演，未宣称已运行复现。`review_process.py` 尚不在快照中，发现针对方案及其与现有工具的衔接。

1. **MUST — reservation 与实际发送之间缺少可恢复的计费状态机。**  
   依据：`design.md:13`。
   
   **反例：**第 8 次 reservation 已落盘，进程在启动 reviewer 前崩溃；另一种情况是在启动后、记录子进程身份前崩溃。两者都只留下 reservation，恢复时无法可靠区分“未发不计”与“已发必须计”。仅人工确认当前没有子进程，不能证明之前没有发送。按 batch 加锁也未说明同批在两个 worktree 中是否共享锁及预算。
   
   **修复：**定义统一 `BatchStore`，以稳定的批次身份定位唯一账本，所有写命令共用锁。明确 `prepared → dispatch_intent → completed/failed/unknown`；发送前持久提交 intent，崩溃后无法排除发送的记录继续占额，禁止自动重发。只有可证明未启动的本地失败才能追加释放记录。账本必须明确原子提交、持久化、损坏处理及恢复协议；恢复使用 request ID、进程创建身份和进程树，不能只检查 PID。  
   **测试：**逐个持久化／启动边界注入崩溃；双进程和双 worktree 抢最后一个额度；超时后后代仍存活；重复恢复不重复计费或释放。

2. **MUST — 旧批兼容与 adopt 没有不可回退的接入身份。**  
   依据：`design.md:7,19`；`workflow.py:198–236,487–493`。
   
   **反例：**旧 opening 存在的批次 adopt 成功后，恢复旧 manifest 或删除 `review_process` 配置，又满足“已有 opening 保持旧验证”，从而绕过新门禁。暂停批次若已有 7 次请求，重复 adopt 或换目录重建配置，还可能重新导入不完整计数。现有 `begin()` 的“检查不存在后 `write_text`”也不能兑现并发下的 write-once。
   
   **修复：**增加持久 `BatchRegistration`：绑定原 opening 哈希、稳定 batch ID、接入模式及历史请求／发现索引。legacy 资格由明确登记确定，不能只看文件存在；adopt 是单向、幂等事务，后续缺配置必须阻断。历史报告、失败请求及未决项按来源身份去重导入，缺失记录记为未知。opening 使用原子无覆盖发布。  
   **测试：**adopt 中断／重试、恢复旧 manifest、移除配置、目录别名、重复历史请求、并发 begin；旧批仍可读取，但接入后不能退回旧门禁。

3. **MUST — 暂停批次的既有重要代码问题可能使修复许可永远无法生成。**  
   依据：`design.md:7,15,17`。
   
   **反例：**暂停批次有一个未解决的重要代码缺陷；reviewer 认可剩余修复方案，但该缺陷必须等实施及回归后才能关闭。`implement` 又要求“无重要未闭合项”，于是没有许可不能修、没有修复不能关闭。
   
   **修复：**区分 `plan_obligation` 与 `implementation_obligation`。方案缺陷必须在许可前关闭；既有代码缺陷可保持原等级和 open 状态，绑定已审修复步骤、允许修改范围及验收测试后，获得**仅用于修复的许可**。它仍阻断生产与 closeout。不得将“方案获准”记录成“缺陷已关闭”。  
   **测试：**带既有重要项的 adopt 能进入限定修复；未经方案覆盖的缺陷不能取得许可；代码问题未关闭时 closeout 必须失败。

4. **MUST — 报告 schema 尚不足以证明报告来自本次请求，也未规定矛盾结论的处理。**  
   依据：`design.md:13,15–17`；`workflow.py:269–289,399–407,546–548`。
   
   **反例：**路径和结构均有效的旧 `pass` 报告被放入本次输出位置，若没有 request／snapshot 绑定就可能被接受。另一份报告同时写 `pass` 和新 IMPORTANT，或者遗漏一项旧发现；仅验证枚举及必填字段不能安全决定许可。
   
   **修复：**由 runner 生成不可混用的 `ReviewReceipt`，绑定 request ID、batch、stage、快照、方案、策略／工具版本、模型配置、进程结果及原始输出哈希。结构化报告只能从该次成功运行产生；缺失或无法核实的实际运行信息阻断。维护累计 findings ledger，要求旧发现逐项处置、不得遗漏或降级；`pass` 必须与未决项和 unknown 集合一致。修复／回归引用绑定具体证据内容及执行来源，不能只信重新填写的源码哈希。  
   **测试：**跨批／跨阶段／旧请求报告重放、退出失败但残留 pass、遗漏旧项、pass 携带重要项、报告引用不存在或旧版本回归证据。

5. **IMPORTANT — 版本失效边界没有覆盖策略、配置、审查工具和证据依赖。**  
   依据：`design.md:17,19`；`workflow.py:566–579`；`consultation_triage.py:89–99`。
   
   **反例：**方案文件不变，但缩小允许源码目录、改变必需模型或更新判定模板，旧许可是否仍有效没有定义。现有 `verify()` 只验证已枚举输入；triage 的等效审查仅检查报告存在和声明的源码哈希，没有将报告内容、设计及审查策略一起绑定。
   
   **修复：**定义统一 `ReviewIdentity`，包含方案、源码清单及内容、合同／配置、导航、策略、schema、工具 bundle、模型要求和证据索引摘要。明确失效表：方案／合同／范围变化使 plan 及下游许可失效；许可范围内源码变化要求新的 implementation 审查；回归证据变化使相关验收失效。所有门命令验证 bundle，不能仅新 worktree 验证。既有 triage 的“可复用”不能直接代替新 receipt。  
   **测试：**逐字段变化验证失效，包括新增依赖、改变模型、替换模板、修改旧报告；正常实现变更不得误要求源码与 plan 快照永远相等。

6. **IMPORTANT — 安全快照没有覆盖 Git diff 的历史敏感内容和输出自包含问题。**  
   依据：`design.md:11`；`workflow.py:36–45,509–510,528–536`。
   
   **反例：**当前允许目录已删除凭据文件，但完整 staged diff 仍包含删除前的密钥；仅过滤当前文件复制无法阻止泄漏。允许目录包含 `_workflow/<batch>` 时，新 snapshot／日志自身可能进入下一次枚举。现有路径函数还允许指向仓库内部的链接，不能直接复用来实现方案承诺的“禁止链接／重解析路径”。
   
   **修复：**建立唯一的捕获策略，覆盖当前文件、Git 历史 diff、显式证据及输出目录。敏感材料与“完整 diff”冲突时阻断并登记，不静默裁剪后宣称完整。拒绝输出位于输入树中，逐路径组件检查链接／重解析点，限制普通文件并处理大小与解码失败。冻结前后对路径、内容、Git HEAD／index／diff 做一致性检查，快照完成标记最后原子发布。  
   **测试：**已删除密钥的 diff、嵌套输出目录、内部链接／junction、捕获期间新增删除及重定向、半成品快照不可送审。

7. **IMPORTANT — 新门禁与旧 audit 的调用顺序存在循环及容量不兼容风险。**  
   依据：`design.md:17,25`；`workflow.py:459–480,525–527,546–548`。
   
   **反例：**若把 implementation pass 强制加入 `audit --stage review`，首次 implementation 审查前就无法生成材料；若只增加独立 closeout 命令，旧 `audit --stage closeout` 仍可能被当成完成入口。全目录快照还可能超过旧工具固定的 512 KiB packet 上限，即使本地 reviewer 可以分步读取。
   
   **修复：**拆分接口：
   - `validate_evidence()`：沿用证据／回归检查，不依赖正在生成的审查结果。
   - `prepare_review()`：冻结完整材料，通过导航分步读取；不要求全量源码拼入旧 packet。
   - `validate_review_receipt()`：检查独立审查结果。
   - `validate_closeout()`：统一汇合当前版本、回归、发现闭环及 implementation receipt。
   
   旧入口对已接入批次必须调用对应的新门禁，或明确返回“仅材料检查，不能收口”。  
   **测试：**首次 implementation 审查可达、无 pass 不能收口、超过旧 packet 上限仍可完整审查、legacy 文档／代码行为保持兼容。

建议实施顺序为：**先定批次身份与事务状态机 → 定 findings／许可语义 → 定版本与来源绑定 → 实现安全快照 → 接入旧入口 → 完成崩溃、并发、兼容及反向突变测试 → 最后做独立 reviewer 演练。**

当前方案需要上述修订；静态审查不能替代这些故障注入与实际调用验证。
