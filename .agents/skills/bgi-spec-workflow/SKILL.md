# BGI Spec 工作流

为用户明确指定的任务使用规格驱动开发。此 Skill 按需启用，不是宿主的原生模式切换，不自动开启 Plan，也不为整个项目永久开启 Spec。

## 启用与退出

- 用户明确说「用 Spec 模式做……」「创建这个功能的 Spec」「继续某个 Spec」或调用 $bgi-spec-workflow 时使用。
- 仅问有没有 Spec、解释某份规格、普通聊天、一般修复或只查历史文件，不创建规格、不切换开发流程。
- 仅说「开启 Spec」但未提供任务时，询问要处理的需求，不创建空目录。
- 当前 Spec 的补充、修改和继续沿用该流程；期间普通提问直接回答。用户明确退出、替换为无关任务或当前 Spec 完成后，恢复普通流程。新会话仅因磁盘存在未完成 Spec，不能自动续做。
- allow_implicit_invocation 为 false。AGENTS.md 只保留上述明确触发的入口，不以问题复杂或涉及多端为由自动使用。

## 先判定本次工作范围

| 用户意图 | 做到哪里 |
|---|---|
| 只分析、只写 Spec、先不改代码 | 输出或保存需求、设计和任务，停在文档阶段 |
| 按 Spec 开发/修复到完成 | 完成规格、实施、验证、回填；已有授权无需逐阶段再次确认 |
| 继续指定 Spec 或指定任务 | 读取当前记录与代码，按已授权阶段/任务续做，不自动扩展到整个计划 |
| 只审查 Spec | 给出可定位的缺口和建议，按用户要求决定是否修改文档 |

若「继续」对应哪份 Spec 或实施授权不清，先做只读核实，再询问真正缺少的那一项信息。目标和验收中的关键产品歧义需澄清；常规实现选择可说明依据后自主决定。

遵守宿主当前模式的文件修改限制。若当前模式仅允许规划，则在回复中起草 Spec，不能宣称文档已保存或代码已实现。

## 执行入口

读取 [阶段与接力规则](references/workflow.md)。项目定位和历史筛选沿用仓库 AGENTS.md 与已安装的 bgi-project-development；已读且未变化的内容无需重复加载。

新 Spec 放在实际仓库根目录下的 .agents/specs/<topic>/，topic 简洁且能识别业务。存在同一任务时复用并保留已完成工作，不能覆盖或另建重名任务。KIRO 原始 .kiro/specs 默认只读；需接续其中任务时，在 .agents/specs 中建立有来源的工作副本。

按任务需要使用三个模板，填写实际内容并移除不适用章节，不把占位符交付为完整方案：
- [需求模板](assets/requirements.md)：目标、可验证验收与应保持的行为。
- [设计模板](assets/design.md)：当前证据、改动方案、兼容/失败处理与验证映射。
- [任务模板](assets/tasks.md)：范围、依赖、任务状态、验证证据与接力点。

已有 Spec 使用 bugfix.md、不同编号或不同结构时，沿用其有效形式；不为符合模板进行无关格式重写，不制造重复事实源。

## 完成标准

规格文档完成：需求、设计、任务之间可追溯且没有影响下一阶段的未处理矛盾；明确区分草案与可实施方案。

实现完成：本次范围内的必要任务完成，验收有相应证据，未完成验证与风险如实列出；必需验收未证实则仍为待验证/受阻，不能勾成完成。用户只要求文档时，以文档阶段交付完成为准。

普通任务不强制 PBT、子代理、外部调研、提交或部署。测试形式与影响相称；不删除/排除失败测试来完成任务，不借 Spec 扩大对运行程序或外部系统的授权。
