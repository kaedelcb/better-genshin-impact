# 阶段、状态与接力

此流程只服务于已明确启用的 Spec 任务。进度以该 Spec 的 tasks.md 为单一登记处，不创建模拟 KIRO 状态机的 tasks.meta.json，也不假设旧工具或 Hook 存在。

## 1. 接手与事实核实

确认当前工作区、分支和用户/其他 Agent 的差异，定位相关历史及实际实现。已有 Spec 先读状态和接力段，再读任务引用的需求、设计与源码。状态记录不能替代当前代码验证。

记录当前实际行为、用户期望以及需要保持的正常路径。Bug 类任务先取得复现或其他有效证据；能建立有价值的失败测试时使用，无法自动复现时记录观测依据和验证缺口。不能为满足模板硬造必红测试。

公版/茶包双引擎、共享单机/联机入口、跨端字段和任务终态沿用项目开发 Skill 的领域导航。调查深度以当前问题为界。

## 2. 需求

- 赋予稳定需求编号 R-1、R-2 等。说明具体触发条件和可观察结果，避免「正确处理」。
- 同时列出本次范围、明确排除项和需要保持的行为 P-1 等。把 Bug 的触发/复现、当前与期望行为分清。
- 需求应可验收，但不必提前锁死函数名或逐行实现。源码落点和技术方案属于设计。
- 区分阻塞决策的问题与可合理默认的选择。已获授权的判断不重复询问；真正决定行为的未知不能默默猜测。
- 用户只要需求时，做到需求即可；无需硬建后续空文档。

## 3. 设计

将方案联系到当前代码证据和已存在的机制。用文件/符号与调用链描述关键改动，不在查证前编造路径或照抄陈旧行号。

对相关项具体评估：
- 目标调用方和需保留行为的其他调用方；
- BGI、助手、服务端及 WEB 中实际涉及的端与字段消费路径；
- 配置缺省、旧数据加载、协议兼容及部署约束；
- 状态迁移、取消/抢占、超时与失败路径；
- WPF 绑定或可见行为的验证方法；
- 回退本次修改的方法，避免涉及运行数据或覆盖他人改动。

按需要比较候选方案，记录实际取舍；不强制每次外部调研或多套方案。设计粒度足以让接手者安全实施，避免把大段未来补丁重复复制进文档。

为每项需求和保持行为安排对应验证 V-1 等，选择能证明行为的单测、集成测试、静态检查或运行观测。纯决策函数适合时可用 PBT；不把所有风险都强制转换成 PBT。

## 4. 拆分任务

按可独立验证的行为改动拆任务 T-1、T-2 等，并记录需求/设计引用、依赖、改动范围和完成依据。一个任务可跨必要文件，不机械按一个文件一个任务拆分。

任务完成要能追溯到验收。实现、检查与必要回归可以交错推进，不等全部代码写完才验证。计划变更时保持稳定 ID，注明撤销/替代原因，不通过删除原要求消除未完成事项。

tasks.md 使用：
- pending：未开始；
- in_progress：正在实施；
- blocked：缺少明确依赖/信息/环境，记录原因与可继续事项；
- done：本任务完成条件已有证据；
- skipped：仅限用户移出范围或可选任务，说明理由，不能冒充 done。

仅 done 项勾选 [x]。未完成、待验证和 skipped 保留未勾选并注明状态。这里是文件记录，不操作宿主的目标状态工具，也不触发后台调度。

## 5. 实施、变更与验证

用户已要求开发到完成时，在范围内连续推进；不人为增设需求、设计、任务三次审批。用户要求阶段确认或仅文档时停在对应边界。

每次进入任务前检查当前文件与前提是否仍成立。可自行恢复的工具失败先诊断与核实，不能把每次失败都变成用户审批；也不原样重复无效操作。

需求改变后同步修订受影响设计、任务和验收映射。已完成项若受到影响，标记需重新验证，不能继续沿用旧通过结果。新的范围或关键语义变化明确说明。

验证记录保存实际命令/操作、结果与证据位置，分清构建、测试、静态和实际运行的证明范围。缺少必需的实机证据时记录待验证，不擅自勾成整体完成；用户已明确接受的范围调整按新范围验收。

## 6. 结束与跨会话接力

tasks.md 接力段写清：
- 本次授权阶段/范围与最新用户决策；
- 最近完成、正在进行及受阻任务；
- 实际验证结果与尚未验证的事项；
- 下一步具体动作及需要重查的前提；
- 本次涉及的工作区文件及注意事项，避免把别人改动归为自己成果。

不保存密码、令牌等凭据；运行时临时信息只在必要的任务记录保留，不升格为长期规则。

完成时以需求→任务→验证映射检查遗漏，并总结本次阶段成果。需要更新项目经验时引用 bgi-project-development 的记忆维护流程；没有新经验无需写入。
