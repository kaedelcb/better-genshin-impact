# 跨端排障与修改决策

用于命令无效、任务吞组、提前恢复、玩家行为分叉、遥控端状态不一致等问题。先用当前代码确定实际通路，以下链路是取证框架，不能假定每次都经过全部节点。

## 找到第一个事实失配点

从可见现象回溯：发起端意图 → 服务端路由/房间 → 目标助手 → BGI 接收/排队 → 引擎执行 → 事件和状态查询 → 助手合并 → UI。

对相关节点记录同一动作的身份（如 requestId、jobId/taskHandle、generation、房间/玩家身份、PID/SessionId，具体字段以当前协议为准）、时间及状态来源。日志要能回答「命令去了谁、谁接收、谁执行、何时进入哪个终态」。先检查拒绝和否决分支，而不是只看成功路径。

按发现缩小范围：

| 证据 | 后续检查 |
|---|---|
| 发起端有发送，目标端无接收 | 目标选择、房间/连接注册、协议路由、断线缓存或旧会话 |
| 已接收但未执行 | 排队、槽位占用、业务拒绝、抢占/取消、实际启动入口 |
| 已执行但展示未更新 | 事件订阅、状态快照字段、服务端缓存、增量合并、VM 通知与绑定 |
| 各玩家做出不同动作 | 房间仲裁、命令身份、幂等、Applied 回报、退化策略 |
| 多次修改画面或行为不变 | 运行进程路径、产物、源码副本、实际调用分支 |

## 状态与生命周期

已发送、已接收、已入队、已开始、动作已应用、任务已完成分别取证。查询失败、目标不唯一或旧会话数据应保持未知，不能转为空闲、成功或条件反转。

涉及执行事实时先查当前机制：

- BetterGenshinImpact/Service/Execution/JobRegistry.cs
- BetterGenshinImpact/Service/Execution/PreemptionGate.cs
- BetterGenshinImpact/Service/ExternalInterface/BgiTaskCoordinator.cs
- Docs/design/unified-job-registry-master-plan.md

事件是快速通知，丢失后的推进依据需落在状态查询或终态登记。计数器差值不能普遍替代显式完工标志；当前任务取消令牌不能可靠承载跨任务间隙的抢占意图。等待槽位/停止完成以状态为准、时间为上限；超时处理要明确，不能谎报成功。

回执型流程先订阅再执行动作，等待有取消与超时，结束解除订阅。旧任务、旧房间与正常收尾事件要与异常停止区分。

## 房间一致动作

跳段、重开等动作需要结合项目现有机制检查：服务端仲裁、命令唯一身份、幂等、必要成员确认、有界重播与失败退化。广播发出不等于全部应用，各端本地判断可能产生不同结果。

协调指令若经过异常通路，确认没有被普通 RetryException 的复苏、escalation 或重试策略吞掉。实例与依据见 .agents/memory/fix-collective-skip-applied-ack.md 和实现模式 v2 的全组收敛章节。

## 字段、配置和展示

扩展成员/任务状态字段时，从产生到展示逐段核对：模型、序列化、上报、服务端缓存/复位、全量和增量广播、助手 Add/Update 合并、只读快照、UI 和诊断输出。只检查一个广播出口可能漏掉监控端或缓存路径。

沿用当前序列化约定。检查大小写、缺省、显式 null/空串、保存后重载及类型标记；加载失败后的默认对象不能覆盖有效配置。IPC 信封字符串转换要查现有解析辅助方法，避免 JObject 的显式 null 被 ToString 转为空串。

当数据已经正确到达 ViewModel，再检查 DataContext 实例/赋值顺序、通知、属性值来源及容器实际尺寸。不要把历史个案中的 WPF 推论当成通用定律。

## 验证闭环

针对实际失配环节验证修复，兼顾受影响的正常路径、旧配置或其他端；运行证据不足时如实说明。不要自动扩展为全系统重构。复盘引用路径和案例能指导诊断，不证明本轮遇到的根因与旧问题相同。
