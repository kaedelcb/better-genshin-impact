阶段：开发侧修复与验证完成；证据与真实游戏验收边界见 tasks.md
更新日期：2026-10-20

## 目标与范围

修复同一 BGI 进程内四人上线接管、绑定锄地任务、各端绑定完成动作的连续执行。暂时占用、通信/记录异常、回复丢失与累计等待时间不得丢弃请求、重复启动或误停。复用现有队列、执行根、请求编号和批次，不新增用户确认步骤。

不包括 BGI 崩溃、断电或执行历史已经丢失后的恢复；不修改游戏路线/战斗逻辑、真实 User、第三方 JS；不操作运行实例，不自动部署或 push。永久无法通信时只能保留待办持续重连，不虚报已执行。

## 验收条件

| 编号 | 条件与预期结果 | 验证 |
|---|---|---|
| R-1 | 原 BGI 已确认同一原任务让位且可接任务时，助手阶段并发变化或补记录失败不取消四人开锄；原恢复信息不丢失 | V-1 |
| R-2 | 暂时占用、准备尚未完成或网络短调用超时后，保留同批、同成员、同项，条件满足后继续，无需再次上线/重置 | V-2/V-4 |
| R-3 | 每项锄地与完成动作具有固定请求编号和冻结内容；重复、并发、迟到与丢回复只对应一个真正执行任务 | V-3 |
| R-4 | BGI 已接收请求但助手查不到普通登记时，可由原编号取回队列/运行/结束事实；未受理才能继续原提交，不因查询为空而另建任务 | V-3/V-5 |
| R-5 | 本批未确认请求、终态和去重关联不因时间或历史条数清除；缓存 unknown 可由真实队列事实修正 | V-3/V-5 |
| R-6 | 辅助登记、状态推进或终态记录异常不阻止已接收任务执行，不遮盖真实执行结果；补登记沿用原编号和原内容 | V-5 |
| R-7 | 每端最后一个绑定配置组结束后，执行该端冻结的完成策略；原任务恢复后接回原计划继续，已有后续任务先观察而非再次要求空槽 | V-6 |
| R-8 | 普通报错、观察/控制超时、队友异常不得取消本端正在运行的任务或原恢复现场；明确停止/重置必须撤销待启动动作并停止已接收任务，迟到回复不复活 | V-7 |
| R-9 | 真实失败、取消、未知不能写成成功；排队、已开始、已完成和记录待补分别保留实际事实 | V-1至V-7 |

## 决策

用户已经授权实施到完成，无逐阶段额外审批。单次 IPC/RPC/连接仍可有超时，以便返回重试；累计超时不再等同业务失败或取消。真正队列无法接收时明确回未受理，继续原请求；永久断链不能保证物理执行。BGI 原队列项是执行事实来源，JobRegistry/回执是可补记录，不额外增加“登记成功才能入队”的门槛。
