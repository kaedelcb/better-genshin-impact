# 四人锄地按实际状态接续：设计

阶段：开发侧实现与验证完成；保留最终设计，执行证据见 tasks.md
需求依据：[requirements.md](requirements.md)
更新日期：2026-10-20

## 结构与最小改动

沿用三端现有链：服务器保持同批成员和业务项；助手保持唯一执行循环及唯一完成动作任务；BGI 保持原队列项、原执行编号和真实结果。不创建另一套调度器或恢复服务。

### D-1 接管和原计划恢复（R-1/R-7）

TaskCenterHost.OnlineHoeing.cs 在合并回调内按最新原任务身份核实，允许 prepared/suspended/parked 的合法单向变化，保留 parked 并补入同一 BGI 的票据、继续位置。明确停止及不同身份仍拒绝。

OnlineBatch 先保留成功挂起回执和票据，再确认原 BGI 已退出/可接任务；补记录未完成不抛 takeover_failed，不清票据或让原 Runner 跳过原节点。完成动作中复用第一次生成的 continuation/ResumeKey；已恢复的 JobId 先保存并只补原计划关联，不能再次恢复或停止刚恢复的任务。

### D-2 BGI 队列事实与不重复（R-3至R-6）

只对明确选择本次能力的带固定编号任务启用 task.stateContinuation.v1；旧调用默认保持。任务请求携带 retainUntilAcknowledged=true（固定 key、同一 BGI、冻结任务内容）。现有 Submit 的锁和原 PendingTask 负责唯一认领；队列接收、在跑和终态都能按 key 找回同一 taskHandle。辅助登记失败继续执行，之后补同一编号，不能把另一次登记当成另一次执行。

扩展现有 ext.task.queueStatus，允许按 idempotencyKey 查询并返回 taskHandle/实际状态/原锄地证据；普通 JobRegistry 缺项时仍读取队列事实。已接受的本次请求及结果不参加普通30分钟/容量淘汰。重复启动请求返回已有任务；unknown 回执有真实队列事实时修正，不能永远回放 unknown。真正未入队明确拒绝；已登记但未排队继续原队列项，不能换编号。

增加 ext.task.acknowledge（submissionKey、taskHandle、bgiEpoch），仅在助手已保存终态后释放详细结果的保留；同号已结算信息保留至进程结束防迟到重发。该确认是程序内部请求，不新增用户确认。BGI 等槽时间不终结此类已接收任务；停止令牌仍随时生效。

JobRegistry/回执写失败不得成为额外入队条件。TaskRunner 和 OneDragonFlowViewModel 使用原 descriptor.JobId；补全普通启动 key/指纹/操作名透传。登记、运行状态和终态推进均容错，不遮盖真实执行结果。

### D-3 助手按同动作接续（R-2至R-9）

锄地项沿用现有 RequestKey；完成动作新增固定 post-hoeing/<batch>/<uid> 逻辑 key，并保存 RequestIdentity、冻结提交内容和后继 JobId。启动回执不明时先按原 key 查询队列；必要时在原操作/原发送责任内幂等核实提交。不得新建操作、换 attempt 或重新播放已完成锄地。

RunCoordinatedBatch 的观察、控制和准备总超时只更新等待/重连状态，不退出后进入取消清理。保留每次网络请求短超时，使用既有检查/重连循环。原控制循环和待办不因 elapsed 时间永久失去接续资格。

完成动作由现有单个 finalization Task 内部接续：未启动时取得同 BGI 实时空槽状态；占用等待标记在确认未发送且占用结束后重评。已有 PolicyExecution 时先观察，不能再次要求空槽、重新释放或重新启动。两层 once 守卫保持防并发，但不永久缓存暂时失败；取消清理不能把尚未执行的动作清掉。

实现取舍（2026-10-20）：增强模式的冻结完成动作延续原批次已有执行权，直接复用 retained queue；不重新进入 R5 通用“新任务”仲裁。因此不扩改 ArbitrationAdmissionService 的数千行通用状态机，也不让其辅助台账重复阻断本批动作。必须保留 LocalSucceeded、同 batch/self/原执行器/BGI epoch、配置修订、控制上下文和明确停止围栏；preempt=false，实际别的任务占用就等。后续动作使用普通 group/onedragon 请求，不携四人锄地名单或 coordinatedHoeing 标记。原配置的普通优先级设置保存，但该动作不重新参加 R5 优先级排序。旧模式及普通手动新启动继续走原 R5 路径。原计划 Resume 仍通过原 Host 继续路径，受理记录只补关联，不重复恢复。

停止围栏在本批准备阶段首次绑定同一 BGI 时从 task.status 获取，并冻结为整批 StateContinuationStopVersion；所有锄地项和后续动作继承该版本，不能在每个新动作前取得停止后的新授权；原请求重交不刷新这个值。retained suspend 同样保存原停止版本；BGI 明确停止/重置后拒绝迟到原请求，不能因时间过去或重新联网恢复其执行权。

### D-4 服务端及停止（R-2/R-8/P-2）

CoordinatedBatchState 的注册/准备/接管/心跳累计超时不 Abort 同批；可恢复准备、记录、通信错误保持等待。只有真实业务终态和明确控制意图能结束相应任务。服务端时间不代表 BGI 已停止或任务失败。

助手区分“明确停止/重置”与普通错误撤销；普通错误不能触发 PolicyExecution 的 TaskCancel，不能从 finally/Cleanup 取消正在运行的原锄地任务。明确停止保持最高优先级并覆盖未起步、排队、已接受后继以及迟到受理；身份变化不授权向新 BGI 重放。

## 兼容与边界

BGI 新能力和服务器状态续办能力需能协商；旧普通启动/单机默认不被改为无限等待。实际发送时才冻结本次合法请求；已接收后由原队列项继续，不每次更改 expiresAtUtc 造成指纹冲突。不扩展断电/新 BGI 进程恢复。测试使用假的时钟/端口、隔离数据和真实状态机，不运行游戏或替换用户程序。

## 实施中的消费顺序补齐

- 恢复原任务的 BGI retained 结果有助手worker和原计划Runner两个消费者。worker只有在原Runner已保存该resume终态后才ack，避免原Runner未读结果就被辅助历史容量淘汰。
- 新模式原计划接续的临时记录/观察失败必须留在同一个Runner里重试；默认旧模式保留旧边界。准备记录已经发布但调用回执丢失时可重建同一continuation，不重复节点历史或尝试号。
- 明确未受理且本地无接管票据时，允许只清prepared/preparedGap并重采同一BGI目标；已parked/已受理不能用此路径丢弃。

## 当前实现与证据消费

- 增强完成动作由 `MainViewModel.StateContinuation.cs` 的同一 worker 接续。指定任务使用 `post-hoeing/<batch>/<uid>`；计划恢复使用冻结 continuation 中的原 key，原生恢复使用 `resume/<原ticket>`。三者均按实际 key 找回队列句柄并确认结果，不把恢复动作错误地归到指定任务 key。
- 完成动作真实终态及退出先保存。原计划停止/恢复关联已经确认时，先释放本端执行权；辅助 ack 暂失败只补 ack，不再准备/启动，不以 ack 等待阻断用户其他实际动作。明确停止仍受原 stop/reset 围栏约束。
- V-1 至 V-8 的具体用例、首轮失败、最终 TRX 与构建空位集中在 `tasks.md`，避免设计说明与最终执行证据各写一套结果。
- 四连接入口在现有单 STA/Application 回合中运行，服务器可由 `NEXUSBGI_TEST_COORDINATOR_DLL` 显式指向本次源码构建；BGI 仅使用私有命名管道。该场景能验证生产助手接收、续办、去重与队友迟到状态处理，不能证明四个真实游戏客户端或一条龙游戏路线全部执行完毕。
